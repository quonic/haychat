# HayChat Server Agents Documentation

## Build & Commands

- Typecheck: `odin check server`
- Test: `odin test server -define:ODIN_TEST_THREADS=1` (serial, as `check.sh` runs it)
- Build: `odin build server`
- Run: `odin run server`

## Multi-Channel Server

- Room visibility, chat sends, live-message fanout, and history retrieval are membership-scoped. Never trust a client-provided room ID without checking membership through the database flow.
- Persist a room message before fanout. Fan out the durable message fields, including its ID and timestamp, only to the room's current members.
- Router database work follows the typed request/continuation pattern in `MainRouterState`: queue a `common.DatabaseQuery`, record the matching pending request type, and handle its result in the exhaustive database-result switch. `common.DatabaseQueryRequest` and `common.DatabaseQueryResult` are tagged unions; the cleanup switches in `ipc.odin` are exhaustive, so a new variant will not compile until its cleanup is written.
- Prefer one SQL statement per client action when correctness depends on a check, as `PostRoomChatMessage` (membership check, insert, and recipients) and room history (membership check and page) do. Separate round trips let state change between the check and the action.
- Startup creates the default room: after `databaseMigrateSchema`, and before it reports readiness, the database process runs `DATABASE_ENSURE_DEFAULT_ROOM_SQL`, which inserts `general` (with every account as a member) only when `rooms` is empty, so it takes ID 1 (`common.GENERAL_ROOM_ID`) on a new database. `rooms.created_by_user_id` is nullable for that room; keep code that reads it ready for `NULL`.
- Identity is the client's Ed25519 key; `users.nickname` is the account's current name. `DATABASE_RESOLVE_USER_IDENTITY_SQL` handles every case in one statement: a key that owns an account resolves to it under an unchanged nickname, renames it (`DatabaseUserIdentityResult.renamed`, with the owned `previousNickname` freed in `IPC__database_query_response_deinit`) when the new nickname is free, and returns no row when another account holds it; a key with no account creates one or claims the nickname's keyless account (one with server roles, such as the seeded admin, only for `HAYCHAT_ADMIN_PUBLIC_KEY`). Do not split these checks into separate queries: `users_public_key_unique` and `users.nickname UNIQUE` turn a race into a statement error, never a second account. After a rename, `MainRouterState_completeAuthentication` updates `clientNickname` on the user's other sessions and broadcasts `ServerUserPresence` with the new name even when the user was already online. Chat and direct message rows store only user IDs, so history fetched after a rename shows the new name.
- The identity statement also reads migration 3's columns (protocol 14): a key whose account has `nickname_locked` (an admin renamed it) is never renamed and resolves under the locked name, and a banned account (`banned_at` set) is never renamed and resolves with `DatabaseUserIdentityResult.banned` and its owned `banReason`. Its columns are the user ID, rename flag, previous nickname, admin flag, the account's nickname after this login (owned `nickname`), the lock, the ban, and the reason. The router answers a ban with `ServerAuthFailure` `SERVER_BANNED_MESSAGE` ("This account is banned from this server", plus ": reason"; clients match the prefix) and a disconnect (`MainRouterState_refuseBannedSignIn`), and otherwise passes the nickname and lock to `MainRouterState_completeAuthentication`, which gives the session the account's name before it sends `ServerAuthSuccess{nickname, nicknameLocked}`.
- Room access modes (protocol 15, migration 4; `database_room_access.odin`, `router_room_access.odin`): `rooms.access` (1 Public, 2 Member invite, 3 Admin invite) and `rooms.history_visibility` (1 From join, 2 Full). `DATABASE_RESOLVE_USER_IDENTITY_SQL` joins a newly created account to every Public room in the same statement as the identity upsert; `DATABASE_CREATE_ROOM_SQL` adds every account to a new Public room (and stores Full history for it), and only the creator to an invite room when `creatorJoins`; `DATABASE_EDIT_ROOM_SQL` sets the access too, and a switch to Public adds every account in the same statement and returns the added IDs (`DatabaseRoomMutationResult.addedUserIDs`), which the router tells with `ServerRoomMembershipChanged` (`MainRouterState_roomMembersAdded`). `RoomSummary.historyVisibility` is the effective one: Full for every Public room (`databaseGetRoomHistoryVisibility`).
- Member actions are one `DatabaseRoomMemberActionRequest` (`Add`, `Remove`, `Leave`, `Fetch`; pending `RoomMemberAction`) whose statement checks the requester (ManageRoomMembers through the shared permission subquery since protocol 23, member), the room's mode and the target and makes the change, returning `DatabaseRoomMemberOutcome` and the members after it: add needs ManageRoomMembers or (Member invite) a member and refuses Public rooms; remove needs ManageRoomMembers in every mode; leave needs membership of a non-public room; fetch needs membership or ManageRoomMembers. A missing room is `UnknownRoom` only to managers and `NotMember` to everyone else. The outcome is still called `AdminRequired`. A removal or leave also deletes the account's `room_read_markers` row, so a re-added member starts over. Refusals are `ServerProtocolError` sentences (`MainRouterState_roomMemberRefusalMessage`). On a change the router evicts the account from the room's voice (removal, leave), notes it in the voice member cache (add), and sends `ServerRoomMembershipChanged{roomId, joined, userId}` to every session of the account, of the members after the change, and of the requester (`MainRouterState_sendRoomMembershipChange`). Do not move a rule into the router.
- `DATABASE_GET_ROOM_HISTORY_SQL` serves a From join member of a non-public room only messages created after their `room_members.joined_at` (the cut the unread count uses), starting its scan at the first such message ID found through `chat_messages_by_room_id_and_created_at`. `ClientAdminListRooms` is `DatabaseAdminRoomListRequest` (`DATABASE_ADMIN_LIST_ROOMS_SQL`: every room with the requester's membership and its member count, refused in the same statement to accounts holding neither ManageRooms nor ManageRoomMembers, `DatabaseAdminRoomListResult.allowed`). Protocol 31 (#73): `MainRouterState_sendAdminRoomChanged` sends `ServerAdminRoomChanged{roomId, change}` to every session whose `RouterPeerSession.permissions` hold ManageRooms or ManageRoomMembers (plus `alsoUserIDs`): after create, edit and delete (`server/main.odin`), from `MainRouterState_sendRoomMembershipChange` and `MainRouterState_roomMembersAdded` (every membership fan-out), and after a grant change that changed something, which also goes to the room's members. Keep a new room or membership change on those paths, or call it.
- Room create/edit/delete need ManageRooms (protocol 23), checked inside `DATABASE_CREATE_ROOM_SQL`, `DATABASE_EDIT_ROOM_SQL` (`$7` the requester) and `DATABASE_DELETE_ROOM_SQL` themselves; without it nothing changes and `DatabaseRoomMutationResult.notPermitted` becomes `ROOM_MANAGEMENT_REQUIRED_MESSAGE` ("Room management permission required"). The delete statement also returns the room's members before the cascade (`memberUserIDs`), whom the router tells. There is no separate admin check round trip any more (`DatabaseUserServerAdminRequest` is gone); membership changes check their permission inside their own statement (above). Creating a Public room notifies every authenticated session with `ServerRoomMembershipChanged`, an invite room only the creator's sessions when the creator joined (`ServerRoomMutationPayload.isMember` tells the creator); membership and deletion changes must notify affected users so their clients refresh the authoritative room list. `MainRouterState_hasValidRoomMetadata` uses `common.ROOM_NAME_MAX_BYTES`/`ROOM_DESCRIPTION_MAX_BYTES`, which the client validates against too.
- `ServerAuthSuccess.isAdmin` (protocol 8) tells the client whether to offer room management. It comes from the identity statement itself (`DATABASE_RESOLVE_USER_IDENTITY_SQL` returns a fourth column, `DatabaseUserIdentityResult.isAdmin`) and `MainRouterState_completeAuthentication` passes it, in the `ServerAuthSuccessPayload`, to the `MainRouterAuthSuccessSender`. It is a UI hint; a role changed from a client follows as `ServerAccountUpdated` (below), one changed in the database shows on the next connection (D8). Never use it instead of the per-request admin check. Protocol 23: the identity statement's ninth column is the account's effective permission mask, sent as `ServerAuthSuccess.permissions` (`MainRouterState_completeAuthentication`'s `permissions`).
- Admin actions on accounts (protocol 14, `router_admin.odin`, `database_admin.odin`): `ClientAdminSetRole`, `ClientAdminRenameUser`, `ClientAdminKickUser`, and `ClientAdminBanUser` are checked for shape in the router (user ID, nickname length `common.NICKNAME_MIN_BYTES..NICKNAME_MAX_BYTES` or empty, reasons up to `common.ADMIN_REASON_MAX_BYTES`; anything else is "Invalid admin request") and then become one `DatabaseAdminUserRequest` (pending `AdminUserAction`). Its statement checks the requester's admin role, the guards, and makes the change in one statement, and reports `DatabaseAdminOutcome`: `NotAdmin`, `UnknownUser`, `LastAdmin` (a revoke of the sole admin, checked before `SelfTarget` so that case says why), `SelfTarget` (kick, ban, or revoke of yourself; renaming yourself is allowed), `AdminTarget` (kick or ban of an admin), `BannedTarget` (granting the role to a banned account), `NicknameTaken`, or `Applied` with whether a row `changed`. Do not move a guard into the router or a second query: a role change between a check and the action would slip through. Refusals are `ServerProtocolError` with a sentence (`MainRouterState_adminRefusalMessage`) and the session stays up. On `Applied` the requester gets `ServerAdminActionResult`; a role or rename that changed something sends `ServerUserUpdated` (the full `UserSummary`, `isOnline` from the sessions) to every authenticated session and `ServerAccountUpdated` to every session of the target; a rename that changed the name also renames the target's sessions (`MainRouterState_renameUserSessions`), sends `ServerUserPresence` with the new name while it is online, and refreshes its voice lists (`MainRouterState_voiceRefreshUserRooms`). Kick and ban call `MainRouterState_endUserSessions`: every authenticated session of the target gets `ServerSessionEnded{kind, reason}`, leaves voice, drops its pending requests, is de-authenticated and disconnected, and the user is announced offline once; a ban that changed something then sends `ServerUserUpdated`. Any new path that ends sessions must do the same. A ban (protocol 32, #72; `banned` true, also of an account already banned) is the one admin action that is a transaction: `databaseExecuteAdminBan` runs `DATABASE_ADMIN_BAN_SQL` inside `databaseRoomLogBegin` (a savepoint in the SQL tests), and only when it applied does `databaseRoomLogRemoveBanned` (`database_room_log.odin`) run `databaseServerRoomLogRemoveInTransaction` for every encrypted room `DATABASE_ROOM_LOG_BANNED_ROOMS_SQL` lists the account in (by room ID), each under `SAVEPOINT haychat_ban_room`, with `DATABASE_ROOM_LOG_LOCK_NOWAIT_SQL` so a room another connection holds is not waited for (SQLSTATE 55P03). An applied, changed removal becomes a `DatabaseBanRoomRemoval` in `DatabaseAdminUserResult.banRemovals`; a damaged log, a held lock or any other refusal rolls back to the savepoint and goes to `failedRoomIDs` (a room deleted meanwhile, or whose verified log does not name the account, to neither); only a database error rolls the whole ban back. The router sends `ServerAdminActionResult.failedRoomIds`, then for each removal after `MainRouterState_endUserSessions` `MainRouterState_voiceEvictUser`, `MainRouterState_sendRoomLogEntries` and `MainRouterState_sendRoomMembershipChange`, as for a `ClientRemoveRoomMember`. Since protocol 33 (#195) `DATABASE_ROOM_LOG_BANNED_ROOMS_SQL` also lists the encrypted rooms `room_log_managers` names the account in, and the ban passes `managerEntry` to `databaseServerRoomLogRemoveInTransaction`: after the Remove (only when the verified log names it a member) it writes the server's unsigned `RemoveManager` (`databaseRoomLogWriteServerEntry`) when the log names it a manager, also the last one, in the same savepoint. `DatabaseBanRoomRemoval` carries either entry or both (`logEntry`/`logVersion`, `managerLogEntry`/`managerLogVersion`; nil when not a member, or not a manager); the router sends a room's entries in one `ServerRoomLog` (Remove first), evicts from voice and sends `ServerRoomMembershipChanged` only for a Remove, and the ban's message counts the manager sets and the rooms left with no manager (`MainRouterState_adminSuccessMessage`). The server never promotes anyone. An unban is still the one statement and adds the account back to nothing.
- Room types (protocol 14, migration 3): `rooms.room_type` is `common.RoomType` as a number, only Chat (1), Voice (2) and ChatAndVoice (3) (`common.roomTypeIsSupported`; the router refuses anything else as invalid metadata). Every `RoomSummary` carries it. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` checks it in the same statement as membership and the insert (`DatabasePostRoomChatMessageResult.chatDisabled`, refused with `CHAT_DISABLED_MESSAGE` "Chat is disabled in this room"), and `DATABASE_LIST_ROOM_MEMBERS_SQL` returns it with the members (`roomFound`, `roomType`) for the voice join check. An edit to a type without voice calls `MainRouterState_voiceDisableRoom` before `ServerEditRoom` goes out.
- Chat messages carry `senderNickname`, joined from `users` by the post and history statements. It is an owned string like the other `StoredChatMessage` fields; free it in `IPC__stored_chat_message_deinit`.
- Signed room messages (protocol 22, #90, migration 10): every plaintext `ClientChatMessage` carries a set `clientMessageId` and `signature`; `MainRouterState_handleClientChatMessage` checks it with `common.verifyPlaintextRoomMessage` against the **session's** identity key (this server's key, the room, the session's account, the ID and the content) before the database sees it, and refuses anything else with `common.ROOM_MESSAGE_SIGNATURE_INVALID_MESSAGE`. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` stores the ID and signature (`$5`, `$9`); the unique index on `(sender_user_id, client_message_id)` refuses a reused ID (`ROOM_MESSAGE_DUPLICATE_MESSAGE`). The live echo (`ServerChatMessage`) and history pages carry both, so every client checks the sender's signature against its own pin. Database tests store messages with `databaseTestPlainRoomPost`, `databaseSQLTestPost` and `DATABASE_TEST_PLAIN_COLUMNS_SQL` (a placeholder signature: the database only stores it); router tests sign with `routerTestSignedChat` and the session key `routerCompleteHandshake` hands back (`RouterVoiceTestClient.identityKey`).
- Encrypted direct messages (protocol 17, migration 6): `ClientSealedDirectMessage` is checked in the router for shape (recipient, a non-zero `clientMessageId`, 1..`common.SEALED_ENVELOPE_MAX_BYTES` bytes, `decodeSealedEnvelope` with kind DirectMessage and two wraps; else `common.SEALED_DIRECT_MESSAGE_INVALID_MESSAGE`) and becomes a `DatabasePostDirectMessageRequest` with the envelope (owned), the server's identity key and the **session's** identity key. The database worker reads the recipient's `users.public_key` (`DATABASE_DIRECT_MESSAGE_RECIPIENT_KEY_SQL`), runs `databaseCheckSealedDirectMessage` (pure: `verifyDirectMessageEnvelope` over every AAD field), and inserts with `DATABASE_POST_DIRECT_MESSAGE_SQL`, whose recipient CTE requires that same key, so a key changed in between stores nothing. The fallback `ClientDirectMessage` must carry a non-zero `clientMessageId` and a `signature` that `verifyPlaintextDirectMessage` accepts for the session's identity key (else `common.DIRECT_MESSAGE_SIGNATURE_INVALID_MESSAGE`); unsigned messages, which only pre-17 clients sent, are refused. `direct_messages_sender_client_message_id` makes `(sender_user_id, client_message_id)` unique and the insert's `ON CONFLICT ... DO NOTHING` reports `DirectMessagePostOutcome.Duplicate` (`common.DIRECT_MESSAGE_DUPLICATE_MESSAGE`). Stored envelopes go out as `ServerSealedDirectMessage`, plaintext as `ServerDirectMessage` with its ID and signature; history and the conversation list return the three protocol 17 columns as hex. Both handlers decode with `temp_allocator = context.allocator` (fixed-size byte fields). `database_encrypted_direct_messages_test.odin` and `router_sealed_direct_messages_test.odin` test it.
- Direct messages (`router_direct_messages.odin`, `database_direct_messages.odin`) are between two accounts on this server, never to oneself. The router refuses a self-addressed message before the database, and `DATABASE_POST_DIRECT_MESSAGE_SQL` checks that the recipient exists and is not the sender in the same statement as the insert. Persist before fanout, then send `ServerDirectMessage` to every authenticated session of the sender and of the recipient and to no one else; the sending session gets the echo too, which is how clients learn the stored ID and timestamp. `StoredDirectMessage` owns its two nicknames, timestamp, content and envelope; free them in `IPC__stored_direct_message_deinit`.
- Presence is derived, not stored: a user is online while one of their sessions in `peerSessions` is authenticated. Send `ServerUserPresence` on three triggers:
  - zero to one authenticated sessions: on auth success, to every other authenticated session. `MainRouterState_completeAuthentication` marks the session authenticated only after `ServerAuthSuccess` is sent, so a failed send announces nothing.
  - a login that renames the account, whatever the count: also from `MainRouterState_completeAuthentication`, with the new nickname, to every other authenticated session (the user's other sessions included). An admin rename of an online account sends it too (`router_admin.odin`).
  - one to zero: `MainRouterState_handlePeerDisconnected`, `MainRouterState_protocolViolation`, which de-authenticates a session before its disconnect event arrives, or a kick or ban (`MainRouterState_endUserSessions`, once for all the account's sessions).
  Any new path that ends or de-authenticates a session must call `MainRouterState_noteSessionEnded`. `ServerUserList` online flags come from the same sessions, never from the database.
- Router tests that authenticate two different user IDs must consume the presence notice the second one causes: client transports accept only the next sequence number, so a skipped packet breaks every later open for that session.
- `server/database_direct_messages_test.odin` runs the direct message SQL against a real PostgreSQL when `HAYCHAT_DATABASE_SQL_TEST=1`; it writes and then deletes its own accounts, so point it only at a throwaway database. `server/database_default_room_test.odin` runs the default room statement under the same flag, inside a schema of its own that it rolls back, starting from a protocol 7 `rooms` table that `databaseApplyMigrations` adopts. `server/database_migrations_test.odin` runs the migration runner (see Schema Migrations). `server/database_read_markers_test.odin` runs the unread rules and mark-read against a migrated schema of its own. `server/database_user_identity_test.odin` runs the identity statement (new account, unchanged, rename to a free name, rename to a taken name, auto-join only for new accounts, and the admin flag for an admin, a renamed admin, and an account with another role) the same way. `server/database_admin_test.odin` runs the protocol 14 statements the same way: the identity statement with a locked name and a ban (also a banned keyless account claimed by a key), every admin action with every guard (the last admin, self, admin and banned targets, a taken name, no-op changes), room types in the create, edit, list, member list, and chat post statements, and migration 3 from a version 2 database with rows. `./dev.sh live --sql` (and `--all`) runs them; add new database-backed tests to `SQL_TESTS` in `dev/live-proof.sh`. Open every SQL test connection through `databaseSQLTestOpen(t)` (or `databaseAdminTestOpen`/`databaseMigrationTestOpen`, which use it) and never close it yourself: it registers a `testing.cleanup` that rolls back, drops the test's schema and closes the connection. A `defer` does not run when an assertion fails (the runner stops the thread without unwinding it), and a connection left open inside the transaction holding the migration lock made every later test that migrates wait forever (#80). `dev/live-proof.sh` checks this by running the SQL test binary a second time with `HAYCHAT_DATABASE_SQL_TEST_FAIL=1`, which makes `testAbandonedSQLTestReleasesItsConnectionAgainstPostgreSQL` (it sorts first) fail while it holds that lock: the run must exit non-zero within 2 minutes, name only that test, and pass every other SQL test.
- Read state (migration 2, protocol 11; `database_read_markers.odin`, `router_read_markers.odin`): `room_read_markers` and `direct_read_markers` hold, per account, the newest message ID read in a room or a direct conversation. The unread rules, used by `DATABASE_LIST_ROOMS_FOR_USER_SQL` and `DATABASE_LIST_DIRECT_CONVERSATIONS_SQL`:
  - Rooms: messages from other users with an ID above the marker. With no marker row, messages from others created after the user's `room_members.joined_at` (index `chat_messages_by_room_id_and_created_at`), so a new account or a new room starts with nothing unread.
  - Direct conversations: messages from the peer with an ID above the marker; with no row, every message from the peer.
  - Counts stop at `common.UNREAD_COUNT_CAP` (100), which the client shows as "99+". Each count is a `LIMIT`ed index range scan, so keep new list columns from turning it into a full scan.
  - `ClientMarkRead` is one statement per kind: the access check (membership; for a DM an existing peer who is not the requester), the clamp to the conversation's newest message, the forward-only upsert (`GREATEST`, and a `WHERE` that makes a no-op return no row), and the count after it. The router sends `ServerReadMarker` to every authenticated session of the account, the asking one included, and nothing for a no-op. A refusal is a `ServerProtocolError` (`Not a room member`, `Unknown user`), never `MainRouterState_protocolViolation`: a room can vanish between the client's last list and its mark-read.
  - Only `ServerListRooms` fills `RoomSummary.lastReadMessageId`/`unreadCount`; other payloads that embed `RoomSummary` carry zeros.
- Account encryption keys (protocol 16, `router_encryption_keys.odin`, `database_encryption_keys.odin`): `ClientPublishEncryptionKey` is verified in the router with `common.verifyEncryptionKeyBundle` on a bundle whose identity key is the **session's** (`RouterPeerSession.clientIdentityPublicKey`), so an account can only store a key it signed; anything else, and a `createdAt` above `max(i64)`, is `ServerProtocolError` `common.ENCRYPTION_KEY_INVALID_MESSAGE` before the database. `DATABASE_PUBLISH_ENCRYPTION_KEY_SQL` is one upsert that changes nothing (and returns no row) for an identical bundle; a returned row (first publish or replacement, `replaced`) is sent as `ServerUserKeyChanged` with the account's identity key from `users.public_key` to every authenticated session. `ClientFetchUserKeys` is checked with `common.userKeysFetchIsValid` (1..64 positive, distinct IDs; else `common.USER_KEYS_INVALID_REQUEST_MESSAGE`), and `DATABASE_FETCH_USER_KEYS_SQL` answers in request order, listing accounts without a key, without a bundle, or unknown in `missingUserIds`; only the requester gets `ServerUserKeys`. Both handlers decode with `temp_allocator = context.allocator`, because CBOR decodes fixed-size byte strings through the temporary allocator, which the router never frees; do the same for any new payload with fixed-size byte fields. `DATABASE_LIST_USERS_SQL` and every admin statement return `encode(public_key, 'hex')` and whether a bundle exists (only for an account with an identity key), so `UserSummary.identityPublicKey`/`hasEncryptionKey` are right in `ServerUserList` and `ServerUserUpdated`; presence carries neither.
- Encrypted rooms (protocol 18, migration 7; `database_room_log.odin`, `router_room_log.odin`): `ClientCreateRoom{encrypted}` must be an invite mode (the router refuses Public with `common.ENCRYPTED_ROOM_PUBLIC_MESSAGE`); `DATABASE_CREATE_ROOM_SQL` stores `encrypted` and adds **no** members for an encrypted room. `ClientAppendRoomLog` becomes a `DatabaseAppendRoomLogRequest` (entry owned, the server's identity key, the session's account); the worker runs one transaction (`databaseRoomLogBegin`, a savepoint when the SQL tests already hold a transaction): lock the room row `FOR UPDATE`, replay every stored entry with `common.replayRoomLog` (no pins; a log that does not replay or does not end at `rooms.log_version` is `Damaged` and refuses everything), validate the entry with `RoomLogState_validate` whose `lookupPin` returns each named account's `users.public_key` (an account without one mismatches), then `roomLogServerAllows`: the actor is the requester; Create needs ManageRooms (protocol 23; `RoomLogLockedRoomView.actorManagesRooms`), the room's creator and the room's own settings; Add needs ManageRoomMembers (`actorManagesMembers`) or (Member invite) membership in `room_members`; SetAccess needs ManageRooms. The server-written Remove needs ManageRoomMembers, and `DATABASE_FETCH_ROOM_LOG_SQL` serves members, managers and holders of either permission. Then insert into `room_log_entries`, move `rooms.log_version` (and `access`), apply to `room_members` (deleting the read marker on a removal, like protocol 15) and `room_log_managers`, commit. The primary key `(room_id, version)` and the lock serialise appends; a version or prevHash that does not follow is `Conflict`. Outcomes become `ServerProtocolError` sentences (`MainRouterState_roomLogRefusalMessage`; `Invalid` adds the `RoomLogError`). An applied entry goes out as `ServerRoomLog` (`MainRouterState_sendRoomLogEntry`) to the sessions of the members and managers after it, its target, and the requester, plus `ServerRoomMembershipChanged` when `room_members` changed. `ClientRemoveRoomMember` on an encrypted room is routed by `databaseExecuteRoomMemberAction` to `databaseExecuteServerRoomLogRemove`, which writes the unsigned Remove (actor 0) itself and returns it in `DatabaseRoomMemberActionResult.logEntry`; Add and Leave are `EncryptedRoom` (`common.ROOM_LOG_REQUIRED_MESSAGE`). `ClientFetchRoomLog` (`DATABASE_FETCH_ROOM_LOG_SQL`) serves members, `room_log_managers` and admins, `ROOM_LOG_FETCH_MAX_ENTRIES` per page with `hasMore`. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` refuses plaintext chat in an encrypted room (`encryptedRoom`, `common.ENCRYPTED_ROOM_CHAT_MESSAGE`; sealed messages since protocol 19, below), the voice join check reports `DatabaseRoomMemberListResult.encrypted` and `logVersion` (protocol 18 to 20 refused voice there; protocol 21 encrypts it, Voice Rooms below), and `DATABASE_EDIT_ROOM_SQL` refuses an edit that changes the flag or an encrypted room's access (`RoomEditRefusal`). A ban removes the account from every encrypted room's log (protocol 32, Admin actions above) and, since protocol 33, from its managers with the server's unsigned `RemoveManager` (valid in `common` only for a target that is no longer a member, never refused by `LastManager`; a room may be left with no manager, after which `roomLogServerAllows` and the log refuse every Add of an Admin invite room, AddManager and SetAccess, while sealed posts and the server's Remove still work). A client's own unsigned entry is refused by `roomLogServerAllows` (its actor is not the requester). `database_room_log_test.odin` (SQL, plus the pure rules) and `router_room_log_test.odin` test it.
- Member log repair (protocol 34, #196; `database_room_log_repair.odin`, `router_room_log_repair.odin`, `common/room_log_repair.odin`): a replay that finds a damaged log (`databaseRoomLogReplay`, so every append, server removal and ban of such a room) calls `databaseRoomLogReportDamage`, which writes one `[RoomLog] Room N's member log is damaged: ...` line naming the version to truncate to (every refused append writes it again). `ClientAdminRoomLogStatus{roomId}` and `ClientAdminTruncateRoomLog{roomId, toVersion}` become one `DatabaseRoomLogRepairRequest` (`Status`, `Truncate`; pending `.RoomLogRepair`, which like `.MessageChange` survives its peer's disconnect and answers only the session that asked; `adminAction` `TruncateRoomLog` marks a truncation). `DATABASE_ROOM_LOG_REPAIR_ROOMS_SQL` checks the admin (`DATABASE_ACTOR_IS_ADMIN_SQL`, always one row) and lists the room or every encrypted room; `databaseRoomLogRepairInspect` replays the stored rows with the room locked (`RoomLogStatus`: `goodVersion` the last version that replays, `failingVersion` and `error` the first that does not, `VersionNotNext` for a gap, `Truncated` for a row that is not an entry; `common.roomLogStatusIsDamaged`), a status in a transaction of its own per room that it rolls back, up to `ROOM_LOG_STATUS_ROOMS_MAX` damaged rooms for `roomId` 0. A truncation is one transaction (`databaseRoomLogBegin`): the rooms statement, `DATABASE_ROOM_LOG_REPAIR_LOCK_SQL` (`FOR UPDATE`, the admin check again), the replay kept as state, then `NotDamaged` (a healthy log is never rolled back), `NothingToKeep` (`goodVersion` 0: delete the room) and `WrongVersion` (`toVersion` must be `goodVersion`, the compare-and-swap); then `DATABASE_ROOM_LOG_TRUNCATE_ENTRIES_SQL`, `_ENVELOPES_SQL` (epochs after it), `_EDITS_SQL` (sealed edits of kept messages whose sealed epoch, bytes 1..8, is later; `edit_count` and `edited_at` follow), `_MESSAGES_SQL` (sealed messages and tombstones of later epochs; edits cascade, attachments lose their message for the sweeper), `_MEMBERS_SQL` (`room_members` becomes the replayed members, a removed member's read marker deleted; returns `a`/`r` rows), `DATABASE_ROOM_LOG_SET_MANAGERS_SQL` and `DATABASE_ROOM_LOG_HEAD_SQL` (head and access). `DatabaseRoomLogRepairResult` carries the status, the members and managers after, the added and removed members and `formerUserIDs` (members and managers before). The router answers `ServerAdminActionResult{TruncateRoomLog, roomId}`, logs the counts, and `MainRouterState_roomLogTruncated` ends the room's voice (`MainRouterState_voiceDisableRoom`, `VOICE_LEFT_ROOM_LOG_REPAIRED`), sets `roomLogVersions[roomId]` back (`MainRouterState_voiceLogAdvanced` only moves forward), sends `ServerRoomLog{afterVersion = headVersion = toVersion, no entries}` to the sessions of the former, current and managing accounts and the requester, and `MainRouterState_sendRoomMembershipChange` per added and removed member (or `ServerAdminRoomChanged{Members}` alone). A requester that is gone is `ROUTER_NO_PEER_ID`. `deploy/sql/truncate-room-log.sql` (one DO block reading `haychat.room_id` and `haychat.to_version`, run by `testRoomLogTruncateHelperAgainstPostgreSQL` through `#load`, so `deploy/Containerfile` copies it into the build stage) does the same with the state decoded from the entries' fixed offsets; it has no change notification, so the server must be restarted after it. `testRoomLogRepairAgainstPostgreSQL` and `router_room_log_repair_test.odin` test it; `dev/e2ee-proof.sh` step 20 proves it live.

## Schema Migrations

- `server/database_migrations.odin` holds `DATABASE_MIGRATIONS`, an ordered, append-only list of `{version, name, sql}` starting at 1 with no gaps. Migration 1 (`baseline`) is the v0.1.0-rc1 schema, statement for statement; `testDatabaseBaselineMigrationIsTheRC1Schema` pins it to a frozen copy. Merged migrations are never edited, reordered, or removed.
- At startup `databaseMigrateSchema` runs, in one transaction under `pg_advisory_xact_lock(DATABASE_MIGRATION_LOCK_KEY)`: it creates `schema_migrations` if needed, then applies every migration to an empty schema; adopts HayChat tables that have no recorded version (runs migration 1, which is idempotent, checks them against `DATABASE_BASELINE_VALIDATION_SQL`, and records version 1); applies the missing migrations to an older version; and refuses a newer version. `DATABASE_SCHEMA_VALIDATION_SQL` then checks the newest schema. Any failure rolls back and becomes `DatabaseStartupFailed`, a `[Startup]` line, and exit status 1. Nothing drops tables; do not add a path that does.
- Every migration runs inside that transaction, so statements that cannot run in a transaction block (`CREATE INDEX CONCURRENTLY`, `VACUUM`, `ALTER SYSTEM`, ...) are not supported.
- Migration 2 (`read markers`) adds the read-state tables, their cascade indexes, and `chat_messages_by_room_id_and_created_at`, and backfills markers at the newest message for every existing room member and both sides of every existing conversation, so an upgraded database starts with nothing unread.
- Migration 3 (`admin`, protocol 14) adds `users.nickname_locked BOOLEAN NOT NULL DEFAULT false`, `users.banned_at TIMESTAMPTZ NULL`, `users.ban_reason VARCHAR(256) NOT NULL DEFAULT ''`, and `rooms.room_type SMALLINT NOT NULL DEFAULT 3` with `rooms_room_type_check` (1, 2, 3), so every existing account is unlocked and unbanned and every existing room is text and voice. `DATABASE_ADMIN_CHECKS` validates them.

## Transport Channels

- `common.TransportState` has six halves with separate keys and counters: `controlSend`, `controlReceive` (strict counter), `voiceSend`, `voiceReceive` (64-packet replay window), and (protocol 26, key schedule `"haychat transport v3"`) `fileSend` and `fileReceive` (strict counter). `NetworkChannel.Chat`, `.Voice` and `.FileTransfer` are the same numbers as `common.TransportChannel.Control`, `.Voice` and `.File` (asserted in `ipc.odin`), and the ENet host allocates channels 0 to 5 (`NETWORK_CHANNEL_COUNT`).
- The file halves never stay in `RouterPeerSession.transport`: `MainRouterState_completeAuthentication` moves them with `common.TransportState_takeFileState` into a heap `AttachmentChannel` (`MainRouterState.attachments.channels`, `MainRouterState_attachmentsOpenChannel`), wiped when the session ends (`MainRouterState_attachmentsEndSession`). Router code copies sessions and writes the copy back (`MainRouterState_setPeerSession`); a file send counter in that copy would be rewound and a nonce reused, so only the `AttachmentChannel` seals and opens channel 5 packets (`sealFilePacket`, `openFilePacket`).
- Who may touch which half: the router (main thread) owns each `RouterPeerSession.transport`, runs the handshake, and alone uses the control halves (`sealPacketForSession`, `openPacketForSession`). The voice halves belong to the network thread: `MainRouterState_completeAuthentication` takes them out with `common.TransportState_takeVoiceState` (which zeroes them in the session before it is stored) right after `ServerAuthSuccess` and sends them in a `NetworkVoiceSessionOpen`; from then on only the network thread's `VoiceRelay` seals or opens that peer's voice datagrams (`sealVoiceDatagram`, `openVoiceDatagram`) and the router never touches voice crypto. Never keep using two copies of one `ChannelSendState`: that reuses voice nonces. The relay's copy is the only live one.
- The router handles `.Chat` and (protocol 26) `.FileTransfer` data; a file packet that does not open or decode is a protocol violation like a control packet. Anything on another channel is dropped without a protocol violation, because ENet does not authenticate datagrams; a voice datagram that reaches the router anyway is counted in `MainRouterState.unexpectedVoiceDatagrams`. A bad voice datagram is counted by the relay, never a reason to disconnect.
- Wipe rules for voice keys: `RouterPeerSession_deinit` wipes the transport with `common.TransportState_deinit`. `IPC__message_deinit` wipes a `NetworkVoiceSessionOpen` in place (`ChannelSendState_wipe`, `VoiceReceiveState_wipe`), so a session open that is dropped, unsent, or left in a queue at shutdown never leaves keys behind; `networkDrainIPC` calls it after the handler has moved the keys out. The IPC ring zeroes a slot when it pops it and a buffer before it frees it. The relay heap-allocates each peer, so a map rehash never copies keys, and wipes the peer when it disconnects, on `NetworkVoiceReset`, and when the network loop exits.

## Attachments

- Protocol 26, migration 14, attachments plan F1 (`router_attachments.odin`, `database_attachments.odin`, `storage.odin`). The router orchestrates every step: the database worker decides (one statement per step, `DatabaseAttachmentRequest` with a `DatabaseAttachmentAction`, pending `.Attachment`), the storage worker writes and reads, and the router seals and opens channel 5 and keeps each transfer's window and the per-session pace. `.Attachment` pending requests survive their peer's disconnect (like `.Register`): every answer is checked against the session ID it was made for (`PendingDBRequest.sessionID`, `attachmentSession` over `MainRouterState_askingSession`) before anyone is told, because ENet reuses peer IDs.
- The storage worker is a third supervised service thread (`ProcessType.Storage`, `IPC_Endpoint_Kind.Storage`, its own IPC ring, restarted like the others; `MainRouterState_prepareForProcessStop(.Storage)` ends every transfer). It does all attachment file I/O and the running SHA-256 and never talks to PostgreSQL. Commands are `StorageCommand{requestId, StorageRequest}` (open, write, finish, close, read, delete blobs, scan, delete orphans; requestId 0 takes no answer) and answers `StorageResponse{requestId, StorageResult}`; `StorageRequest_deinit`/`StorageResult_deinit` are exhaustive. `StorageWorker_handle` is the whole state machine and needs no thread (`storage_test.odin`, with `freeBytes` and `now` replaceable). Layout: `incoming/<hex>.part` while uploading, then `blobs/<2 hex>/<hex>` after fsync, rename and a directory fsync; files 0600, directories 0700; names come only from the server's random blob IDs. A read of a file that does not exist answers `StorageReadData.missing` (ENOENT, #132: a row whose file is gone, as after a restore without the blob directory), which the router refuses with `ATTACHMENT_NOT_FOUND_MESSAGE` (clients show "Attachment unavailable") and logs; every other read failure is `ATTACHMENT_STORAGE_ERROR_MESSAGE` and marks nothing. The server is not a backup (#132 follow-up, `router_attachment_missing.odin`): a missing read then becomes `DatabaseAttachmentAction.MarkMissing` (userId 0, reason `ATTACHMENT_MISSING_REMOVAL_REASON` "File missing from storage"), whose `DATABASE_ATTACHMENT_MARK_MISSING_SQL` shares `DATABASE_ATTACHMENT_TOMBSTONE_BODY_SQL` with `DATABASE_ATTACHMENT_REMOVE_SQL` (its actor CTE is `$1 = 0` with a NULL remover, so `removed_by_user_id` is NULL in both tables) and applies only to a Ready or Bound row; `MainRouterState_attachmentMarkMissingResult` ends the blob's downloads (`ATTACHMENT_REMOVED_MESSAGE`) and sends `ServerAttachmentRemoved` to the readers (`MainRouterState_attachmentSendRemoved`, shared with the admin removal), with no `StorageDeleteBlobs`. Guards (`AttachmentMissingGuard`, `attachmentMissingDecide`): the storage worker sets `StorageReadData.blobDirectoryIntact` only when `blobs/` is readable with an entry and the blob's shard directory exists (shard directories are never deleted), else the router logs a warning and marks nothing; at most `ATTACHMENT_MISSING_MARKS_PER_WINDOW` (10) marks per `ATTACHMENT_MISSING_MARK_WINDOW` (an hour, in memory), past which it logs once and marks nothing; a blob with a mark in flight (`marking`) is not marked twice. An unmarked row stays as it was and the next download reads the disk again. Startup (`attachmentDirectoryPreflightError`) refuses a blob directory that is `HAYCHAT_FILE_STORAGE_PATH` or contains the identity file, and creates `incoming/` and `blobs/`.
- `DATABASE_ATTACHMENT_BEGIN_SQL` is the one begin statement: membership of a room with chat, `DATABASE_ATTACHMENT_ROOM_PERMISSIONS_REQUIRED_SQL` (Send | AttachFiles since protocol 27; the result reports `SendDenied` and `AttachDenied` apart) through the shared room permission subquery, the room's encryption flag, or for a direct message the recipient and `DATABASE_USERS_MAY_MEET_*` like a direct message send; then size, quota (owner's rows not Removed), hourly rate (owner's rows created in the last hour, tombstones included), capacity, and the insert that reserves the declared size. The storage worker then checks the free-disk reserve, and a refusal deletes the unwritten row (`DeleteNew`). An upload chunk is acknowledged only after the storage worker wrote it; a cancel or a hash mismatch makes the row a tombstone (`Abandon`, state Removed). The download check (`DATABASE_ATTACHMENT_DOWNLOAD_CHECK_SQL`, protocol 27, D10) allows a Bound blob of a room message to a member who may read the message (the From join cut `DATABASE_HISTORY_SINCE_*`, shared with `DATABASE_GET_ROOM_HISTORY_SQL`), a Bound blob of a direct message to its sender or recipient, and the owner's Ready blob; no admin bypass, never a Removed blob.
- Binding (protocol 27, migration 15): `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` (plaintext and sealed) and `DATABASE_POST_DIRECT_MESSAGE_SQL` (plaintext and sealed) build `bind_in` from five comma-separated text parameters (`databaseAttachmentBindParams`: blob IDs, sizes, and for plaintext hashes, names and media types as hex), lock the rows (`bind_rows`), check them (`bind_ok`: the sender's, Ready, unbound, this room or this recipient, `encrypted` equal to whether the message is sealed, size and plaintext hash as listed, no duplicates), insert the message with `attachment_count` only when they qualify, and bind them (`bound`: state 2, the message link, `bound_at`, `position`, `name`, `media_type`) in the same statement, from the shared `DATABASE_ATTACHMENT_BIND_*` pieces. A room message with files needs AttachFiles (`may_attach`). Refusals: `DatabasePostRoomChatMessageResult.attachDenied` (`ATTACHMENT_SEND_NOT_PERMITTED_MESSAGE`), `.attachmentsRefused` and `DirectMessagePostOutcome.AttachmentsRefused` (`ATTACHMENT_BIND_REFUSED_MESSAGE`). The router checks the list's shape first (`common.attachmentRefsAreValid`, `ATTACHMENT_REFS_INVALID_MESSAGE`) and a plaintext message's v2 signature over it. History, conversation lists and echoes carry the list (`DATABASE_MESSAGE_ATTACHMENTS_*`, parsed by `databaseParseAttachmentRefs`; a sealed message's blobs carry only ID, size and `removed`). A removal (F3, below) keeps `sha256`, `size`, `name`, `media_type` and the message link, so history reports the file with `removed`. Room deletion turns the links NULL and the sweeper deletes the rows once they are an hour old, then the files (`testAttachmentRoomDeletionSweepsItsFilesAgainstPostgreSQL`; live in `dev/attachment-proof.sh` step 15, which backdates the rows of its own server and restarts it).
- Moderation (protocol 28, F3, `router_attachment_moderation.odin`): admin-only, checked in the statement (`DATABASE_ACTOR_IS_ADMIN_SQL`). `DATABASE_ATTACHMENT_REMOVE_SQL` (`.Remove`) sets state 3, `removed_by_user_id`, `removed_at` on a Ready or Bound blob and nothing else (the v2 signature covers size, hash, name, type, position, and history still lists the file), and returns the owner, the conversation and the readers (room members past `DATABASE_HISTORY_SINCE_*`, a DM's two sides, or the owner of a blob no message holds) in `DatabaseAttachmentResult.removal`; outcomes `NotAdmin` and `NotFound` (unknown, Uploading, Removed). Since protocol 29 (#138) the same statement inserts the `attachment_removals` row (`logged`, with `DatabaseAttachmentRequest.reason`, owned and freed by the IPC deinit), and `applied` needs both the tombstone and the row. The router logs the reason, ends the blob's downloads (`MainRouterState_attachmentCancelDownloads`, `ATTACHMENT_REMOVED_MESSAGE`), sends `StorageDeleteBlobs`, fans `ServerAttachmentRemoved` (with `chatMessageId`/`directMessageId`, protocol 29) out with `MainRouterState_sendMessageToUserID` per reader, and answers `ServerAdminActionResult{RemoveAttachment, userId = owner, blobId}`. `DATABASE_ATTACHMENT_USAGE_SQL` (`.Usage`, top `ATTACHMENT_USAGE_ACCOUNTS_MAX` accounts, state <> 3) then `StorageFreeSpace` (the worker's `freeBytes`; `AttachmentPendingStorage.kind = .FreeSpace` carries the accounts) give `ServerAdminAttachmentUsage`; a stopped storage worker still answers with `freeBytesKnown` false. The download check reports `Removed` for a reader of a bound tombstone. `MainRouterState_attachmentsTombstonePass` (startup and hourly, `nextTombstonePass`) runs `DATABASE_ATTACHMENT_TOMBSTONE_FILES_SQL` (the newest `ATTACHMENT_TOMBSTONE_FILES_BATCH` bound tombstones), cuts off their downloads and deletes their files again (idempotent; `.DeleteTombstones` logs a count), which is how `deploy/sql/remove-attachment.sql`'s files go; the startup scan already treats a Removed row's file as an orphan. The removal log (protocol 29): `ClientAdminListAttachmentRemovals{beforeId}` (a negative cursor is "Invalid admin request") becomes `.Removals` with `ATTACHMENT_REMOVALS_PAGE_MAX`; `DATABASE_ATTACHMENT_REMOVALS_SQL` checks the admin in the statement (always one row: the flag, then the entries or NULLs), asks for one row more to set `hasMore`, and the router answers `ServerAdminAttachmentRemovals{beforeId (PendingDBRequest.attachmentBeforeID), entries, hasMore}` or "Admin permission required". `deploy/sql/remove-attachment.sql` writes a row with a NULL admin and `-v reason`; `testAttachmentRemovalLogAgainstPostgreSQL` runs its DO block as the file has it (`#load`), so keep it one block reading only `haychat.blob` and `haychat.reason`. Tests: `router_attachment_moderation_test.odin`, and in `database_attachments_test.odin` (SQL) `testAttachmentRemovalAgainstPostgreSQL`, `testAttachmentUsageAgainstPostgreSQL`, `testAttachmentSQLRemovalFileIsDeletedByTheHourlyPassAgainstPostgreSQL`, `testAttachmentRemovalLogAgainstPostgreSQL` (one row per removal, none for a refusal, the helper, the row outliving the sweeper) and `testAttachmentRemovalLogListingAgainstPostgreSQL` (admin only, newest first, pages without drops or repeats).
- `ServerAuthSuccess.attachments` (D18): the identity statement's fifteenth column is the account's stored bytes (rows not Removed), and `MainRouterState_attachmentLimits` adds the configured limits.
- The sweeper (`MainRouterState_attachmentsSweep`, at startup and hourly from `MainRouterState_attachmentsTick`, which the main loop calls every pass) deletes the rows `DATABASE_ATTACHMENT_SWEEPABLE_SQL` allows (never one younger than an hour or bound to a message; stale or overdue uploads, unbound Ready blobs past `HAYCHAT_ATTACHMENT_PENDING_HOURS`, Bound blobs whose message is gone, unbound tombstones; never a blob with a live transfer) and then the storage worker deletes their files. Rows go first, a departure from the plan's order: a deleted row can no longer be bound or resumed, and a file a crash leaves behind is removed by the startup scan (`StorageScan`, then `Known`, then `StorageDeleteOrphans`, each deletion logged). The scan is guarded against a wrong restore order (#131, `attachmentOrphanGuard`): it deletes nothing and logs a warning naming `deploy/README.md (Restoring)` when `Known` reports `tableEmpty` (no row at all, `DATABASE_ATTACHMENT_ANY_ROW_SQL`, asked only when no scanned file has a row) or when more than `ATTACHMENT_ORPHAN_PURGE_MAX_SHARE_PERCENT` (10) of the scanned files and more than `ATTACHMENT_ORPHAN_PURGE_FLOOR` (10) are orphans; `HAYCHAT_ATTACHMENT_ALLOW_ORPHAN_PURGE` (`config.attachmentAllowOrphanPurge`, one start) lifts both. Blobs the sweeper deletes while the scan is pending (`scanPending`, `scanSwept`) count as neither files nor orphans, so a startup sweep never trips the guard. Kept orphans count in `orphansKept` (`attachment_orphans_kept`). The hourly sweeper and the tombstone pass are unguarded: they delete only by rows. Tests: `router_attachment_orphan_scan_test.odin` (the router against a storage worker on a temporary directory). Upload progress reaches the database at most every 30 s and when a transfer stops, so an active upload never looks stale.
- File crypto runs on the router thread (plan, Risks); `AttachmentRouterStats.cryptoNanos` and the `attachment_*` pairs of the `[Status]` line measure it. `router_attachments_test.odin` covers the router's checks, the window, acks, session end and a missing file (`router_attachment_moderation_test.odin` its tombstone and guards, `testAttachmentMissingFileMarkAgainstPostgreSQL` the statement); `database_attachments_test.odin` (SQL) every begin refusal, the steps and the sweeper; `dev/attachment-proof.sh` the live round trip with latency (`ATTACHMENT_PROOF_P95_LIMIT_MS`, default 250 ms), and on a second server it starts with small limits (port `HAYCHAT_ATTACHMENT_PROOF_PORT`, 12347, a fresh database it drops) the size, quota, membership, From join and AttachFiles refusals, a killed uploader and the startup sweep and scan. A resume (`ClientAttachmentUploadResume`) is allowed to the owner from any session while the blob is Uploading; only the client limits it to its own process.

## Voice Rooms

- Control plane in the router (`server/voice.odin`, design 4.2): `ClientJoinVoice` checks membership with a `DatabaseRoomMemberListRequest` (pending `JoinVoiceMemberCheck`) and is refused with `ServerVoiceJoinRejected` and a human reason (not authenticated, invalid room, voice disabled, not a room member, voice is disabled in this room for a text-only room (protocol 14, checked after membership), room full, database unavailable, invalid device ID, voice active on another device). A join while in another room sends `ServerVoiceLeft` for the old room and fans it out first; a refused switch keeps the session where it was. `ClientLeaveVoice` and `ClientVoiceState` outside voice are no-ops. `MainRouterState.voiceRooms` and `peerVoiceRoom` are the source of truth.
- One voice session per user (Q2, protocol 13): a voice session belongs to a client session, but an account has at most one, so a participant list names each user once. `MainRouterState_handleJoinVoiceMemberCheckResult` decides before it changes anything, so a refused join leaves every session where it was: a join with `rejoin` (the client's automatic re-join after a reconnect) is refused with "voice is active on another device" while another session of the user is in voice with a different device ID; otherwise every other voice session of the user is removed first with `ServerVoiceLeft{"joined voice on another device"}`, and its room gets its route and participant update unless it is the room being joined, whose single update shows the replacement. A replaced session frees its place, so a takeover in a full room succeeds. `VoiceParticipantState.deviceID` is the parsed `ClientJoinVoicePayload.deviceId`, used only for that comparison and never sent or logged; `handleClientJoinVoice` refuses a missing or malformed one with "invalid voice device ID" without ending the session, before the membership check.
- Every change sends the network thread a full `NetworkVoiceRoute` for the room (never a delta), then `ServerVoiceParticipants` (the full set, nicknames from `peerSessions`) to every authenticated session of every room member. Recipients come from `VoiceRoomState.memberUserIDs`, a cache that each join check replaces, a room list or an added member extends, and a member removal narrows, so leaves, mute changes and disconnects fan out without a database round trip. A room's state is dropped once its participant set is empty and announced.
- After `ServerListRooms` the requester also gets `ServerVoiceParticipants` for each of its rooms with active voice.
- Every `ServerVoiceParticipants` carries `recipientJoined` (protocol 12), set per recipient session by `MainRouterState_voicePeerIsInRoom`: true only when the session receiving it is itself in that room's voice. Participants carry user IDs, not sessions, so this is how a client tells its own join acknowledgement from a list that names its account on another device. Set it on every send path; the shared payload from `MainRouterState_voiceBuildParticipants` leaves it false.
- Sessions leave voice on disconnect (before `MainRouterState_removePeerSession`, skipping the departing session) and on `MainRouterState_protocolViolation`. A member removal evicts that user's sessions and a room deletion every participant, each with `ServerVoiceLeft{reason}` (deletion sends no participant list). Editing a room to text-only (`MainRouterState_voiceDisableRoom`) removes every participant with `ServerVoiceLeft{"voice is disabled in this room"}` and then sends the members the empty list, since the room is still there. A kick or ban leaves voice through `MainRouterState_endUserSessions`. `MainRouterState_prepareForProcessStop(.Network)` clears all voice state and sends `NetworkVoiceReset`, so commands queued before a network restart cannot attach to the new service's reused peer IDs.
- Data plane on the network thread (`server/voice_relay.odin`, design 4.3): `handlePeerData` hands every channel 2 packet to `VoiceRelay_handleDatagram` and never to the router. The relay is a pure state machine with an injected send and clock, so its tests need no ENet; keep it that way. Per datagram it allocates nothing, logs nothing, and counts every drop by reason in `VoiceRelayStats`; no drop disconnects a peer. The loop flushes ENet once per pass when the relay sent anything.
- Voice counters reach the main thread's `[Status]` log line (`server/status.odin`, every `SERVER_STATUS_LOG_INTERVAL` and once at shutdown) through `voiceRelayPublishedStats`, which the network loop updates with atomic stores after each ENet pass in which the counters changed, and `MainRouterState_statusSnapshot` reads with atomic loads. Rooms and participants come from the router. The server has no HTTP or admin port. Per-room counters and a speaking broadcast are deliberately absent.
- Encrypted voice (protocol 21, design `docs/plan/e2ee-voice-design.md` 3.3 and 6): joins of encrypted rooms are accepted like any other; the join check's `DatabaseRoomMemberListResult` carries `encrypted` and `logVersion`, kept on `VoiceRoomState` (`logVersion` also moves on every `ServerRoomLog` fan-out through `MainRouterState_voiceLogAdvanced`, called from `MainRouterState_sendRoomLogEntry`, so the server-written Remove counts too). That fan-out also records the version in `MainRouterState.roomLogVersions` (every room, voice or not; removed when the room is deleted), and a voice room takes the larger of it and the join check's `logVersion`, so an append applied while a room's first join is still in the database is not lost (#77). `ClientVoiceKey` is checked in the router only (`MainRouterState_checkVoiceKey`: a valid `VoiceKey` envelope without a wrap for its sender, signed by the **session's** identity key over every field of `makeVoiceKeyAAD`), accepted only from a session in that room's voice, for an encrypted room, at the room's current log version (`VOICE_KEY_OUT_OF_DATE_MESSAGE` for an older epoch, `VOICE_KEY_INVALID_MESSAGE` otherwise, the session stays). The latest key per participant lives in `VoiceRoomState.keys` (memory only, never the database), goes to every other participant as `ServerVoiceKey`, and is handed to a joiner right after its acknowledging `ServerVoiceParticipants` (`MainRouterState_voiceSendStoredKeys`). `VoiceRoomState_pruneKeys` (in `MainRouterState_voiceRoomChanged` and `MainRouterState_voiceRemoveParticipant`) forgets the keys of sessions that left, were taken over, evicted or disconnected; `VoiceRoomState_dropStaleKeys` those of older epochs. `ClientRequestVoiceKey` is relayed to the speaker's voice session as `ServerVoiceKeyRequest` at most once per requester and speaker every `VOICE_KEY_REQUEST_INTERVAL_SECONDS` (`requestStamps`), anything else dropped silently. `NetworkVoiceRoute.encrypted` marks the room for the relay, which then skips the Opus TOC check, drops a payload that is not a sealed one (`NotSealed`, `voicePayloadLooksSealed`), applies `maxFrameBytes` to the payload minus `VOICE_E2EE_OVERHEAD`, and forwards it unchanged; unencrypted routes are relayed exactly as before.
- Config: `HAYCHAT_VOICE_ENABLED`, `HAYCHAT_VOICE_MAX_PARTICIPANTS`, `HAYCHAT_VOICE_MAX_PACKETS_PER_SECOND`, `HAYCHAT_VOICE_MAX_FRAME_BYTES` (`loadVoiceConfig`, clamped by `validateVoiceConfig`). The router test harness sets the defaults explicitly, because its `ServerConfig` is zeroed.

## Database Change Notifications

- #116 (`database_notifications.odin`, `router_database_changes.odin`): a trigger sends `NOTIFY` with the changed row's ID (migration 18), and `DatabaseChangeListener`, a thread the database worker starts after `DatabaseStartupReady` and stops (joins) before it returns, `LISTEN`s on every `DatabaseChangeChannel` on a connection of its own (`databaseListenerConninfo`: the worker's plus TCP keepalives). It waits in `poll()` on the socket for `DATABASE_LISTENER_POLL_MS`, reads with `PQconsumeInput`/`PQnotifies`, and sends main one `DatabaseChangeNotification{channel, ids}` per channel per pass (distinct, ascending, owned). A lost connection is reopened with a 1 s to 30 s backoff, logged once per outage; after every `LISTEN`, the first included, it sends `DatabaseChangeListening`, and the router reads each channel's state again (`MainRouterState_databaseChangesListening`), because notifications are not kept for a listener that was away. The worker's own connection never `LISTEN`s, so no query waits on the listener.
- Restricted: a notification enqueues `DatabaseRestrictedChangesRequest` (`DATABASE_RESTRICTED_CHANGES_SQL`: the admin statements' columns per account, and for accounts the router still counts as restricted that are not any more, the Public rooms joined in the same statement and all Public rooms reported); the result goes through `MainRouterState_applyRestrictedChange` per account and one `MainRouterState_resendAllUserLists`. The resync is the `LoadRestrictedUsers` request again: its first answer fills the set (`restrictedUsersLoaded`), a later one reads again the accounts that differ. `LoadRestrictedUsers` and `RestrictedChanges` have no peer and survive `removePendingRequestsForPeer`.
- Idempotence is the rule for every channel: the router's own statements fire the same triggers, and a resync can repeat a notification. `MainRouterState_applyRestrictedChange` does nothing when the set already matches and no room was joined; an admin's SetRestricted is answered before the read its notification causes (one worker, FIFO), so it fans out once. Channels are database-wide, so IDs from another schema on the same database (the SQL tests run beside the live proof's server) are read in the server's schema, found unchanged, and send nothing.
- Adding a channel (#75): a migration with a trigger that calls `haychat_notify_row_id('haychat_...')` (or a function of its own for a table without an `id`), a `DatabaseChangeChannel` member and its name in `DATABASE_CHANGE_CHANNEL_NAMES`, a case in `MainRouterState_handleDatabaseChange` that reads the rows again and applies them through the code path the router's own change uses, and a resync in `MainRouterState_databaseChangesListening`.
- `database_notifications_test.odin` tests the parsing and batching, and against PostgreSQL (`testRestrictedChangeInTheDatabaseReachesSessionsAgainstPostgreSQL`) the real listener thread, the router with stub sessions and an operator's `UPDATE` on another connection; `router_database_changes_test.odin` the router (one fan-out, an admin's change and its notification, a lift's rooms, the resync); `dev/registration-proof.sh` step 7a `deploy/sql/set-restricted.sql` against a live server.

## Network Thread And IPC

- `docs/server-networking.md` describes the threads, the IPC queues, and the network loop.
- The network loop drains every queued IPC message (up to `NETWORK_IPC_DRAIN_LIMIT`) before it services ENet, flushes once per pass, and waits at most `NETWORK_SERVICE_TIMEOUT_MS` (2 ms) in `host_service`. Do not add per-send `host_flush` calls or longer service timeouts: fan-out depends on the drain keeping up.
- `networkDrainIPC` takes the IPC fd and a `NetworkIPCHandlers` callback set, so tests drive it through the real queue without ENet (`network_throughput_test.odin`). Handlers borrow `msg.data`; the drain frees it.
- IPC queues are `IPC_Ring` ring buffers. A consumer that finds its queue empty calls `IPC_Client_wait` with a timeout instead of `thread.yield()` or a fixed sleep; every push signals the destination's condition variable.
- Per-packet logging goes behind `serverLogLevelIsDebug(config.logLevel)` (`HAYCHAT_LOG_LEVEL=debug`). Never log every packet at the default level.
- `NetworkSendData.unreliable` and `NetworkBroadcast.unreliable` default to `false`, which is reliable delivery. Only real-time media should set it.
- There is no network worker pool. Do work that must happen on the network thread in the loop itself, or design a pool that parks on a condition variable.
- No server loop calls `free_all(context.temp_allocator)`, so whatever the router, database, or network loop allocates from the temporary allocator stays allocated for the life of the process. Allocate per-message and per-request scratch on the heap and free it (`make` with `defer delete`), as `MainRouterState_handleJoinVoiceMemberCheckResult` does. Only code that runs once at startup, such as config loading and migrations, uses `context.temp_allocator`.

## Dev Workflow

- `./dev.sh up` starts the dev pod: PostgreSQL 17 and a server built from the working tree. `./dev.sh restart` rebuilds and restarts the server; a compile error leaves the running one up.
- The server migrates and validates its schema before it accepts traffic, so the database role must be able to create and alter objects in `public`. The dev pod's role owns its database.
- `./dev.sh logs [-f]` shows server output (including the `[Status]` lines), `./dev.sh seed` loads `server/sql/auth_bootstrap.sql` (the admin and haypeer accounts; `#general` exists without it), and `./dev.sh psql` opens the dev database.
- Server settings for the pod go in `.env` (see `.env.example`). `./dev.sh` owns the database, listen, and path keys and ignores them there.
- Every startup failure in `main` prints a line starting with `[Startup]` (`dev/live-proof.sh` and `./dev.sh` look for it) and exits through `mainExitStartupFailure` with status 1 after the cleanup it needs, so `Restart=on-failure` and scripts can tell it from a clean shutdown. A new startup step that can fail must do both. `dev/live-proof.sh --sql` (and `--all`) checks it by starting a server against a closed database port.
- `./dev.sh live` is the end-to-end proof: `dev/live-proof.sh` builds the server, starts it against a throwaway database, checks that the server created `#general` as room 1, loads `server/sql/auth_bootstrap.sql` for its admin account, and runs the live client tests. `--all` (what CI runs) adds the two-client room chat, direct message and voice tests, the harness smoke test, the admin proof (`dev/admin-proof.sh`, alone with `./dev.sh live --admin`), the two-process voice proof, the GUI smoke test, the room access and encryption proofs, the registration proof (`dev/registration-proof.sh`, alone with `./dev.sh live --registration`: it runs a second server from the same binary, `HAYCHAT_SERVER_BIN`, on a database it creates and drops, and restores the main server's registration mode), the attachment proof (`dev/attachment-proof.sh`, alone with `./dev.sh live --attachments`), the server SQL proof, and the startup failure exit check.
