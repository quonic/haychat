# HayChat Server Agents Documentation

## Build & Commands

- Typecheck: `odin check server`
- Test: `odin test server -define:ODIN_TEST_THREADS=1` (serial, as `check.sh` runs it)
- Build: `odin build server`
- Run: `odin run server`

## Multi-Channel Server

- Room visibility, chat sends, live-message fanout, and history retrieval are membership-scoped. Never trust a client-provided room ID without checking membership through the database flow.
- Persist a room message before fanout. Fan out the durable message fields, including its ID and timestamp, only to the room's current members.
- Router database work follows the typed request/continuation pattern in `MainRouterState`: queue a `common.DatabaseQuery`, record the matching pending request type, and handle its result in the exhaustive database-result switch. `common.DatabaseQueryRequest` and `common.DatabaseQueryResult` are tagged unions; the cleanup switches in `ipc.odin` are exhaustive, so a new variant will not compile until its cleanup is written.
- Prefer one SQL statement per client action when correctness depends on a check, as `PostRoomChatMessage` (membership check, insert, and recipients) and room history (membership check and page) do. Separate round trips let state change between the check and the action.
- Startup creates the default room: after `databaseMigrateSchema`, and before it reports readiness, the database process runs `DATABASE_ENSURE_DEFAULT_ROOM_SQL`, which inserts `general` (with every account as a member) only when `rooms` is empty, so it takes ID 1 (`common.GENERAL_ROOM_ID`) on a new database. `rooms.created_by_user_id` is nullable for that room; keep code that reads it ready for `NULL`.
- Identity is the client's Ed25519 key; `users.nickname` is the account's current name. `DATABASE_RESOLVE_USER_IDENTITY_SQL` handles every case in one statement: a key that owns an account resolves to it under an unchanged nickname, renames it (`DatabaseUserIdentityResult.renamed`, with the owned `previousNickname` freed in `IPC__database_query_response_deinit`) when the new nickname is free, and returns no row when another account holds it; a key with no account creates one or claims the nickname's keyless account (one with server roles, such as the seeded admin, only for `HAYCHAT_ADMIN_PUBLIC_KEY`). Do not split these checks into separate queries: `users_public_key_unique` and `users.nickname UNIQUE` turn a race into a statement error, never a second account. After a rename, `MainRouterState_completeAuthentication` updates `clientNickname` on the user's other sessions and broadcasts `ServerUserPresence` with the new name even when the user was already online. Chat and direct message rows store only user IDs, so history fetched after a rename shows the new name.
- The identity statement also reads migration 3's columns (protocol 14): a key whose account has `nickname_locked` (an admin renamed it) is never renamed and resolves under the locked name, and a banned account (`banned_at` set) is never renamed and resolves with `DatabaseUserIdentityResult.banned` and its owned `banReason`. Its columns are the user ID, rename flag, previous nickname, admin flag, the account's nickname after this login (owned `nickname`), the lock, the ban, and the reason. The router answers a ban with `ServerAuthFailure` `SERVER_BANNED_MESSAGE` ("This account is banned from this server", plus ": reason"; clients match the prefix) and a disconnect (`MainRouterState_refuseBannedSignIn`), and otherwise passes the nickname and lock to `MainRouterState_completeAuthentication`, which gives the session the account's name before it sends `ServerAuthSuccess{nickname, nicknameLocked}`.
- Room access modes (protocol 15, migration 4; `database_room_access.odin`, `router_room_access.odin`): `rooms.access` (1 Public, 2 Member invite, 3 Admin invite) and `rooms.history_visibility` (1 From join, 2 Full). `DATABASE_RESOLVE_USER_IDENTITY_SQL` joins a newly created account to every Public room in the same statement as the identity upsert; `DATABASE_CREATE_ROOM_SQL` adds every account to a new Public room (and stores Full history for it), and only the creator to an invite room when `creatorJoins`; `DATABASE_EDIT_ROOM_SQL` sets the access too, and a switch to Public adds every account in the same statement and returns the added IDs (`DatabaseRoomMutationResult.addedUserIDs`), which the router tells with `ServerRoomMembershipChanged` (`MainRouterState_roomMembersAdded`). `RoomSummary.historyVisibility` is the effective one: Full for every Public room (`databaseGetRoomHistoryVisibility`).
- Member actions are one `DatabaseRoomMemberActionRequest` (`Add`, `Remove`, `Leave`, `Fetch`; pending `RoomMemberAction`) whose statement checks the requester (admin, member), the room's mode and the target and makes the change, returning `DatabaseRoomMemberOutcome` and the members after it: add needs an admin or (Member invite) a member and refuses Public rooms; remove needs an admin in every mode; leave needs membership of a non-public room; fetch needs membership or the admin role. A missing room is `UnknownRoom` only to admins and `NotMember` to everyone else. A removal or leave also deletes the account's `room_read_markers` row, so a re-added member starts over. Refusals are `ServerProtocolError` sentences (`MainRouterState_roomMemberRefusalMessage`). On a change the router evicts the account from the room's voice (removal, leave), notes it in the voice member cache (add), and sends `ServerRoomMembershipChanged{roomId, joined, userId}` to every session of the account, of the members after the change, and of the requester (`MainRouterState_sendRoomMembershipChange`). Do not move a rule into the router.
- `DATABASE_GET_ROOM_HISTORY_SQL` serves a From join member of a non-public room only messages created after their `room_members.joined_at` (the cut the unread count uses), starting its scan at the first such message ID found through `chat_messages_by_room_id_and_created_at`. `ClientAdminListRooms` is `DatabaseAdminRoomListRequest` (`DATABASE_ADMIN_LIST_ROOMS_SQL`: every room with the admin's membership and its member count, refused to non-admins in the same statement).
- Admin room create/edit/delete require the database-backed server-admin role, checked by `DatabaseUserServerAdminRequest` on every request; membership changes check the role inside their own statement (above). Creating a Public room notifies every authenticated session with `ServerRoomMembershipChanged`, an invite room only the creator's sessions when the creator joined (`ServerRoomMutationPayload.isMember` tells the creator); membership and deletion changes must notify affected users so their clients refresh the authoritative room list. `MainRouterState_hasValidRoomMetadata` uses `common.ROOM_NAME_MAX_BYTES`/`ROOM_DESCRIPTION_MAX_BYTES`, which the client validates against too.
- `ServerAuthSuccess.isAdmin` (protocol 8) tells the client whether to offer room management. It comes from the identity statement itself (`DATABASE_RESOLVE_USER_IDENTITY_SQL` returns a fourth column, `DatabaseUserIdentityResult.isAdmin`) and `MainRouterState_completeAuthentication` passes it, in the `ServerAuthSuccessPayload`, to the `MainRouterAuthSuccessSender`. It is a UI hint; a role changed from a client follows as `ServerAccountUpdated` (below), one changed in the database shows on the next connection (D8). Never use it instead of the per-request admin check.
- Admin actions on accounts (protocol 14, `router_admin.odin`, `database_admin.odin`): `ClientAdminSetRole`, `ClientAdminRenameUser`, `ClientAdminKickUser`, and `ClientAdminBanUser` are checked for shape in the router (user ID, nickname length `common.NICKNAME_MIN_BYTES..NICKNAME_MAX_BYTES` or empty, reasons up to `common.ADMIN_REASON_MAX_BYTES`; anything else is "Invalid admin request") and then become one `DatabaseAdminUserRequest` (pending `AdminUserAction`). Its statement checks the requester's admin role, the guards, and makes the change in one statement, and reports `DatabaseAdminOutcome`: `NotAdmin`, `UnknownUser`, `LastAdmin` (a revoke of the sole admin, checked before `SelfTarget` so that case says why), `SelfTarget` (kick, ban, or revoke of yourself; renaming yourself is allowed), `AdminTarget` (kick or ban of an admin), `BannedTarget` (granting the role to a banned account), `NicknameTaken`, or `Applied` with whether a row `changed`. Do not move a guard into the router or a second query: a role change between a check and the action would slip through. Refusals are `ServerProtocolError` with a sentence (`MainRouterState_adminRefusalMessage`) and the session stays up. On `Applied` the requester gets `ServerAdminActionResult`; a role or rename that changed something sends `ServerUserUpdated` (the full `UserSummary`, `isOnline` from the sessions) to every authenticated session and `ServerAccountUpdated` to every session of the target; a rename that changed the name also renames the target's sessions (`MainRouterState_renameUserSessions`), sends `ServerUserPresence` with the new name while it is online, and refreshes its voice lists (`MainRouterState_voiceRefreshUserRooms`). Kick and ban call `MainRouterState_endUserSessions`: every authenticated session of the target gets `ServerSessionEnded{kind, reason}`, leaves voice, drops its pending requests, is de-authenticated and disconnected, and the user is announced offline once; a ban that changed something then sends `ServerUserUpdated`. Any new path that ends sessions must do the same.
- Room types (protocol 14, migration 3): `rooms.room_type` is `common.RoomType` as a number, only Chat (1), Voice (2) and ChatAndVoice (3) (`common.roomTypeIsSupported`; the router refuses anything else as invalid metadata). Every `RoomSummary` carries it. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` checks it in the same statement as membership and the insert (`DatabasePostRoomChatMessageResult.chatDisabled`, refused with `CHAT_DISABLED_MESSAGE` "Chat is disabled in this room"), and `DATABASE_LIST_ROOM_MEMBERS_SQL` returns it with the members (`roomFound`, `roomType`) for the voice join check. An edit to a type without voice calls `MainRouterState_voiceDisableRoom` before `ServerEditRoom` goes out.
- Chat messages carry `senderNickname`, joined from `users` by the post and history statements. It is an owned string like the other `StoredChatMessage` fields; free it in `IPC__stored_chat_message_deinit`.
- Signed room messages (protocol 22, #90, migration 10): every plaintext `ClientChatMessage` carries a set `clientMessageId` and `signature`; `MainRouterState_handleClientChatMessage` checks it with `common.verifyPlaintextRoomMessage` against the **session's** identity key (this server's key, the room, the session's account, the ID and the content) before the database sees it, and refuses anything else with `common.ROOM_MESSAGE_SIGNATURE_INVALID_MESSAGE`. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` stores the ID and signature (`$5`, `$9`); the unique index on `(sender_user_id, client_message_id)` refuses a reused ID (`ROOM_MESSAGE_DUPLICATE_MESSAGE`). The live echo (`ServerChatMessage`) and history pages carry both, so every client checks the sender's signature against its own pin. Database tests store messages with `databaseTestPlainRoomPost`, `databaseSQLTestPost` and `DATABASE_TEST_PLAIN_COLUMNS_SQL` (a placeholder signature: the database only stores it); router tests sign with `routerTestSignedChat` and the session key `routerCompleteHandshake` hands back (`RouterVoiceTestClient.identityKey`).
- Encrypted direct messages (protocol 17, migration 6): `ClientSealedDirectMessage` is checked in the router for shape (recipient, a non-zero `clientMessageId`, 1..`common.SEALED_ENVELOPE_MAX_BYTES` bytes, `decodeSealedEnvelope` with kind DirectMessage and two wraps; else `common.SEALED_DIRECT_MESSAGE_INVALID_MESSAGE`) and becomes a `DatabasePostDirectMessageRequest` with the envelope (owned), the server's identity key and the **session's** identity key. The database worker reads the recipient's `users.public_key` (`DATABASE_DIRECT_MESSAGE_RECIPIENT_KEY_SQL`), runs `databaseCheckSealedDirectMessage` (pure: `verifyDirectMessageEnvelope` over every AAD field), and inserts with `DATABASE_POST_DIRECT_MESSAGE_SQL`, whose recipient CTE requires that same key, so a key changed in between stores nothing. The fallback `ClientDirectMessage` must carry a non-zero `clientMessageId` and a `signature` that `verifyPlaintextDirectMessage` accepts for the session's identity key (else `common.DIRECT_MESSAGE_SIGNATURE_INVALID_MESSAGE`); unsigned messages, which only pre-17 clients sent, are refused. `direct_messages_sender_client_message_id` makes `(sender_user_id, client_message_id)` unique and the insert's `ON CONFLICT ... DO NOTHING` reports `DirectMessagePostOutcome.Duplicate` (`common.DIRECT_MESSAGE_DUPLICATE_MESSAGE`). Stored envelopes go out as `ServerSealedDirectMessage`, plaintext as `ServerDirectMessage` with its ID and signature; history and the conversation list return the three protocol 17 columns as hex. Both handlers decode with `temp_allocator = context.allocator` (fixed-size byte fields). `database_encrypted_direct_messages_test.odin` and `router_sealed_direct_messages_test.odin` test it.
- Direct messages (`router_direct_messages.odin`, `database_direct_messages.odin`) are between two accounts on this server, never to oneself. The router refuses a self-addressed message before the database, and `DATABASE_POST_DIRECT_MESSAGE_SQL` checks that the recipient exists and is not the sender in the same statement as the insert. Persist before fanout, then send `ServerDirectMessage` to every authenticated session of the sender and of the recipient and to no one else; the sending session gets the echo too, which is how clients learn the stored ID and timestamp. `StoredDirectMessage` owns its two nicknames, timestamp, content and envelope; free them in `IPC__stored_direct_message_deinit`.
- Presence is derived, not stored: a user is online while one of their sessions in `peerSessions` is authenticated. Send `ServerUserPresence` on three triggers:
  - zero to one authenticated sessions: on auth success, to every other authenticated session. `MainRouterState_completeAuthentication` marks the session authenticated only after `ServerAuthSuccess` is sent, so a failed send announces nothing.
  - a login that renames the account, whatever the count: also from `MainRouterState_completeAuthentication`, with the new nickname, to every other authenticated session (the user's other sessions included). An admin rename of an online account sends it too (`router_admin.odin`).
  - one to zero: `MainRouterState_handlePeerDisconnected`, `MainRouterState_protocolViolation`, which de-authenticates a session before its disconnect event arrives, or a kick or ban (`MainRouterState_endUserSessions`, once for all the account's sessions).
  Any new path that ends or de-authenticates a session must call `MainRouterState_noteSessionEnded`. `ServerUserList` online flags come from the same sessions, never from the database.
- Router tests that authenticate two different user IDs must consume the presence notice the second one causes: client transports accept only the next sequence number, so a skipped packet breaks every later open for that session.
- `server/database_direct_messages_test.odin` runs the direct message SQL against a real PostgreSQL when `HAYCHAT_DATABASE_SQL_TEST=1`; it writes and then deletes its own accounts, so point it only at a throwaway database. `server/database_default_room_test.odin` runs the default room statement under the same flag, inside a schema of its own that it rolls back, starting from a protocol 7 `rooms` table that `databaseApplyMigrations` adopts. `server/database_migrations_test.odin` runs the migration runner (see Schema Migrations). `server/database_read_markers_test.odin` runs the unread rules and mark-read against a migrated schema of its own. `server/database_user_identity_test.odin` runs the identity statement (new account, unchanged, rename to a free name, rename to a taken name, auto-join only for new accounts, and the admin flag for an admin, a renamed admin, and an account with another role) the same way. `server/database_admin_test.odin` runs the protocol 14 statements the same way: the identity statement with a locked name and a ban (also a banned keyless account claimed by a key), every admin action with every guard (the last admin, self, admin and banned targets, a taken name, no-op changes), room types in the create, edit, list, member list, and chat post statements, and migration 3 from a version 2 database with rows. `./dev.sh live --sql` (and `--all`) runs them; add new database-backed tests to `SQL_TESTS` in `dev/live-proof.sh`. Open every SQL test connection through `databaseSQLTestOpen(t)` (or `databaseAdminTestOpen`/`databaseMigrationTestOpen`, which use it) and never close it yourself: it registers a `testing.cleanup` that rolls back, drops the test's schema and closes the connection. A `defer` does not run when an assertion fails (the runner stops the thread without unwinding it), and a connection left open inside the transaction holding the migration lock made every later test that migrates wait forever (#80). `dev/live-proof.sh` checks this by running the SQL test binary a second time with `HAYCHAT_DATABASE_SQL_TEST_FAIL=1`, which makes `testAbandonedSQLTestReleasesItsConnectionAgainstPostgreSQL` (it sorts first) fail while it holds that lock: the run must exit non-zero within 2 minutes, name only that test, and pass every other SQL test.
- Read state (migration 2, protocol 11; `database_read_markers.odin`, `router_read_markers.odin`): `room_read_markers` and `direct_read_markers` hold, per account, the newest message ID read in a room or a direct conversation. The unread rules, used by `DATABASE_LIST_ROOMS_FOR_USER_SQL` and `DATABASE_LIST_DIRECT_CONVERSATIONS_SQL`:
  - Rooms: messages from other users with an ID above the marker. With no marker row, messages from others created after the user's `room_members.joined_at` (index `chat_messages_by_room_id_and_created_at`), so a new account or a new room starts with nothing unread.
  - Direct conversations: messages from the peer with an ID above the marker; with no row, every message from the peer.
  - Counts stop at `common.UNREAD_COUNT_CAP` (100), which the client shows as "99+". Each count is a `LIMIT`ed index range scan, so keep new list columns from turning it into a full scan.
  - `ClientMarkRead` is one statement per kind: the access check (membership; for a DM an existing peer who is not the requester), the clamp to the conversation's newest message, the forward-only upsert (`GREATEST`, and a `WHERE` that makes a no-op return no row), and the count after it. The router sends `ServerReadMarker` to every authenticated session of the account, the asking one included, and nothing for a no-op. A refusal is a `ServerProtocolError` (`Not a room member`, `Unknown user`), never `MainRouterState_protocolViolation`: a room can vanish between the client's last list and its mark-read.
  - Only `ServerListRooms` fills `RoomSummary.lastReadMessageId`/`unreadCount`; other payloads that embed `RoomSummary` carry zeros.
- Account encryption keys (protocol 16, `router_encryption_keys.odin`, `database_encryption_keys.odin`): `ClientPublishEncryptionKey` is verified in the router with `common.verifyEncryptionKeyBundle` on a bundle whose identity key is the **session's** (`RouterPeerSession.clientIdentityPublicKey`), so an account can only store a key it signed; anything else, and a `createdAt` above `max(i64)`, is `ServerProtocolError` `common.ENCRYPTION_KEY_INVALID_MESSAGE` before the database. `DATABASE_PUBLISH_ENCRYPTION_KEY_SQL` is one upsert that changes nothing (and returns no row) for an identical bundle; a returned row (first publish or replacement, `replaced`) is sent as `ServerUserKeyChanged` with the account's identity key from `users.public_key` to every authenticated session. `ClientFetchUserKeys` is checked with `common.userKeysFetchIsValid` (1..64 positive, distinct IDs; else `common.USER_KEYS_INVALID_REQUEST_MESSAGE`), and `DATABASE_FETCH_USER_KEYS_SQL` answers in request order, listing accounts without a key, without a bundle, or unknown in `missingUserIds`; only the requester gets `ServerUserKeys`. Both handlers decode with `temp_allocator = context.allocator`, because CBOR decodes fixed-size byte strings through the temporary allocator, which the router never frees; do the same for any new payload with fixed-size byte fields. `DATABASE_LIST_USERS_SQL` and every admin statement return `encode(public_key, 'hex')` and whether a bundle exists (only for an account with an identity key), so `UserSummary.identityPublicKey`/`hasEncryptionKey` are right in `ServerUserList` and `ServerUserUpdated`; presence carries neither.
- Encrypted rooms (protocol 18, migration 7; `database_room_log.odin`, `router_room_log.odin`): `ClientCreateRoom{encrypted}` must be an invite mode (the router refuses Public with `common.ENCRYPTED_ROOM_PUBLIC_MESSAGE`); `DATABASE_CREATE_ROOM_SQL` stores `encrypted` and adds **no** members for an encrypted room. `ClientAppendRoomLog` becomes a `DatabaseAppendRoomLogRequest` (entry owned, the server's identity key, the session's account); the worker runs one transaction (`databaseRoomLogBegin`, a savepoint when the SQL tests already hold a transaction): lock the room row `FOR UPDATE`, replay every stored entry with `common.replayRoomLog` (no pins; a log that does not replay or does not end at `rooms.log_version` is `Damaged` and refuses everything), validate the entry with `RoomLogState_validate` whose `lookupPin` returns each named account's `users.public_key` (an account without one mismatches), then `roomLogServerAllows`: the actor is the requester; Create needs the admin role, the room's creator and the room's own settings; Add needs the admin role or (Member invite) membership in `room_members`; SetAccess needs the admin role. Then insert into `room_log_entries`, move `rooms.log_version` (and `access`), apply to `room_members` (deleting the read marker on a removal, like protocol 15) and `room_log_managers`, commit. The primary key `(room_id, version)` and the lock serialise appends; a version or prevHash that does not follow is `Conflict`. Outcomes become `ServerProtocolError` sentences (`MainRouterState_roomLogRefusalMessage`; `Invalid` adds the `RoomLogError`). An applied entry goes out as `ServerRoomLog` (`MainRouterState_sendRoomLogEntry`) to the sessions of the members and managers after it, its target, and the requester, plus `ServerRoomMembershipChanged` when `room_members` changed. `ClientRemoveRoomMember` on an encrypted room is routed by `databaseExecuteRoomMemberAction` to `databaseExecuteServerRoomLogRemove`, which writes the unsigned Remove (actor 0) itself and returns it in `DatabaseRoomMemberActionResult.logEntry`; Add and Leave are `EncryptedRoom` (`common.ROOM_LOG_REQUIRED_MESSAGE`). `ClientFetchRoomLog` (`DATABASE_FETCH_ROOM_LOG_SQL`) serves members, `room_log_managers` and admins, `ROOM_LOG_FETCH_MAX_ENTRIES` per page with `hasMore`. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` refuses plaintext chat in an encrypted room (`encryptedRoom`, `common.ENCRYPTED_ROOM_CHAT_MESSAGE`; sealed messages since protocol 19, below), the voice join check reports `DatabaseRoomMemberListResult.encrypted` and `logVersion` (protocol 18 to 20 refused voice there; protocol 21 encrypts it, Voice Rooms below), and `DATABASE_EDIT_ROOM_SQL` refuses an edit that changes the flag or an encrypted room's access (`RoomEditRefusal`). Bans do not touch encrypted rooms' logs. `database_room_log_test.odin` (SQL, plus the pure rules) and `router_room_log_test.odin` test it.
- Sender chains in encrypted rooms (protocol 19, migration 8; `router_room_keys.odin`, `database_room_keys.odin`, the sealed path of `MainRouterState_handleClientChatMessage`): a `ClientChatMessage` with `sealed` bytes is checked in the router (`MainRouterState_checkSealedRoomMessage`: no content, a set `clientMessageId`, at most `common.SEALED_ROOM_MESSAGE_MAX_BYTES`, `decodeSealedRoomMessage`, and `verifyRoomMessageSignature` against the **session's** identity key, which is the account's `users.public_key`, over this server, the room, the account, the chain position and the client message ID; else `common.SEALED_ROOM_MESSAGE_INVALID_MESSAGE`) and becomes a `DatabasePostRoomChatMessageRequest` with the bytes (owned) and the decoded epoch, chain ID and index. `DATABASE_POST_ROOM_CHAT_MESSAGE_SQL` stores plaintext only in unencrypted rooms and sealed bytes only in encrypted rooms whose `log_version` is the epoch, in the same statement as membership and the room type; the result says `notEncrypted`, `staleEpoch` (`common.ROOM_KEY_OUT_OF_DATE_MESSAGE`) or `duplicate` (a unique index refused a reused client message ID or chain index; `common.ROOM_MESSAGE_DUPLICATE_MESSAGE`). History returns `client_message_id` and `sealed` as hex. `ClientRoomKeyEnvelope` is checked in the router (`MainRouterState_checkRoomKeyEnvelope`: a SenderKey envelope whose signature verifies under `makeRoomKeyAAD` with the session's account and key; else `common.ROOM_KEY_ENVELOPE_INVALID_MESSAGE`), which also lists its wraps' user IDs; `DATABASE_STORE_ROOM_KEY_ENVELOPE_SQL` stores it only from a member, to members only, at the room's log version or, for a chain already stored, an older epoch (a key request's re-seal), and the stored envelope goes as `ServerRoomKeyEnvelope` to the sessions of its wraps' accounts. `ClientFetchRoomKeys` (`DATABASE_FETCH_ROOM_KEYS_SQL`) serves members only, only envelopes whose `recipient_user_ids` hold the requester, `common.ROOM_KEYS_FETCH_MAX_ENVELOPES` per page by envelope ID. `ClientRequestRoomKey` runs `DATABASE_ROOM_KEY_REQUEST_CHECK_SQL` (encrypted room, both accounts members, the chain stored) and is relayed as `ServerRoomKeyRequest` to the chain sender's sessions; a refused request is dropped without an answer. Handlers with fixed-size byte fields decode with `temp_allocator = context.allocator`. `database_room_keys_test.odin` (SQL) and `router_room_keys_test.odin` test it.
- Full history in encrypted rooms (protocol 20, migration 9; same files): a `ClientRoomKeyEnvelope` whose `senderId` names another account is a forward, checked in the router by `MainRouterState_checkRoomKeyForward` (a RoomKeyForward envelope with one wrap, `verifyRoomKeyForwardEnvelope` under `makeRoomKeyForwardAAD` with the **session's** account and key as the forwarder and that wrap's user as the recipient; else `common.ROOM_KEY_ENVELOPE_INVALID_MESSAGE`). `DATABASE_STORE_ROOM_KEY_ENVELOPE_SQL` ($7 the forwarder, 0 for a SenderKey) stores it only in an encrypted room with `history_visibility` 2, from a member to members, at an epoch up to the log version whose `(sender, chain)` is already stored, and not when a stored envelope of that chain already wraps the recipient (`AlreadyHeld`: dropped without an answer; `NotFullHistory` is `common.ROOM_KEY_FORWARD_NOT_ALLOWED_MESSAGE`). Stored forwards fan out like other envelopes and the fetch returns `forwarder_user_id` (0 for none). `DATABASE_ROOM_KEY_REQUEST_CHECK_SQL` also answers whether the room has Full history and, then, every member but the requester (`DatabaseRoomKeyRequestCheckResult.memberUserIDs`, owned): the router relays the request to all their sessions, with `senderId`; a From join room still needs the sender to be a member and asks only it. `database_room_keys_test.odin` (SQL) and `router_room_keys_test.odin` test it.
- For deterministic router/database validation, use `odin test server -define:ODIN_TEST_THREADS=1`. Database-backed runtime tests require a role that can create and drop schemas, because the SQL tests isolate themselves in schemas of their own.

## Schema Migrations

- `server/database_migrations.odin` holds `DATABASE_MIGRATIONS`, an ordered, append-only list of `{version, name, sql}` starting at 1 with no gaps. Migration 1 (`baseline`) is the v0.1.0-rc1 schema, statement for statement; `testDatabaseBaselineMigrationIsTheRC1Schema` pins it to a frozen copy. Merged migrations are never edited, reordered, or removed.
- At startup `databaseMigrateSchema` runs, in one transaction under `pg_advisory_xact_lock(DATABASE_MIGRATION_LOCK_KEY)`: it creates `schema_migrations` if needed, then applies every migration to an empty schema; adopts HayChat tables that have no recorded version (runs migration 1, which is idempotent, checks them against `DATABASE_BASELINE_VALIDATION_SQL`, and records version 1); applies the missing migrations to an older version; and refuses a newer version. `DATABASE_SCHEMA_VALIDATION_SQL` then checks the newest schema. Any failure rolls back and becomes `DatabaseStartupFailed`, a `[Startup]` line, and exit status 1. Nothing drops tables; do not add a path that does.
- Every migration runs inside that transaction, so statements that cannot run in a transaction block (`CREATE INDEX CONCURRENTLY`, `VACUUM`, `ALTER SYSTEM`, ...) are not supported.
- Migration 2 (`read markers`) adds the read-state tables, their cascade indexes, and `chat_messages_by_room_id_and_created_at`, and backfills markers at the newest message for every existing room member and both sides of every existing conversation, so an upgraded database starts with nothing unread.
- Migration 3 (`admin`, protocol 14) adds `users.nickname_locked BOOLEAN NOT NULL DEFAULT false`, `users.banned_at TIMESTAMPTZ NULL`, `users.ban_reason VARCHAR(256) NOT NULL DEFAULT ''`, and `rooms.room_type SMALLINT NOT NULL DEFAULT 3` with `rooms_room_type_check` (1, 2, 3), so every existing account is unlocked and unbanned and every existing room is text and voice. `DATABASE_ADMIN_CHECKS` validates them.
- Migration 4 (`room access`, protocol 15) adds `rooms.access SMALLINT NOT NULL DEFAULT 1` with `rooms_access_check` (1, 2, 3) and `rooms.history_visibility SMALLINT NOT NULL DEFAULT 2` with `rooms_history_visibility_check` (1, 2), so every existing room is Public with full history. `DATABASE_ROOM_ACCESS_CHECKS` validates them. `database_room_access_test.odin` runs the rules, From join history and the migration from version 3 under `HAYCHAT_DATABASE_SQL_TEST=1`.
- Migration 5 (`user encryption keys`, protocol 16) adds `user_encryption_keys (user_id PK → users ON DELETE CASCADE, encryption_public_key BYTEA (32 bytes), created_at_unix BIGINT (>= 0), signature BYTEA (64 bytes), updated_at)`, with named size checks. Existing accounts start without a row. `DATABASE_USER_ENCRYPTION_KEYS_CHECKS` validates it; `database_encryption_keys_test.odin` runs the statements and the migration from version 4 under `HAYCHAT_DATABASE_SQL_TEST=1`.
- Migration 6 (`encrypted direct messages`, protocol 17) drops the baseline's unnamed check on `direct_messages.content` (found by its definition) and adds `client_message_id`, `envelope` and `signature` (`BYTEA NULL`), `direct_messages_content_or_envelope` (exactly one of a 1..4000 character content or a 1..8192 byte envelope, with content `''`), size checks, `direct_messages_envelope_has_id`, `direct_messages_signature_on_plaintext`, and the partial unique index `direct_messages_sender_client_message_id`. Existing rows stay plaintext without ID or signature. `DATABASE_ENCRYPTED_DIRECT_MESSAGES_CHECKS` validates it; `database_encrypted_direct_messages_test.odin` runs it from version 5 with rows.
- Migration 7 (`encrypted room log`, protocol 18) adds `rooms.encrypted BOOLEAN NOT NULL DEFAULT false` and `rooms.log_version BIGINT NOT NULL DEFAULT 0` with `rooms_encrypted_access` (never Public) and `rooms_log_version_check`, `room_log_entries (room_id → rooms ON DELETE CASCADE, version >= 1, entry BYTEA 1..4208 bytes, created_at, PK (room_id, version))` and `room_log_managers (room_id, user_id, PK, both cascading, index by user)`. `DATABASE_ENCRYPTED_ROOM_LOG_CHECKS` validates it; `testRoomLogMigrationUpgradesVersion6AgainstPostgreSQL` runs it from version 6 with rows. Order by a table column, not a `::text` output alias of the same name (text order).
- Migration 8 (`room sender chains`, protocol 19) drops the baseline's unnamed check on `chat_messages.content` (found by its definition) and adds `client_message_id`, `sealed`, `epoch`, `chain_id` and `chain_index` (all NULL for plaintext), `chat_messages_content_or_sealed` (exactly one of a 1..4000 character content or a 1..8192 byte sealed message with content `''`), `chat_messages_sealed_fields` (a sealed row has all four others), size and position checks, and the partial unique indexes `chat_messages_sender_client_message_id` and `chat_messages_sender_chain_index`; and `room_key_envelopes (id, room_id → rooms, epoch >= 1, sender_user_id → users, chain_id 16 bytes, recipient_user_ids BIGINT[] 1..100, envelope 1..8192 bytes, created_at)`, indexed by `(room_id, epoch)` and by chain. `DATABASE_ROOM_SENDER_CHAINS_CHECKS` validates it; `testRoomSenderChainsMigrationUpgradesVersion7AgainstPostgreSQL` runs it from version 7 with rows.
- Migration 9 (`room key forwards`, protocol 20) adds `room_key_envelopes.forwarder_user_id BIGINT NULL` (NULL for a SenderKey envelope) and `room_key_envelopes_forward_check` (a positive forwarder other than the sender, with exactly one recipient). The column has no foreign key, because migration 8's checks count the table's two cascading keys; the server never deletes accounts, and clients verify a forward against the identity the room log names. `DATABASE_ROOM_KEY_FORWARDS_CHECKS` validates it; `testRoomKeyForwardsMigrationUpgradesVersion8AgainstPostgreSQL` runs it from version 8 with rows.
- Migration 10 (`signed messages`, protocols 22, #82, #90) deletes every unsigned message (plaintext `chat_messages`, none of which had a signature, and `direct_messages` from before protocol 17): clients never show a message without its sender's valid signature, so nobody could read them again. It adds `chat_messages.signature BYTEA NULL` with `chat_messages_signature_size` (64 bytes), replaces `chat_messages_sealed_fields` under the same name (a plaintext row has a client message ID and a signature and no chain fields; a sealed row its client message ID and chain fields and no signature column), and adds `direct_messages_signed` (an envelope or a signature). `DATABASE_SIGNED_MESSAGES_CHECKS` validates it; `testSignedMessagesMigrationUpgradesVersion9AgainstPostgreSQL` runs it from version 9 with rows. The read marker backfill tests stop at version 9, before the deletion.
- To add a migration (the next is 11):
  1. Append `{version = N, name = "...", sql = DATABASE_MIGRATION_N_..._SQL, checks = DATABASE_..._CHECKS}` to `DATABASE_MIGRATIONS`. It runs exactly once per database, so it need not be idempotent, but it must keep existing rows: add columns with defaults, backfill in the same SQL, and never drop data that a client can still read.
  2. Put validation rows for what the migration adds in that `DATABASE_..._CHECKS` constant and append it to `DATABASE_SCHEMA_VALIDATION_SQL` too. The runner validates a list with `databaseSchemaValidationQuery(migrations)` (the baseline, the bookkeeping, and every migration's `checks`), so `DATABASE_MIGRATIONS[:N-1]` still validates as version N-1; `testDatabaseSchemaValidationMatchesTheMigrationList` pins the constant to the production list. If a migration changes a baseline object, replace `DATABASE_BASELINE_SCHEMA_CHECKS` in both with an edited copy; the frozen constant stays for adoption.
  3. Add an SQL test in `server/database_migrations_test.odin` that starts from version N-1 with rows (migrate with `DATABASE_MIGRATIONS[:N-1]` first), applies the migration, and checks the rows and the new objects; add it to `SQL_TESTS` in `dev/live-proof.sh`. The existing tests already run every migration on a fresh schema and on an adopted rc1 schema.
  4. Say in the release notes that the schema changed.
- Validation uses `current_schema()` and unqualified names that `to_regclass` resolves through `search_path`, so the SQL tests run the real runner in schemas of their own (`databaseMigrationTestOpen`) while production uses `public`. `databaseApplyMigrations` is the same runner without its own transaction, for tests that roll back.

## Transport Channels

- `common.TransportState` has four halves with separate keys and counters: `controlSend`, `controlReceive` (strict counter), `voiceSend`, and `voiceReceive` (64-packet replay window). `NetworkChannel.Chat` and `NetworkChannel.Voice` are the same numbers as `common.TransportChannel.Control` and `.Voice` (asserted in `ipc.odin`), and the ENet host allocates channels 0 to 4.
- Who may touch which half: the router (main thread) owns each `RouterPeerSession.transport`, runs the handshake, and alone uses the control halves (`sealPacketForSession`, `openPacketForSession`). The voice halves belong to the network thread: `MainRouterState_completeAuthentication` takes them out with `common.TransportState_takeVoiceState` (which zeroes them in the session before it is stored) right after `ServerAuthSuccess` and sends them in a `NetworkVoiceSessionOpen`; from then on only the network thread's `VoiceRelay` seals or opens that peer's voice datagrams (`sealVoiceDatagram`, `openVoiceDatagram`) and the router never touches voice crypto. Never keep using two copies of one `ChannelSendState`: that reuses voice nonces. The relay's copy is the only live one.
- The router handles only `.Chat` data. Anything on another channel is dropped without a protocol violation, because ENet does not authenticate datagrams; a voice datagram that reaches the router anyway is counted in `MainRouterState.unexpectedVoiceDatagrams`. A bad voice datagram is counted by the relay, never a reason to disconnect.
- Wipe rules for voice keys: `RouterPeerSession_deinit` wipes the transport with `common.TransportState_deinit`. `IPC__message_deinit` wipes a `NetworkVoiceSessionOpen` in place (`ChannelSendState_wipe`, `VoiceReceiveState_wipe`), so a session open that is dropped, unsent, or left in a queue at shutdown never leaves keys behind; `networkDrainIPC` calls it after the handler has moved the keys out. The IPC ring zeroes a slot when it pops it and a buffer before it frees it. The relay heap-allocates each peer, so a map rehash never copies keys, and wipes the peer when it disconnects, on `NetworkVoiceReset`, and when the network loop exits.

## Voice Rooms

- Control plane in the router (`server/voice.odin`, design 4.2): `ClientJoinVoice` checks membership with a `DatabaseRoomMemberListRequest` (pending `JoinVoiceMemberCheck`) and is refused with `ServerVoiceJoinRejected` and a human reason (not authenticated, invalid room, voice disabled, not a room member, voice is disabled in this room for a text-only room (protocol 14, checked after membership), room full, database unavailable, invalid device ID, voice active on another device). A join while in another room sends `ServerVoiceLeft` for the old room and fans it out first; a refused switch keeps the session where it was. `ClientLeaveVoice` and `ClientVoiceState` outside voice are no-ops. `MainRouterState.voiceRooms` and `peerVoiceRoom` are the source of truth.
- One voice session per user (Q2, protocol 13): a voice session belongs to a client session, but an account has at most one, so a participant list names each user once. `MainRouterState_handleJoinVoiceMemberCheckResult` decides before it changes anything, so a refused join leaves every session where it was: a join with `rejoin` (the client's automatic re-join after a reconnect) is refused with "voice is active on another device" while another session of the user is in voice with a different device ID; otherwise every other voice session of the user is removed first with `ServerVoiceLeft{"joined voice on another device"}`, and its room gets its route and participant update unless it is the room being joined, whose single update shows the replacement. A replaced session frees its place, so a takeover in a full room succeeds. `VoiceParticipantState.deviceID` is the parsed `ClientJoinVoicePayload.deviceId`, used only for that comparison and never sent or logged; `handleClientJoinVoice` refuses a missing or malformed one with "invalid voice device ID" without ending the session, before the membership check.
- Every change sends the network thread a full `NetworkVoiceRoute` for the room (never a delta), then `ServerVoiceParticipants` (the full set, nicknames from `peerSessions`) to every authenticated session of every room member. Recipients come from `VoiceRoomState.memberUserIDs`, a cache that each join check replaces, a room list or an added member extends, and a member removal narrows, so leaves, mute changes and disconnects fan out without a database round trip. A room's state is dropped once its participant set is empty and announced.
- After `ServerListRooms` the requester also gets `ServerVoiceParticipants` for each of its rooms with active voice.
- Every `ServerVoiceParticipants` carries `recipientJoined` (protocol 12), set per recipient session by `MainRouterState_voicePeerIsInRoom`: true only when the session receiving it is itself in that room's voice. Participants carry user IDs, not sessions, so this is how a client tells its own join acknowledgement from a list that names its account on another device. Set it on every send path; the shared payload from `MainRouterState_voiceBuildParticipants` leaves it false.
- Sessions leave voice on disconnect (before `MainRouterState_removePeerSession`, skipping the departing session) and on `MainRouterState_protocolViolation`. A member removal evicts that user's sessions and a room deletion every participant, each with `ServerVoiceLeft{reason}` (deletion sends no participant list). Editing a room to text-only (`MainRouterState_voiceDisableRoom`) removes every participant with `ServerVoiceLeft{"voice is disabled in this room"}` and then sends the members the empty list, since the room is still there. A kick or ban leaves voice through `MainRouterState_endUserSessions`. `MainRouterState_prepareForProcessStop(.Network)` clears all voice state and sends `NetworkVoiceReset`, so commands queued before a network restart cannot attach to the new service's reused peer IDs.
- Data plane on the network thread (`server/voice_relay.odin`, design 4.3): `handlePeerData` hands every channel 2 packet to `VoiceRelay_handleDatagram` and never to the router. The relay is a pure state machine with an injected send and clock, so its tests need no ENet; keep it that way. Per datagram it allocates nothing, logs nothing, and counts every drop by reason in `VoiceRelayStats`; no drop disconnects a peer. The loop flushes ENet once per pass when the relay sent anything.
- Voice counters reach the main thread's `[Status]` log line (`server/status.odin`, every `SERVER_STATUS_LOG_INTERVAL` and once at shutdown) through `voiceRelayPublishedStats`, which the network loop updates with atomic stores after each ENet pass in which the counters changed, and `MainRouterState_statusSnapshot` reads with atomic loads. Rooms and participants come from the router. The server has no HTTP or admin port. Per-room counters and a speaking broadcast are deliberately absent.
- Encrypted voice (protocol 21, design `docs/plan/e2ee-voice-design.md` 3.3 and 6): joins of encrypted rooms are accepted like any other; the join check's `DatabaseRoomMemberListResult` carries `encrypted` and `logVersion`, kept on `VoiceRoomState` (`logVersion` also moves on every `ServerRoomLog` fan-out through `MainRouterState_voiceLogAdvanced`, called from `MainRouterState_sendRoomLogEntry`, so the server-written Remove counts too). That fan-out also records the version in `MainRouterState.roomLogVersions` (every room, voice or not; removed when the room is deleted), and a voice room takes the larger of it and the join check's `logVersion`, so an append applied while a room's first join is still in the database is not lost (#77). `ClientVoiceKey` is checked in the router only (`MainRouterState_checkVoiceKey`: a valid `VoiceKey` envelope without a wrap for its sender, signed by the **session's** identity key over every field of `makeVoiceKeyAAD`), accepted only from a session in that room's voice, for an encrypted room, at the room's current log version (`VOICE_KEY_OUT_OF_DATE_MESSAGE` for an older epoch, `VOICE_KEY_INVALID_MESSAGE` otherwise, the session stays). The latest key per participant lives in `VoiceRoomState.keys` (memory only, never the database), goes to every other participant as `ServerVoiceKey`, and is handed to a joiner right after its acknowledging `ServerVoiceParticipants` (`MainRouterState_voiceSendStoredKeys`). `VoiceRoomState_pruneKeys` (in `MainRouterState_voiceRoomChanged` and `MainRouterState_voiceRemoveParticipant`) forgets the keys of sessions that left, were taken over, evicted or disconnected; `VoiceRoomState_dropStaleKeys` those of older epochs. `ClientRequestVoiceKey` is relayed to the speaker's voice session as `ServerVoiceKeyRequest` at most once per requester and speaker every `VOICE_KEY_REQUEST_INTERVAL_SECONDS` (`requestStamps`), anything else dropped silently. `NetworkVoiceRoute.encrypted` marks the room for the relay, which then skips the Opus TOC check, drops a payload that is not a sealed one (`NotSealed`, `voicePayloadLooksSealed`), applies `maxFrameBytes` to the payload minus `VOICE_E2EE_OVERHEAD`, and forwards it unchanged; unencrypted routes are relayed exactly as before.
- Config: `HAYCHAT_VOICE_ENABLED`, `HAYCHAT_VOICE_MAX_PARTICIPANTS`, `HAYCHAT_VOICE_MAX_PACKETS_PER_SECOND`, `HAYCHAT_VOICE_MAX_FRAME_BYTES` (`loadVoiceConfig`, clamped by `validateVoiceConfig`). The router test harness sets the defaults explicitly, because its `ServerConfig` is zeroed.

## Network Thread And IPC

- `docs/server-networking.md` describes the threads, the IPC queues, and the network loop.
- The network loop drains every queued IPC message (up to `NETWORK_IPC_DRAIN_LIMIT`) before it services ENet, flushes once per pass, and waits at most `NETWORK_SERVICE_TIMEOUT_MS` (2 ms) in `host_service`. Do not add per-send `host_flush` calls or longer service timeouts: fan-out depends on the drain keeping up.
- `networkDrainIPC` takes the IPC fd and a `NetworkIPCHandlers` callback set, so tests drive it through the real queue without ENet (`network_throughput_test.odin`). Handlers borrow `msg.data`; the drain frees it.
- IPC queues are `IPC_Ring` ring buffers. A consumer that finds its queue empty calls `IPC_Client_wait` with a timeout instead of `thread.yield()` or a fixed sleep; every push signals the destination's condition variable.
- Per-packet logging goes behind `serverLogLevelIsDebug(config.logLevel)` (`HAYCHAT_LOG_LEVEL=debug`). Never log every packet at the default level.
- `NetworkSendData.unreliable` and `NetworkBroadcast.unreliable` default to `false`, which is reliable delivery. Only real-time media should set it.
- There is no network worker pool. Do work that must happen on the network thread in the loop itself, or design a pool that parks on a condition variable.
- No server loop calls `free_all(context.temp_allocator)`, so whatever the router, database, or network loop allocates from the temporary allocator stays allocated for the life of the process. Allocate per-message and per-request scratch on the heap and free it (`make` with `defer delete`), as `MainRouterState_handleJoinVoiceMemberCheckResult` does. Only code that runs once at startup, such as config loading and migrations, uses `context.temp_allocator`.

## Dev Workflow

- `./dev.sh up` starts the dev pod: PostgreSQL 17 and a server built from the working tree. `./dev.sh restart` rebuilds and restarts the server; a compile error leaves the running one up.
- The server migrates and validates its schema before it accepts traffic, so the database role must be able to create and alter objects in `public`. The dev pod's role owns its database.
- `./dev.sh logs [-f]` shows server output (including the `[Status]` lines), `./dev.sh seed` loads `server/sql/auth_bootstrap.sql` (the admin and haypeer accounts; `#general` exists without it), and `./dev.sh psql` opens the dev database.
- Server settings for the pod go in `.env` (see `.env.example`). `./dev.sh` owns the database, listen, and path keys and ignores them there.
- Every startup failure in `main` prints a line starting with `[Startup]` (`dev/live-proof.sh` and `./dev.sh` look for it) and exits through `mainExitStartupFailure` with status 1 after the cleanup it needs, so `Restart=on-failure` and scripts can tell it from a clean shutdown. A new startup step that can fail must do both. `dev/live-proof.sh --sql` (and `--all`) checks it by starting a server against a closed database port.
- `./dev.sh live` is the end-to-end proof: `dev/live-proof.sh` builds the server, starts it against a throwaway database, checks that the server created `#general` as room 1, loads `server/sql/auth_bootstrap.sql` for its admin account, and runs the live client tests. `--all` (what CI runs) adds the two-client room chat, direct message and voice tests, the harness smoke test, the admin proof (`dev/admin-proof.sh`, alone with `./dev.sh live --admin`), the two-process voice proof, the GUI smoke test, the server SQL proof, and the startup failure exit check.
