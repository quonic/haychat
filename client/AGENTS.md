# HayChat Client Agents Documentation

## Build & Commands

- Typecheck: `odin check client`
- Test: `odin test client` and `odin test client/ui` (the UI toolkit is its own package)
- Build: `odin build client`
- Run: `odin run client`

## Multi-Channel Client

- `State` owns room data in server-scoped caches. Cache identity is `(serverID, roomID)` because room IDs can overlap between configured servers. Do not reintroduce a global room transcript or global channel draft as the source of truth.
- Keep every loaded history page and live message in its room cache. A live message for an inactive room or inactive server must update only that cache; render updates are limited to the selected server and selected room.
- Drafts are client-local and belong to their room cache. Switching rooms restores that room's draft without sending or persisting it.
- `transport.odin` owns encrypted runtime packet construction and decoded runtime-event cleanup. `State_applyRuntimeEvent` in `actions.odin` moves dynamic payloads (room lists, edited rooms) into `State` and clears the moved fields on the event; the caller still runs `ClientTransportRuntimeEvent_deinit` to free whatever was only borrowed.
- `network_worker.odin` services every server session on a background thread and queues decoded runtime events, then wakes the UI loop through its `onEventQueued` callback. The frame loop in `app.odin` drains that queue (`State_drainNetworkEvents`) before drawing. Any UI-thread code that sends through a transport or reads its mutable fields (`lastError`, `connection`, crypto state) must hold `ClientNetworkWorker_lock`. The worker thread runs with the creating thread's context, so its allocations are freed with the same allocator (and the test leak checker tracks them).
- Connecting is non-blocking. `connection.odin` holds the per-transport connect state machine (`Idle`, `Connecting`, `Handshaking`, `Established`, `Failed`, `Disconnected` with a `nextAttemptAt` retry time), driven by `ClientServerTransport_serviceRuntime` on the worker. It emits `Connecting`, `Connected` (user ID, nickname, and a server key pinned on first use), `ConnectFailed` (raw message, `failureKind`, `retryable`, `retryAt`), and `Disconnected` runtime events. Retries back off 1, 2, 4, … s capped at 30 s with jitter; `classifyConnectFailure` decides what is retryable. Add new server failure strings there when the server gains them.
- `State_initFromConfig` only queues every server to connect; nothing touches the network until `State_startNetwork` starts the worker (`init` does this for the GUI). Tests that never start a worker get no network I/O. The worker holds a slice of `state.serverTransports`, so code that rebuilds that array must go through `State_reconfigureNetwork` (stop, rebuild, restart).
- `State.serverConnections` is the UI thread's mirror of each server's connection, updated only from runtime events and the `State_retryConnection`/`State_trustNewServerKey` actions. The view and view models read it (`State_isServerConnected`, `State_selfUserID`, `buildConnectionBanner`) and never the transport's own fields. Room list and history requests are skipped while a server is not connected; `Connected` requests the room list, and the room list requests the selected room's newest history page.
- The transport never touches the config: it keeps its own copies of the server pins, and the `Connected` event carries a newly pinned key back to `State`, which writes `config.json` through `State_saveConfig`. `State_saveConfig` writes only when `state.persistConfig` is set, which only `init` does, so tests never write a config file.
- `State_initFromConfig` uses the config as given. An empty display name or server list opens the first-run settings screen (`settings.odin`, `view_settings.odin`). Tests or tools that want the old built-in profile ("Test User" on `localhost:12345`) call `Config_fillLocalDefaults` first.
- The UI is immediate mode: `view.odin` draws every frame from `State` and calls `State_*` actions in `actions.odin` directly when a widget reports a click or submit. Keep logic in actions and pure view models (`view_model.odin`) so it stays testable without a window; `client/ui` must not depend on HayChat types. Run actions after a list loop when they can reallocate the arrays being drawn.
- Transcript lines label other senders with the message's `senderNickname` (an owned string in every cached `StoredChatMessage`; clone it on merge, free it on deinit) and the local user as "You". "User N" is only the fallback for an empty nickname.
- Build sidebar rooms from the selected server's joined-room list. The chat view derives its transcript from structured cached messages and only shows pagination when `hasOlder` is true.
- Add action tests for cache isolation, history page merge/de-duplication, and selected-room removal fallback whenever channel behavior changes.

## Direct Messages

- `direct_messages.odin` holds the per-server direct-message state (`State.serverDirectCaches`, one `ServerDirectCache` per server): the user directory (`users`, every account including yourself, `isOnline` updated in place by `ServerUserPresence`), the conversation list (`conversations`, most recent first), and one `DirectConversationCache` per peer. Cache identity is `(serverID, peerUserID)`: user IDs overlap between servers exactly like room IDs.
- Never append a sent direct message locally. `State_sendDirectMessageTo` only sends the draft and clears it when the transport accepted it; the message enters the cache when the server's `ServerDirectMessage` echo arrives (to every session of both users), carrying the stored ID and timestamp. The conversation's peer is the recipient when you are the sender, otherwise the sender (`directMessagePeerUserID`).
- Messages merge by ID (`DirectConversationCache_mergeMessage` clones the borrowed strings), so overlapping history pages and live echoes never duplicate. Cursor 0 fetches the newest page and older pages use `oldestMessageID`, like rooms. Only a page that reaches the oldest loaded message may change `hasOlder`, so reloading the newest page after a reconnect does not bring back "Load older".
- A received message from the peer counts as unread unless that conversation is open (`State_isDirectConversationOpen`); every new message moves its conversation to the top of `conversations`, adding it when missing. Opening a conversation clears its count. There is no server read state.
- The open conversation is `State.selected_dm_peer_id` on the selected server, kept apart from `selected_channel_id`: opening a conversation leaves the room selection alone, clicking a channel sets the peer back to 0, and switching servers or rebuilding a server's transport closes it.
- `Connected` requests the room list, then the user list and the conversation list, and the open conversation's newest page. `State_resetDirectRequests` clears the loading flags on every connection change and marks conversations for reload on a new session. `State_receiveUserList` and `State_receiveDirectConversations` take ownership of the event's arrays; presence for an unknown account takes the event's nickname. The server announces a rename as presence, so `State_userPresenceChanged` also replaces a known account's nickname in `users` and in its `conversations` summary when the event's differs; cached messages keep the `senderNickname` they were stored with, and a history fetch brings the current name.
- The sidebar is built by `buildSidebarRows` (channels, Direct Messages, Members) and the DM pane by `buildDirectConversationView`, both in `view_model.odin`; `view_direct.odin` draws the pane. Test DM logic through the actions and view models (`direct_messages_test.odin`), swapping `directMessageSendBridge` under `directMessageSendBridgeTestMutex` when a test needs to observe a send.

## Dev Workflow

- Start the dev server with `./dev.sh up`; seed fixture users and `#general` with `./dev.sh seed`.
- `./dev.sh client [PROFILE]` builds the client from the working tree and opens it on the host's Wayland or X11 display, inside the dev pod. Each profile keeps its config and identity key in its own volume, and a new profile starts with the profile name as display name and the dev server (`localhost:12345`) as its server, so profiles are distinct users. `./dev.sh key PROFILE` prints a profile's public key.
- A client on the host (`odin run client`) uses the host's real `~/.config/haychat`; with an empty config it opens the first-run screen, where `localhost` reaches the dev server. Point `XDG_CONFIG_HOME` at a scratch directory to try the first-run flow without touching your real identity.
- `headless.odin` is the headless harness (`client --headless`, see `docs/testing-harness.md`). It drives `State` and the actions with no SDL; `main` in `app.odin` only branches to it. Its connect step is one procedure (`headlessConnectAndWait`), so connection-flow changes adapt there. New runtime event kinds need a name and a case in `headlessRenderRuntimeEvent`; new user actions can get a row in `HEADLESS_COMMANDS`. Direct messages have `users`, `conversations`, `dm`, and `dm-history` commands and `direct_message`, `direct_history`, `user_list`, `conversations`, and `presence` events.
- Live client tests (`HAYCHAT_LIVE_STARTUP_AUTH=1`) run through `./dev.sh live`, which gives them a fresh server and database. They connect to `127.0.0.1:12345`.
