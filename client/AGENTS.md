# HayChat Client Agents Documentation

## Build & Commands

- Typecheck: `odin check client`
- Test: `odin test client`, `odin test client/ui` (the UI toolkit is its own package), `odin test client/hotkey` (global push-to-talk) and `odin test client/toneanalysis`
- Build: `odin build client`
- Run: `odin run client`

## Multi-Channel Client

- `State` owns room data in server-scoped caches. Cache identity is `(serverID, roomID)` because room IDs can overlap between configured servers. Do not reintroduce a global room transcript or global channel draft as the source of truth.
- Keep every loaded history page and live message in its room cache. A live message for an inactive room or inactive server must update only that cache; render updates are limited to the selected server and selected room.
- Drafts are client-local and belong to their room cache. Switching rooms restores that room's draft without sending or persisting it.
- `transport.odin` owns encrypted runtime packet construction and decoded runtime-event cleanup. `State_applyRuntimeEvent` in `actions.odin` moves dynamic payloads (room lists, edited rooms) into `State` and clears the moved fields on the event; the caller still runs `ClientTransportRuntimeEvent_deinit` to free whatever was only borrowed.
- `network_worker.odin` services every server session on a background thread and queues decoded runtime events, then wakes the UI loop through its `onEventQueued` callback. The frame loop in `app.odin` drains that queue (`State_drainNetworkEvents`) before drawing. Any UI-thread code that sends through a transport or reads its mutable fields (`lastError`, `connection`, crypto state) must hold `ClientNetworkWorker_lock`. The worker thread runs with the creating thread's context, so its allocations are freed with the same allocator (and the test leak checker tracks them).
- Connecting is non-blocking. `connection.odin` holds the per-transport connect state machine (`Idle`, `Connecting`, `Handshaking`, `Established`, `Failed`, `Disconnected` with a `nextAttemptAt` retry time), driven by `ClientServerTransport_serviceRuntime` on the worker. It emits `Connecting`, `Connected` (user ID, the account's nickname from `ServerAuthSuccess`, which an admin may have locked to another one than the display name, `nicknameLocked`, and a server key pinned on first use), `ConnectFailed` (raw message, `failureKind`, `retryable`, `retryAt`), and `Disconnected` runtime events. Retries back off 1, 2, 4, … s capped at 30 s with jitter; `classifyConnectFailure` decides what is retryable. Add new server failure strings there when the server gains them. Protocol 14: a message starting with `SERVER_BANNED_MESSAGE` (the server's refusal of a banned sign-in) is `.Banned`, and `ServerSessionEnded` on an established session is turned by `ClientServerTransport_sessionEnded` into a `.SessionEnded` event built like `ConnectFailed` (`failureKind` `.Kicked` with `CLIENT_KICKED_MESSAGE` or `.Banned`, the admin's reason in `detail`): the transport stops at `Failed`, so the next automatic reconnect never undoes a kick, and only `State_retryConnection` connects again. `buildConnectionBanner` says "Kicked" or "Banned" with the reason instead of "Could not connect". Protocol 25 (#43 G1): `ClientAuthRequestPayload.registering` is sent false, and a `ServerRegistrationRequired` answer ends the handshake as a `.RegistrationRequired` failure (message `CLIENT_REGISTRATION_REQUIRED_MESSAGE` plus the server's sentence) that is not retried; G2 replaces this with the sign-up flow.
- `State_initFromConfig` only queues every server to connect; nothing touches the network until `State_startNetwork` starts the worker (`init` does this for the GUI). Tests that never start a worker get no network I/O. The worker holds a slice of `state.serverTransports`, so code that rebuilds that array must go through `State_reconfigureNetwork` (stop, rebuild, restart).
- `State.serverConnections` is the UI thread's mirror of each server's connection, updated only from runtime events and the `State_retryConnection`/`State_trustNewServerKey` actions. The view and view models read it (`State_isServerConnected`, `State_selfUserID`, `buildConnectionBanner`) and never the transport's own fields. Room list and history requests are skipped while a server is not connected; `Connected` requests the room list, and the room list requests the selected room's newest history page.
- The transport never touches the config: it keeps its own copies of the server pins, and the `Connected` event carries a newly pinned key back to `State`, which writes `config.json` through `State_saveConfig`. `State_saveConfig` writes only when `state.persistConfig` is set, which only `init` does, so tests never write a config file.
- `State_initFromConfig` uses the config as given (after `Config_validateServers`, which `loadConfig` runs too). An empty display name or server list opens the first-run settings screen (`settings.odin`, `view_settings.odin`). Outside first run the General tab edits only the global name and adds servers; an existing server's address, labels and key are in its Server settings (see below). Tests or tools that want the old built-in profile ("Test User" on `localhost:12345`) call `Config_fillLocalDefaults` first.
- The UI is immediate mode: `view.odin` draws every frame from `State` and calls `State_*` actions in `actions.odin` directly when a widget reports a click or submit. Keep logic in actions and pure view models (`view_model.odin`) so it stays testable without a window; `client/ui` must not depend on HayChat types. Run actions after a list loop when they can reallocate the arrays being drawn.
- Transcript lines label other senders with the message's `senderNickname` (an owned string in every cached `StoredChatMessage`; clone it on merge, free it on deinit) and the local user as "You". "User N" is only the fallback for an empty nickname.
- Build sidebar rooms from the selected server's joined-room list. The chat view derives its transcript from structured cached messages and only shows pagination when `hasOlder` is true.
- Add action tests for cache isolation, history page merge/de-duplication, and selected-room removal fallback whenever channel behavior changes.

## Transport Channels

- `common.TransportState` has four halves with separate keys and counters: `controlSend`, `controlReceive` (strict counter), `voiceSend`, and `voiceReceive` (64-packet replay window). Control is ENet channel 1 (`STARTUP_AUTH_CHANNEL_CHAT`), voice is channel 2 (`STARTUP_AUTH_CHANNEL_VOICE`); `transport.odin` asserts both against `common.TransportChannel` at compile time.
- Who may touch which half: the control halves belong to the network worker, and the UI thread reaches them only through `sealPacketForSession` under `ClientNetworkWorker_lock` (the existing rule). `voiceReceive` is used only by the worker, in its channel 2 receive path. `voiceSend` is used only by the voice thread, which seals **and** sends while holding `ClientNetworkWorker_lock` (`ClientServerTransport_sendVoiceFrame`, a few microseconds). The lock is required, not just for ENet: on a reconnect the worker rewrites `voiceSend` (`TransportState_activate`) and on a lost session wipes it, both under the lock, so sealing outside it could race them. The voice halves are never taken out of the transport (`TransportState_takeVoiceState` is the server's tool); there is one live copy of each `ChannelSendState`, so no voice nonce is reused.
- Channel 2 during the handshake is dropped by `ClientServerTransport_acceptReceiveChannel` and counted (`voiceStats.receiveDropped[.BeforeSession]`); any channel other than 1 and 2 is counted as `.WrongChannel` in every phase. A stray datagram is never parsed as a control packet, which would end the session.
- Keys are wiped, not just dropped: `TransportState_reset` and `TransportState_deinit` zero every half with `crypto.zero_explicit`, and the pending handshake keys are wiped once the transport is activated.

## Server Settings

- `server_settings.odin` holds one server's settings screen (`State.serverSettings`, a `ServerSettingsForm`) and its actions; `view_server_settings.odin` draws it in the main pane while `State_serverSettingsVisible` (open on the selected server), before the room form in `viewApp`. The settings are client-local (plan decision D1): fields of the server's `Server` entry in `config.json`, never synced, and nothing reaches the server except the name the transport signs in with.
- `State_openServerSettings(state, serverID)` switches to that server when another is shown, closes the general settings and the room form, and fills the fields from the config; the sidebar header's gear (`server-settings SERVER`) and the rail button's context menu ("Server settings") call it. `State_closeServerSettings` closes it, and so do `State_switchToServer`, `State_switchToChannel`, `State_openDirectConversation`, the room form's open actions and `State_openSettings`; `State_reconfigureNetwork` closes it when its server is gone. An open conversation stays selected underneath. While visible, nothing is viewed for read state (`State_isConversationViewed`), as with the settings screen and the room form.
- Profile and Server share one Save (`State_applyServerSettings`, validated by `validateServerSettings`: the name like the global one via `validateDisplayName` or empty, the address via `validateServerAddress`, labels one line, the short label at most 3 runes and 8 bytes; empty labels are filled from the address). `Server.display_name` overrides `Config.display_name` on that server only (`Server_displayName`, plan decision D2): `ClientServerTransport_init` signs in with it and `ClientServerTransport_matchesConfig` compares it, so a per-server rename, or a global rename, rebuilds only the transports whose effective name changed. Labels alone rebuild nothing. `Server_setAddress` (shared with the General form's first-run path) clears the pins and lets automatic labels follow the address.
- Forget key (`State_serverSettingsForgetKey`) and Remove server (`State_serverSettingsRemoveServer`, which calls `State_settingsRemoveServer`) take two calls, the first arms them; any other action disarms. Forget key clears the pins and calls `State_reconfigureNetwork`: `matchesConfig` also compares the pinned key, which is safe because it runs only with the worker stopped and every Connected event that pinned a key already applied, so only that server reconnects and pins on first use again.
- The banner's **Open settings** for a name problem calls `State_openNameSettings`, which opens Server settings when the server has a name of its own, else Settings; `buildConnectionBanner` and the harness's `connect_failed` text name the effective name.
- Voice section: `buildServerVoiceUserRows` lists every other account of the server's user directory (in `sortedMembers` order) with voice participants of that server first, plus participants the directory does not have yet and stored entries for users not listed (so they can be reset). Each row's slider and Mute for me call the per-user voice actions below. Widget IDs: `server-settings-name`, `-label`, `-short`, `-host`, `-port`, `-save`, `-close`, `-forget-key`, `-remove` (with the server ID), `server-voice-volume` and `server-voice-mute` (server ID, user ID). The Profile section shows the server's name read-only with "Set by an admin of this server" instead of the field while `ServerConnection.nicknameLocked` (`ServerSettingsView.nameLocked`/`lockedName`). The Admin section is described under Admin UI.
- Per-user voice (`user_voice.odin`, issue 47): `Server.user_voice` holds `{user_id, volume, muted}` for users that differ from the default (volume 1, not muted; `Server_setUserVoice` drops default entries, at most `SERVER_USER_VOICE_MAX_ENTRIES`). `State_setUserVoice` / `State_setUserVoiceVolume` / `State_setUserVoiceMuted(state, serverID, userID, …)` store it (saving unless `persist` is false, which sliders pass while dragging) and, when voice runs on that server, apply it to the engine at once (`VoiceEngine_setSpeakerControl`); `State_voiceStartEngine` gives every new engine its server's entries through `State_voiceApplyUserVoice` before it starts. `State_userVoice` reads one. The Voice section's rows, the voice participant menu (see Context Menus) and the harness's `voice-volume` / `voice-mute-user` call them.
- Tests: `server_settings_test.odin` (open and close rules, the per-server name rebuilding only that transport and a global rename skipping it, labels and address, Forget key, Remove server, the Voice rows), `user_voice_test.odin` (the engine's table, gain and mute on the file sink, the State actions), `config_test.odin` (round trip and validation of the per-server keys).

## Room Management (Admins)

- `room_admin.odin` holds the admin's room form (`State.roomEditor`, a `RoomEditor` with modes `Closed`, `Create`, `Edit`) and the request actions `State_sendCreateRoom`, `State_sendEditRoom`, `State_sendDeleteRoom`, which validate like the server (`validateRoomMetadata`: name 1..`common.ROOM_NAME_MAX_BYTES` with one leading `#` dropped, description up to `common.ROOM_DESCRIPTION_MAX_BYTES`, no duplicate of a cached room name) and send through `roomAdminSendBridge` (tests swap it under `roomAdminSendBridgeTestMutex`). `view_room_admin.odin` draws the form in the main pane while `State_roomEditorVisible`.
- The admin flag is `ServerConnection.isAdmin`, copied from the `Connected` event (`ServerAuthSuccess.isAdmin`, protocol 8), updated in place by `.AccountUpdated` (`ServerAccountUpdated`, protocol 14, #41: `State_accountUpdated` also takes the nickname and `nicknameLocked`, and closes the room form when the role went away), and cleared on every connection change; read it with `State_isServerAdmin`. Since protocol 23 the room controls follow the account's permissions instead (`State_hasPermission(state, serverID, .ManageRooms)`: `SidebarRow.action == .NewRoom` on the Channels header, `RoomView.canEditRoom`, `State_openRoomCreator`/`State_openRoomEditor`, the channel menu's Edit/Delete; see Roles below); the server checks the permission for every request. A permission or role changed directly in the database shows on the next connection.
- Room types (protocol 14): every cached `common.RoomSummary` carries `roomType` (Chat, Voice, ChatAndVoice; read one with `State_roomType`). `RoomEditor.roomType` starts at ChatAndVoice for Create and at the room's own for Edit; `State_sendCreateRoom` takes a type (ChatAndVoice by default) and `State_sendEditRoom` requires one, so an edit never changes a type by accident. `RoomAdminRequest.roomType` goes out in `ClientCreateRoom`/`ClientEditRoom`. The client does not refuse chat in a voice-only room or a voice join in a text-only one by itself; the server does (`Chat is disabled in this room`, `voice is disabled in this room`). The client hides the controls: `State_roomAllowsChat` / `State_roomAllowsVoice` (`admin_ui.odin`; an unsupported type counts as both, via `roomTypeShown`) make `RoomView.allowsChat` false for a voice-only room, which draws `ROOM_VOICE_ONLY_NOTE` ("This room is voice only") where the composer would be, and `roomVoiceHeaderAction` `.None` for a text-only room (unless voice there is still active, which shows Leave), so neither the header nor the channel menu offers Join voice. The room form's type selector (`room-type N`, N the protocol number: 1 text, 2 voice, 3 both, in `ROOM_EDITOR_TYPES` order) calls `State_setRoomEditorType`; `RoomEditorView` carries `roomType`, `typeNote` (`roomTypeNote`) and `typeWarning` (an edit to text-only of a room with people in its voice).
- Admin actions on accounts (protocol 14, `admin.odin`): `State_sendAdminSetRole`, `State_sendAdminRenameUser` (an empty name changes only the lock), `State_sendAdminKickUser`, and `State_sendAdminBanUser` (an unban sends no reason) validate like the server (`validateAdminRequest`: a target, names of `common.NICKNAME_MIN_BYTES..NICKNAME_MAX_BYTES`, reasons up to `common.ADMIN_REASON_MAX_BYTES`) and send through `adminSendBridge` (tests swap it under `adminSendBridgeTestMutex`). They leave the guards (yourself, other admins, the last admin) to the server. `State.adminRequest` (`AdminRequestState`) records the last request: `.AdminActionResult` (`ServerAdminActionResult`, the server's sentence in `message`) answers it, a protocol error on its server while pending is its refusal, and a connection change ends the wait. `.UserUpdated` (`ServerUserUpdated`, the full `UserSummary` with `isAdmin` and `isBanned`) replaces the account's directory entry in place through `State_userUpdated`, which takes the event's nickname, and renames its conversation summary. The screens that use them are under Admin UI.
- The form never edits the room list itself. `ServerCreateRoom` becomes a `.RoomCreated` event (owned `room`), which `State_roomCreated` adds to the list, uses to close a Create form, and selects on the selected server; `RoomMembershipChanged` then refreshes the list. `.RoomEdited` and `.RoomDeleted` for the edited room close the form whoever sent them, so it never saves over a change it did not show. A protocol error on the form's server while a request is pending (`RoomEditor.pending`) is shown in the form; a connection change ends the wait. Switching rooms, servers, or opening a conversation closes the form.
- Delete needs two clicks (`confirmDelete`); deleting `#general` is allowed and the form says the server recreates it only when no rooms are left. A deleted selected room falls back to `#general` while it exists (`State_fallBackFromRemovedRoom`).
- Access modes in the form (protocol 15): `RoomEditor.access` (Create starts Public, Edit at the room's), `history` (Create only, fixed afterwards; Public shows Full) and `creatorJoins` (Create, on by default; always on for Public), set by `State_setRoomEditorAccess`, `State_setRoomEditorHistory`, `State_toggleRoomEditorCreatorJoins` and sent in `RoomAdminRequest`. `State_sendCreateRoom` defaults to Public, From join, joining; `State_sendEditRoom` requires the access like the type. `RoomEditorView` carries `access`/`accessNote`/`accessWarning` (an edit to Public adds everyone, away from Public removes nobody), `history`/`historyNote`/`historyLocked`, and the join toggle. `State_roomCreated(…, isMember)`: a non-public room created without joining goes into the admin room list (`State_noteAdminRoom`) and its Members page opens. The form scrolls (`RoomEditor.contentH`). Keep `ClientCreateRoomPayload` and the form open for E4's **Encrypt this room**: add fields, do not reuse these.

## Room Access and Members

- `room_members.odin` (protocol 15). `roomMemberRights(state, serverID, roomID)` is the one place for what the client offers, from the room's mode (`roomAccessShown`: an unknown mode counts as Public), its membership (the room list) and (protocol 23) ManageRoomMembers, which `RoomMemberRights.isAdmin` holds (`roomLogRights` likewise, plus `managesRooms` for SetAccess); "admins" below means holders of it: view the Members page (admins; members of non-public rooms), add (non-public, admins, or members of Member invite), remove (admins), leave (members of non-public rooms). The server checks every request again. `State_knownRoom` finds a room in the room list or, for admins, in `ServerRoomCache.adminRooms` (`ServerAdminRooms`, every room, requested by `State_requestAdminRooms` when Server settings opens; `State_roomEdited` and `State_roomDeleted` keep it current).
- The Members page is `RoomEditor` mode `.Members` (`State_openRoomMembers`; from a channel's **Members…**, the edit form's **Members…**, and the Admin section's **Members…**), so it shares the main pane, `pending`, and the closing rules; `State_roomEditorRoomChanged` keeps it open while `canView` holds and `State_roomEditorRoomDeleted` closes it. It fetches `ClientFetchRoomMembers` (`members`, `membersLoaded`), and `buildRoomMembersView` lists members and, when the account may add, the directory accounts that are not members (names from `ServerUserList`). `State_addRoomMember`, `State_removeRoomMember`, `State_leaveRoom` (with `checkRights`, which the harness turns off) and `State_fetchRoomMembers` send through `roomMemberSendBridge` (tests swap it under `roomMemberSendBridgeTestMutex`). `.RoomMemberResult` (`ServerRoomMemberAdded`/`Removed`) becomes the page's `notice`, or the chat status when the page is not showing that room (an invite from a menu). `.RoomMembershipChanged` carries the changed account in `peerUserID`: another account's change only refetches an open member list (`State_roomMembersChanged`), this account's changes the room list as before.
- Menus: a channel gets **Members…** (`canView`) and **Leave room…** (`canLeave`, two clicks: `ContextMenuState.confirmLeave`, "Click again to leave"); user menus get **Invite to room…** for someone else when `State_invitableRooms` is not empty, which keeps the menu open with one **Invite to #room** entry per room (`ContextMenuState.inviteOpen`, action `InviteToRoomPick` with `ContextMenuEntry.roomID`; the view keys them `CONTEXT_MENU_ROOM_KEY_BASE + roomID` and passes the room ID to `State_runContextMenuAction`).
- Widget IDs: `room-access N`, `room-history N`, `room-editor-join`, `room-editor-members`; on the Members page `room-members-add` and `room-members-remove` (server, room, user ID), `room-members-leave`, `room-members-edit`, `room-members-close` (server, room ID); in the Admin section `admin-room-members`.
- Tests: `room_members_test.odin` (rights per mode, the page through the bridge, menus, the create form's fields, a room created without joining, the Admin room list, the harness commands).

## Admin UI

- `admin_ui.odin` (plan P4) holds the admin's controls; `view_server_settings.odin` draws them. The section shows while `State_hasAdminSection` (an admin, or a holder of a delegable permission, protocol 23): accounts, their controls and Roles only for admins (`AdminSectionView.showMembers`/`showRoles`), the room list for ManageRooms or ManageRoomMembers (`showRooms`; Members… needs `canManageRoomMembers`, Create/Edit/Delete `canManageRooms`, disabled with a reason otherwise). Every request still goes through the actions in `admin.odin`, so the server checks the role, the permissions and the guards.
- `buildAdminUserControls(state, serverID, userID)` is the one place for what the server refuses (plan decision D6), from the account's directory entry (`UserSummary.isAdmin`/`isBanned`): Rename… always; Make admin, disabled for a banned account, or Remove admin, disabled for yourself; Kick… and Ban… disabled for yourself and for another admin; Unban for a banned account. A disabled `AdminControl` carries the sentence (`ADMIN_REASON_*`) the Admin section shows as its tooltip. The last-admin guard needs no rule: an admin other than you is never the last one. The context menus and the Admin section both build from it.
- Server settings → Admin (`buildAdminSectionView`, `AdminSectionView` in `ServerSettingsView.admin`): every account of the directory, you included ("(you)"), sorted by name only (so rows do not move when an account goes offline or is banned), with an online dot, Admin and Banned badges and the four controls; the server's answer to the last request (`State.adminRequest`: "Waiting for the server…", the `ServerAdminActionResult` sentence, or the refusal) as `status`, drawn under the row of `statusUserID` so it is where the admin is looking (above the table when that account is not listed); and the rooms with their type (`roomTypeLabel`), every room from `ServerRoomCache.adminRooms` once it arrived (joined ones until then), with its access mode, whether the admin is in it and its member count (`AdminRoomRow.accessLabel`), Members… (`State_openRoomMembers`), Edit… (`State_openRoomEditor`, which also opens a room the admin is not in), Delete… (`State_openRoomEditorForDelete`, the form with its delete armed, shared with the channel menu) and Create room… (`State_openRoomCreator`).
- Actions that need input open an inline confirmation under the member (`ServerSettingsForm.adminConfirm`, an `AdminConfirm` with an owned text buffer): Rename (new name, empty changes only the lock; Lock name starts on, `State_toggleAdminConfirmLock`), Kick and Ban (optional reason). `State_openAdminConfirm(state, serverID, kind, userID)` opens Server settings on that server first unless it is already shown there, and sets `scrollTo`, so the view scrolls the member's row and the confirmation into view (`adminScrollIntoView`, through `ui.scrollState(...).pendingDelta`, until they are visible or the area cannot scroll further). `State_submitAdminConfirm` sends and closes it; a request that cannot go out (a local check, not connected) stays open with the reason as the status (`State_adminRequestFailed`). Make admin / Remove admin (`State_adminSetRole`) and Unban (`State_adminUnban`) act at once. Each action re-checks the controls, so a disabled one never sends. Opening the screen forgets an old answer (`State_clearAdminRequestStatus`); closing it drops the confirmation.
- A refusal of a request sent from a menu (with the screen closed) shows where every protocol error does, as the chat status under the composer.
- Roles (protocol 23): each account row shows "Roles: …" (`AdminMemberRow.roleNames`, `State_userRoleNames`, the admin role left out) and **Roles…** (`rolesControl`, disabled until a role other than admin exists), which opens a checkbox per role under the row (`ServerSettingsForm.memberRolesUserID`, `State_openMemberRoles`, `State_toggleMemberRole` sends the whole new set). Under the accounts, **Roles** lists every role (`buildAdminRoleRows`: name, `serverPermissionsSummary`, holders), **New role…** and **Edit…** open the role form (`ServerSettingsForm.roleEditor`, `RoleEditorForm`, `buildRoleEditorView`): name, a checkbox per `SERVER_PERMISSIONS_ASSIGNABLE` permission (`State_toggleRoleEditorPermission`), Create/Save (`State_submitRoleEditor`), Delete… twice (`State_deleteRoleEditorRole`) and Cancel; the built-in role's form is read-only.
- Widget IDs (server ID, then user or room ID): `admin-member-rename`, `admin-member-role`, `admin-member-kick`, `admin-member-ban` (Ban… or Unban), `admin-confirm-text`, `admin-confirm-lock`, `admin-confirm`, `admin-confirm-cancel`, `admin-room-edit`, `admin-room-delete`, `admin-room-create` (server ID only); roles: `admin-member-roles`, `admin-member-role-toggle` (server, user, role ID), `admin-member-roles-close`, `admin-role-new` (server ID), `admin-role-edit` (server, role ID), `admin-role-name`, `admin-role-permission` (server, role ID, `ServerPermission` value), `admin-role-save`, `admin-role-delete`, `admin-role-cancel` (server, role ID; 0 for a new role).
- Tests: `admin_ui_test.odin` (the D6 controls, the section only for admins and gone with the role, every confirmation and direct action through `adminSendBridge` under `adminSendBridgeTestMutex` and what is never sent, the status, the room type selector through `roomAdminSendBridge`, voice-only and text-only room views, the locked Profile name), `context_menu_test.odin` (the admin entries per target and role, their actions, the participant menu's mute and volume, the rail's Server settings), `voice_state_test.odin` (a kick or ban clears the voice re-join). `dev/ui-smoke.sh` step 7 (see `docs/testing-harness.md`).

## Roles

- `roles.odin` (protocol 23, #95). The account's effective permissions are `ServerConnection.permissions`, set from `Connected` (`ServerAuthSuccess.permissions`) and `.AccountUpdated` and cleared on every connection change; read them with `State_serverPermissions`/`State_hasPermission` (an admin holds `SERVER_PERMISSIONS_ALL` whatever was sent) and `State_hasAdminSection`. They only decide which controls are drawn: gate new controls on the permission the server checks, not on `isAdmin` (R2 and G1: CreateInvites, ApproveRegistrations, room permissions). `State_accountUpdated` closes a room Create/Edit form when ManageRooms went away and the role controls when the admin role did.
- `ServerRoleCache` (`State.serverRoles`) holds each server's roles, by position then ID. `State_rolesConnected` asks for them after every `Connected` (`ClientAdminListRoles`, any account, through `roleListSendBridge`); `.RoleListReceived`, `.RoleUpdated` and `.RoleDeleted` keep it current (`State_receiveRoleList`, `State_roleUpdated`, `State_roleDeleted`, which also drops the ID from every directory entry's `roleIds`, since the server sends no `ServerUserUpdated` for a deleted role's holders). `UserSummary.roleIds` is owned: free directory entries with `common.UserSummary_deinit` (`UserSummaries_deinit`), and `State_userUpdated` frees the old entry's.
- Role actions are admin actions (`admin.odin`: `State_sendAdminSaveRole`, `State_sendAdminDeleteRole`, `State_sendAdminSetUserRoles`, `AdminRequest.roleID`/`roleName`/`permissions`/`position`/`roleIDs[:roleIDCount]`, a fixed array so the request stays comparable), so they share `adminSendBridge`, `validateAdminRequest` (`common.roleNameIsValid`) and the Admin section's status; `.AdminActionResult` carries `roleID`.
- Menus: Member, Conversation, Sender and Voice participant menus show a disabled "Roles: …" line (`ContextMenuAction.RoleNames`) to everyone, and admins get **Roles…** (`MemberRoles`, `State_openMemberRoles`) once a role other than admin exists.
- Headless (`headless_roles.odin`): `roles-list`, `roles-save ROLE_ID PERMISSIONS|none NAME...`, `roles-delete ROLE_ID`, `roles-assign USER_ID ROLE_IDS|none` and the `role_list`, `role_updated`, `role_deleted` events; `connected`, `status` and `account_updated` carry `permissions` (words in `HEADLESS_PERMISSION_NAMES`), `users`, `user_list` and `user_updated` carry `roleIds`, and `admin_result` carries `roleID`.
- Tests: `roles_test.odin` (permissions from sign-in and updates and the controls they gate, the role cache and its fan-outs, the Admin section per permission, the role form and member picker through `adminSendBridge`, the menu entries, the harness parsing and events).

## Room Permissions

- `room_permissions.odin` (protocol 24, #96). `RoomSummary.myPermissions` is this account's set in a room, from `ServerListRooms`, `ServerAdminRooms` and the creator's `ServerCreateRoom`; `State_roomEdited` keeps it across `ServerEditRoom`, which carries none. Read it with `State_roomPermissions`/`State_hasRoomPermission`, which add what server permissions imply (ManageRoomMembers: ManageMembers, ManageRooms: EditRoom, an admin: every one) and read an unknown room as `ROOM_PERMISSIONS_DEFAULT`. The server resends the room list whenever the set can change, so nothing here polls.
- Gates: without SendMessages `buildRoomView` replaces the composer with `ROOM_SEND_NOT_PERMITTED_NOTE` and `State_sendChannelChat` refuses locally (the harness passes `checkPermission = false` so the server's refusal shows). ## Direct Messages

- `direct_messages.odin` holds the per-server direct-message state (`State.serverDirectCaches`, one `ServerDirectCache` per server): the user directory (`users`, every account including yourself, `isOnline` updated in place by `ServerUserPresence`), the conversation list (`conversations`, most recent first), and one `DirectConversationCache` per peer. Cache identity is `(serverID, peerUserID)`: user IDs overlap between servers exactly like room IDs.
- Never append a sent direct message locally. `State_sendDirectMessageTo` only sends the draft and clears it when the transport accepted it; the message enters the cache when the server's `ServerDirectMessage` echo arrives (to every session of both users), carrying the stored ID and timestamp. The conversation's peer is the recipient when you are the sender, otherwise the sender (`directMessagePeerUserID`).
- Messages merge by ID (`DirectConversationCache_mergeEntry`), so overlapping history pages and live echoes never duplicate. Cursor 0 fetches the newest page and older pages use `oldestMessageID`, like rooms. Only a page that reaches the oldest loaded message may change `hasOlder`, so reloading the newest page after a reconnect does not bring back "Load older".
- Every new message moves its conversation to the top of `conversations`, adding it when missing (`ServerDirectCache_noteLatestMessage` keeps the summary's read state). Unread counts are the server's; see Read State.
- The open conversation is `State.selected_dm_peer_id` on the selected server, kept apart from `selected_channel_id`: opening a conversation leaves the room selection alone, clicking a channel sets the peer back to 0, and switching servers or rebuilding a server's transport closes it.
- `Connected` requests the room list, then the user list and the conversation list, and the open conversation's newest page. `State_resetDirectRequests` clears the loading flags on every connection change and marks conversations for reload on a new session. `State_receiveUserList` and `State_receiveDirectConversations` take ownership of the event's arrays; presence for an unknown account takes the event's nickname. The server announces a rename as presence, so `State_userPresenceChanged` also replaces a known account's nickname in `users` and in its `conversations` summary when the event's differs; cached messages keep the `senderNickname` they were stored with, and a history fetch brings the current name.
- Cached messages are `DirectMessageEntry` (`using message: common.StoredDirectMessage` plus `security`) and conversation summaries `DirectConversationEntry` (`using summary` plus the preview's `security`); `content`/`lastContent` hold the opened text and are wiped (`wipeString`) before they are freed. Merge with `DirectConversationCache_mergeEntry` (takes ownership).
- The sidebar is built by `buildSidebarRows` (channels, Direct Messages, Members) and the DM pane by `buildDirectConversationView`, both in `view_model.odin`; `view_direct.odin` draws the pane. Test DM logic through the actions and view models (`direct_messages_test.odin`), swapping `directMessageSendBridge` under `directMessageSendBridgeTestMutex` when a test needs to observe a send.

## Voice Engine

- `client/opus` is a libopus binding loaded at runtime with `core:dynlib` (`libopus.so.0`; on Windows `libopus-0.dll` next to the executable first). Like `client/ui` it must not import HayChat types. `opus.load()` is process-wide, idempotent and thread safe; when it fails, `opus.loadError()` says why and the client keeps working for chat. Never `foreign import` libopus: nothing about voice may stop the client from starting.
- `VoiceEngine` (`voice_engine.odin`) runs capture → gate (`voice_gate.odin`) → Opus encode → outbound, and inbound → per-speaker `JitterBuffer` (`voice_jitter.odin`) → decode with FEC/PLC → sink, on its own thread. Sources: SDL recording device, raw F32LE mono 48 kHz file, tone, silence. Sinks: SDL playback device (one `SDL_AudioStream` per remote speaker bound to one logical device, so SDL mixes and per-speaker gain is stream gain), raw F32LE file (all speakers mixed, silence written while nobody speaks), null.
- Threads: `VoiceEngine_start` opens the codec, source and sink on the calling thread (errors come back from it, see `VoiceEngine_lastError`) and then starts the voice thread; `VoiceEngine_stop` joins it and closes everything. While it runs the voice thread alone owns the codec, gate, jitter buffers, SDL streams and sink file. Other threads only use the atomic controls (`VoiceEngine_setMuted`, `setPushToTalk`, `setGateMode`, `setVADThreshold`, `setInputGain`, `setOutputVolume`, `setBitrate`; the voice thread applies the bitrate with `OPUS_SET_BITRATE` and the volume as the playback device's gain, or to a file or null sink's mix, at the start of its next step), the per-speaker controls (below), `VoiceEngine_pushInbound`, `VoiceEngine_inputLevel` (lock-free meter) and `VoiceEngine_snapshot` (counters and per-speaker state, copied under a mutex once per step). The UI thread never touches audio streams itself.
- Per-speaker gain and local mute (issue 47): `VoiceEngine_setSpeakerControl(engine, userID, gain, muted)` (and `setSpeakerGain`, `setSpeakerMuted`; `VoiceEngine_speakerControl` reads one back) write a fixed table of `VOICE_SPEAKER_CONTROL_CAPACITY` (256) entries under `speakerControlMutex`, holding only non-default entries (gain 1 and not muted removes one; gains are clamped to 0..`VOICE_SPEAKER_GAIN_MAX`, 2), and bump an atomic version. At the start of a step the voice thread copies the table into its own `appliedControls` when the version moved (no allocation, no lock afterwards), sets each active speaker's `gain` (its SDL stream's gain with `SDL_SetAudioStreamGain` on a device sink; the file and null mix multiply by it) and releases a speaker that became muted, so nothing buffered plays. A muted speaker's frames are dropped in `VoiceEngine_deliverInbound`, before a decoder or stream exists, and counted in `stats.inboundLocallyMuted` (with what a released speaker still had buffered). A new speaker takes its gain when it is created. `VoiceSpeakerSnapshot.gain` reports it. The output volume still applies on top.
- Seams for networking (used by H5, see Voice Rooms): `VoiceEngineConfig.onOutbound` is called on the voice thread with each encoded frame (`frameSequence`, flags, Opus bytes borrowed for the call). `VoiceEngine_pushInbound(engine, senderUserID, frameSequence, flags, opus)` copies a received frame into a bounded ring (oldest dropped when full) under its own mutex, from any thread; it refuses frames while the engine is not open or is deafened. Voice frames never become runtime events.
- `VoiceEngine_setDeafened` stops playback at once: `pushInbound` refuses frames and the next step discards the queue and releases every speaker (`stats.inboundDeafened` counts both).
- `VoiceEngineConfig.inputGain`, `outputVolume` and `vadThresholdDB` treat 0 as "the default" unless `explicitLevels` is set, which configs built from the user's settings (`voiceEngineConfigWithSettings`) always set, because 0 is a valid gain and threshold there. `VoiceEngine_usedDeviceFallback` says whether the last open fell back to the default device because a named one was missing.
- Frame constants come from `common` (`VOICE_SAMPLE_RATE`, `VOICE_FRAME_SAMPLES`, `VOICE_OPUS_MAX_BYTES`, `VOICE_FRAME_FLAG_*`); the client keeps only derived ones such as `VOICE_FRAME_BYTES`.
- `frameSequence` advances on every 20 ms capture tick, gated or not, so receivers can tell silence from loss. The last frame of a talk spurt carries `common.VOICE_FRAME_FLAG_END_OF_SPURT`; mute closes the gate without one, and receivers end the spurt by timeout. A new engine starts at `config.resumeSequence` plus the 20 ms ticks since `config.resumeSequenceAt` (rounded up); `State_voiceRestartEngine` passes the stopped engine's `VoiceEngine_nextSequence`, so listeners still in its spurt keep their place instead of dropping the new frames as late.
- Jitter buffer edges: the end of a spurt drops only that spurt's frames; frames already queued after the END_OF_SPURT frame (a quick push-to-talk re-press) start the next spurt at once and keep the playout position, with the skipped ticks as pre-roll silence. A transit step larger than the ring (`JITTER_CLOCK_STEP_MS`, 640 ms: a sender whose sequence started over, or a receiver clock jump) resets the transit baseline instead of counting as jitter. `stats.maxGapRun` is the longest run inside a spurt heard as neither decoded nor FEC-rebuilt.
- Measurement hooks: `VoiceEngineConfig.onFrameTiming` reports each encoded frame (speaker 0) and each normally decoded received frame on the monotonic clock, on the voice thread (the live voice test uses it for encode-to-playout latency); `VoiceEngineStats.playoutDelay*` sum each decoded frame's wait between arrival and decoding. A build with `-define:HAYCHAT_TEST_FAULTS=true` adds the receive fault hook of `voice_faults.odin` (`HAYCHAT_TEST_VOICE_LOSS`, `HAYCHAT_TEST_VOICE_JITTER_MS`, `HAYCHAT_TEST_VOICE_SEED`), applied in `VoiceEngine_drainInbound` and counted in `faultDropped`/`faultDelayed`; in a normal build `VoiceReceiveFaults` is an empty struct and every use sits under `when HAYCHAT_TEST_FAULTS`. `check.sh` runs its unit test in a faults build.
- No allocation per frame on the voice thread: every buffer lives in the `VoiceEngine` allocated by `VoiceEngine_create`. Opus decoders and SDL speaker streams are created per speaker (on its first frame) and released when it has been idle for 10 s or the engine closes.
- SDL's audio subsystem is initialised (`SDL.InitSubSystem({.AUDIO})`) only when a device source or sink opens, and quit on close, so the headless harness and the tests never initialise SDL otherwise. The engine sets the stream role and name hints at normal priority, so `SDL_AUDIO_*` environment variables (the `disk` driver) still win. Do not set `SDL_AUDIO_DEVICE_SAMPLE_FRAMES`: with 480 frames SDL 3.4's PipeWire capture lost over half its samples on a host with a 1024-frame minimum quantum.
- Loopback mode (`config.loopback`) feeds the encoder's output back through `VoiceEngine_pushInbound` as speaker `VOICE_LOOPBACK_USER_ID`; `config.loopbackFaults` drops and reorders frames deterministically. `config.unpaced` makes each `VoiceEngine_step` exactly one 20 ms frame each way, which is how the tests run the engine without a thread or a clock (`VoiceEngine_open`, `VoiceEngine_step`, `VoiceEngine_close`). `client --voice-loopback` (`voice_loopback.odin`, see `docs/testing-harness.md`) runs it by hand.
- File sink flush: `VoiceEngine_requestSinkFlush` (any thread) returns a ticket and `VoiceEngine_sinkFlushCompleted` reaches it once the voice thread has played out and flushed the file on its next step (writes are unbuffered; the ticket is the guarantee that every frame played before the request is in the file). The headless `voice-flush` uses it. Source and sink specs (`device[:NAME]`, `tone:HZ[:AMP]`, `file:PATH`, `silence`; `device[:NAME]`, `file:PATH`, `null`) are parsed by `voiceParseSourceSpec` / `voiceParseSinkSpec` (`voice_spec.odin`) for both `--voice-loopback` and the harness.
- Tests (`voice_test.odin`, `voice_jitter_test.odin`) need libopus for the codec and engine cases and skip with a warning without it, unless `HAYCHAT_REQUIRE_OPUS=1` (set by `check.sh`, so CI never skips). `voice_analysis.odin` names the Goertzel tone check they use, which lives in the `client/toneanalysis` package (no HayChat types, tested by `odin test client/toneanalysis`) so `dev/tools/voice-check` shares it. Only `testVoiceEngineDevicePathWithTheDiskDriver` initialises SDL audio, under its own mutex, and it resets every hint it sets; keep any new SDL audio test inside that test or behind the same mutex.

## Voice Rooms

- `voice_state.odin` holds `State.voice` (`ClientVoiceState`): `status` (`Idle`, `Joining`, `Joined`, `Unavailable`), `serverID` and `roomID` (voice is active on at most one server), `muted`, `deafened`, `pushToTalkHeld`, an owned `lastError`, `roomParticipants` (the server's last list for every room with anyone in voice, joined or not, keyed by `(serverID, roomID)`; read with `State_voiceRoomParticipants`), `wantVoiceRoomID` for the re-join, the running `engine` and its `link`, and `engineTemplate`, the `VoiceEngineConfig` every new engine starts from (`State_setVoiceEngineTemplate` clones its strings). The GUI default is device source and sink with voice activity; the headless harness uses silence and null; tests swap in tone, file, silence and null.
- Actions: `State_joinVoice(state, serverID, roomID)` leaves any current voice first, checks libopus (`Unavailable` without it, nothing sent), sends `ClientJoinVoice{roomID, muted, deafened, rejoin = false, deviceID}` and waits in `Joining`; the re-join in `State_voiceConnected` sends `rejoin = true` (protocol 13: the server lets it replace only this device's stale session, never another device's). `deviceID` is `State.config.device_id`. Only a `ServerVoiceParticipants` for that room that lists this account's user ID moves it to `Joined`, which creates and starts the engine. `State_leaveVoice` sends `ClientLeaveVoice`, stops the engine and clears the want. `State_setVoiceMuted` / `State_setVoiceDeafened` update the engine's gate or playback at once and then send `ClientVoiceState`; `State_setVoicePushToTalk` is local only. Control messages go through `voiceControlSendBridge` (tests swap it under `voiceControlSendBridgeTestMutex`).
- Events: `.VoiceParticipants` (owned `voiceParticipants`, taken by `State_receiveVoiceParticipants`; an empty list removes the room; `voiceRecipientJoined` is the server's per-session flag, and only a list with it set completes a join, since a list that merely names this user may be about another device; a list without it never ends a joined session, which only `ServerVoiceLeft` does), `.VoiceJoinRejected` and `.VoiceLeft` (roomID plus the reason in `message`, taken into `lastError`). A rejection of the room being joined (even one that already counts as Joined, after a quick leave and re-join; this includes "voice is active on another device" for a re-join), a `VoiceLeft` for the joined room (including "joined voice on another device" when another device of the account took voice over), a deleted room, and leaving a room's membership all end voice and clear the want; the server sends `ServerVoiceLeft` before `ServerDeleteRoom`. A kick or ban (`ConnectFailed` or `SessionEnded` with `failureKind` `.Kicked` or `.Banned`) also clears it (`State_voiceEndedByAdmin`), so the reconnect that Retry starts later does not join voice by itself.
- Connection lifecycle: `Disconnected` or `ConnectFailed` on the voice server stops the engine, drops that server's participant lists and goes to `Idle`, keeping `serverID` and `wantVoiceRoomID`; the next `Connected` re-joins (`State_voiceConnected`). If the engine cannot start (libopus, a device, a file), voice becomes `Unavailable` with `VoiceEngine_lastError`, the server is told to drop the session from voice, and chat is untouched. `State_reconfigureNetwork` leaves and stops voice before the transports are rebuilt (`State_voiceSuspendForReconfigure`) and joins again afterwards when the session survived; `State_deinit` stops the engine before the worker.
- The engine pointer is shared with two other threads through `ClientServerTransport.voice` (`ClientTransportVoiceBinding{engine, roomID, sessionGeneration}`), which only the UI thread writes, always under `ClientNetworkWorker_lock`. The rule: **bind after the engine started, and clear the binding under the lock before stopping and destroying the engine** (`State_voiceStopEngine`); the `ClientVoiceLink` the voice thread sends through is freed only after `VoiceEngine_destroy` has joined that thread. The worker and the voice thread use the engine only while holding the lock and only through a live binding, so they never see a freed one.
- A binding belongs to one session: `ClientServerTransport.sessionGeneration` goes up on every `Connected` (which carries it, mirrored in `ServerConnection.sessionGeneration`), and the binding is live only while it matches and the session is established (`ClientServerTransport_voiceBindingIsLive`). A frame captured just before a leave, a room switch or a reconnect is therefore dropped rather than sent into a session that has not joined voice, and a stale participant list processed late cannot make a new session play or send.
- Receive (`voice_network.odin`, network worker, lock held): an established session's channel 2 packet goes through `common.openVoiceDatagram` into a stack scratch buffer, `common.decodeServerVoiceFrame`, a room and binding check, then `VoiceEngine_pushInbound`, which copies the Opus bytes. `ClientServerTransport_serviceEstablishedSession` handles up to `CLIENT_VOICE_DATAGRAMS_PER_SERVICE` datagrams in a row before returning, so voice never holds up the control packets behind it, never queues an event and never wakes the UI loop. Every drop is counted by reason in `ClientServerTransport.voiceStats` (`ClientVoiceReceiveDropReason`), and none ends the session.
- Send (voice thread): the engine's `onOutbound` is `clientVoiceOutbound`, which takes the worker lock and calls `ClientServerTransport_sendVoiceFrame`: binding check, `common.encodeClientVoiceFrame` into the link's buffer, `common.sealVoiceDatagram` with the session's `voiceSend`, then `voiceDatagramSendBridge` (`ENet.peer_send` on channel 2 with `UNSEQUENCED` and a `host_flush`; tests swap it under `voiceDatagramSendBridgeTestMutex`). Drops are counted in `voiceStats.sendDropped`; a failed send never touches the control channel. Nothing on either path allocates.
- Tests: `voice_state_test.odin` (actions against the stubbed bridge, with real quiet engines, including the `rejoin` flag and device ID on manual and automatic joins and the takeover and other-device reasons), `voice_network_test.odin` (receive and send paths against a server-side `TransportState`, and the established-session loop over a loopback ENet connection), and the gated live proof `voice_live_test.odin` (`testClientVoiceLiveToneReachesSecondClientThroughServer`: a 440 Hz tone from A through the real server relay into B's file sink, checked with `voice_analysis.odin`; part of `dev/live-proof.sh --all`).

## Voice UI and Settings

- `device_id` (`config.odin`, protocol 13): the profile's voice device ID, 32 lowercase hex characters from `common.generateVoiceDeviceID`. `loadConfig` calls `ensureDeviceID` after the identity keys and saves a new one when it was missing or malformed (deleting the key resets it); `State_initFromConfig` gives a config built in code one for that run. A copied profile directory keeps the same ID. Do not log it.
- Config keys (`config.odin`, read through `Config_voiceSettings` in `voice_settings.odin`): `voice_input_device`, `voice_output_device`, `voice_mode`, `voice_ptt_key` (strings, `""` is the default), `voice_ptt_global` (`Maybe(bool)`, default true) and `voice_vad_threshold_db`, `voice_input_gain`, `voice_output_volume`, `voice_bitrate` (`Maybe` numbers, so 0 is not "unset"). All are `omitempty`; `Config_setVoiceSettings` stores a value equal to its default as unset, so a later change of a default reaches users who never chose. `voiceSettingsValidate` clamps numbers (−80..0 dBFS, gain 0..4, volume 0..2, 12000..64000 bit/s) and replaces invalid strings with the default.
- The engine template is built from them: `State_initFromConfig` uses `voiceDefaultEngineTemplate` (device source and sink), and `State_applyVoiceSettings` replaces only the settings part of the current template (device names, mode, levels, bitrate, `explicitLevels`), keeping its source and sink kinds, so tests and the harness that run on tones and null sinks keep them. It stores the settings in the config (saving it when `persist`; sliders pass false while dragging and save on release), then reapplies them: in place on the joined engine and the microphone test (`VoiceEngine_applySettings`), or, for a new input or output device, by `State_voiceRestartEngine`, which stops and starts the engine and rebinds it while the session stays `Joined` and the server hears nothing. A failed reopen becomes `Unavailable` exactly like a failed join.
- `State.voicePanel` (`VoiceSettingsPanel`) is the Settings → Voice section: `viewApp` calls `State_setVoiceSettingsVisible` every frame, which takes its own reference on SDL's audio subsystem and lists device names only while the section is shown (a failed `InitSubSystem` is shown as a note, and the lists offer only "System default"), and stops the microphone test when it is hidden. The test (`State_startVoiceTest`) is a loopback engine from the template; it is refused while an engine runs, and `State_voiceSettingsFrame` stops it as soon as voice is joining or joined. `AUDIO_DEVICE_ADDED`/`REMOVED` events call `State_voiceAudioDevicesChanged`, which refreshes the lists and reopens an engine whose named device went away or came back (`voiceDevicesNeedReopen`).
- Push-to-talk (`app.odin`, `appHandleVoiceEvent`): the configured key's `KEY_DOWN`/`KEY_UP` (no repeats, not while capturing a key) go through `voicePushToTalkKeyEvent` and set `state.voice.pushToTalkWindowHeld`; `WINDOW_FOCUS_LOST` clears it. After every event batch the loop calls `State_voiceSyncPushToTalk`, which combines it with the global monitor (`voicePushToTalkCombined`) and calls `State_voicePushToTalkChanged` on a change, which drives the joined engine and the test. The harness and tests call `State_setVoicePushToTalk` / `State_voicePushToTalkChanged` directly.
- Global push-to-talk (issue 45, `client/hotkey`, its own package with no HayChat types and every system library loaded with `core:dynlib`, like `client/opus`): `runApp` creates `state.voice.globalPushToTalk` with `hotkey.defaultBackend()` (Windows: `GetAsyncKeyState` polling; Linux: the GlobalShortcuts portal when `WAYLAND_DISPLAY` is set, else `XQueryKeymap` polling when `DISPLAY` is set; a UI script gets `.None`), waking the loop through `appWakeFromWorker`; `State_deinit` destroys it before anything else. `State_voiceSyncPushToTalk` sets its key every pass and arms it only in push-to-talk mode with `voice_ptt_global` on and `State_voicePushToTalkInUse` (joining, joined, or the microphone test): disarmed, the polling backends read nothing and the portal sets up nothing, so the desktop's dialog appears only on the first push-to-talk use in voice. The portal keeps its session for the monitor's life; the desktop owns its trigger (`StatusReport.trigger`), and `State_configureGlobalPushToTalk` opens its dialog (portal version 2). A held global key that types is ignored while HayChat has focus and a text field is focused. The monitor's `StatusReport`, copied into `state.voice.globalReport` by the sync (which asks for a frame when it changes while the section is shown), drives `voicePushToTalkNotice`, the `voice-ptt-global` toggle and the `voice-ptt-shortcut` button. `client/hotkey/hotkey_linux_test.odin` runs the X11 poller on Xvfb with XTest and the portal client against a mock portal on a private `dbus-daemon`; they skip without those unless `HAYCHAT_REQUIRE_HOTKEY_TESTS=1` (set by `check.sh`). `client/dbus` is not used: it links libdbus-1 at build time. A key that edits text (`voiceKeyEditsText`: SDL keycodes without `SDLK_SCANCODE_MASK`, i.e. characters, Space, Enter, Tab, Backspace, Delete, Esc) does not press push-to-talk while a text field had focus in the last frame (`ui.hasTextFocus`); a key up always releases. The settings note (`VoiceSettingsView.pttNotice`) says so when the chosen key types. Leaving push-to-talk mode releases a held key. The key is an SDL key name resolved with `SDL_GetKeyFromName` on each key event; key capture in the section takes the next key press's `SDL_GetKeyName`, Esc cancels.
- Redraws: while `State_voiceNeedsRedraws` (joined, or the test running) the frame loop wakes every `VOICE_REDRAW_INTERVAL_MS` (100 ms) and `State_voiceRedrawDue` asks for a frame only when `State_voiceVisualKey` (meter level in whole dB within the meter's range, transmitting, who speaks) differs from `state.voice.drawnVisual`, which `viewApp` records each frame. An idle joined window renders nothing (about 0.55 % of a core offscreen, against 5.1 % for a frame every 100 ms). Anything new the voice UI draws from the engine without an event must go into the key.
- View models (`voice_view_model.odin`): `buildVoiceParticipantRows` makes one row per user in the server's order (the server lists each user once since protocol 13; a repeated user ID keeps its first entry as a defence), with speaking taken from `VoiceEngine_snapshot` speakers and this client's own gate, only for the room this client is joined to; `buildSidebarRows` puts them under each Channel row as `.VoiceParticipant` rows and sets `voiceUsers` on the Channel. `roomVoiceHeaderAction` (Join, or Leave while joining, joined or re-joining that room), `buildVoiceBarView` (`Joined`, `Joining`, `Rejoining` = Idle with a want, `Unavailable`, `Notice` = an error after a refusal, cleared by Dismiss through `State_leaveVoice`), and `buildVoiceSettingsView`. `view_voice.odin` draws them; widget IDs for automation: `room-voice SERVER ROOM`, `voice-mute`, `voice-deafen`, `voice-leave`, `voice-dismiss`, `voice-test`, `voice-mode-vad`, `voice-mode-ptt`, `voice-ptt-key`, `voice-ptt-global`, `voice-ptt-shortcut`, `settings-tab N` (0 General, 1 Voice).
- `client/ui/meter.odin` holds the generic `ui.levelMeter` and `ui.slider` (with the pure `ui.rangeFraction` and `ui.sliderValueAt`, tested in `client/ui`); callers map decibels and gains onto them.
- Tests: `voice_ui_test.odin` (sidebar rows, speaking, header action, every voice bar state, settings → config → template, reapplying to the joined engine and the test, key capture, device options, hotplug decisions, and the engine's gain, volume and bitrate), `config_test.odin` (defaults, validation, round trip, and the device ID generated once and kept across a save and a load). `dev/ui-smoke.sh` joins voice from the GUI on SDL's dummy audio driver, mutes, opens Settings → Voice while joined, and leaves, while a headless bob checks the participant lists.

## Read State

- `read_state.odin` holds it (protocol 11). The server's marker and count for a room live in its `common.RoomSummary` in `ServerRoomCache.rooms` (from `ServerListRooms`), and for a direct conversation in its `common.DirectConversationSummary` in `ServerDirectCache.conversations`. Replacing a list replaces them; `State_roomEdited` keeps the room's (`ServerEditRoom` carries zeros), and `State_roomCreated` starts at zero. `RoomCache.readSend` and `DirectConversationCache.readSend` only record the last mark-read that went out.
- Counting: a live `ServerChatMessage` or `ServerDirectMessage` (one that `RoomCache_mergeMessage` / `ServerDirectCache_noteLatestMessage` reports as new) adds one when `readStateCountsMessage` agrees: from someone else, ID above the marker, and the conversation not viewed. Capped at `common.UNREAD_COUNT_CAP`; the sidebar shows `unreadBadgeText` ("99+" from 100). History pages never count. The client never lowers a count itself.
- "Viewed" (`State_isConversationViewed`) is: selected on the selected server (a room only while no conversation is open), `State.windowFocused`, no settings screen, no Server settings, no room editor. Only `runApp` sets `windowFocused` (from SDL focus events; always true under a UI script), so tests and the headless harness view nothing unless they set it.
- Marking: `State_updateReadMarkers(state, now)` sends `ClientMarkRead` for the viewed conversation up to its newest loaded message ID when that is above both the marker and `readSend.sentMessageID`, at most once per `READ_MARKER_MIN_INTERVAL` per conversation (a failed send waits too); it returns how long a held mark waits, which the frame loop folds into its event timeout. `runApp` calls it once per loop iteration, after the events and the frame. The headless `read` command calls `State_markConversationRead` directly. Sends go through `readMarkerSendBridge` (tests swap it under `readMarkerSendBridgeTestMutex`).
- `ServerReadMarker` (`.ReadMarkerReceived`, no owned fields) goes through `State_receiveReadMarker`, which takes the marker and count when the marker is not older than the one held. It reaches every session of the account, the one that asked included, so reading on one device clears the badge on another. `State_resetPendingRequests` clears `readSend` on every connection change.

## Encryption Keys

- Protocol 16, design sections 2-3: the key layer that encrypted direct messages (protocol 17, below) and later rooms build on.
- Config (`config.odin`): `encryption_private_key`, `encryption_public_key`, `encryption_key_signature`, `encryption_key_created_at`. `loadConfig` calls `ensureEncryptionKey` after `ensureIdentityKeys` and saves a new key when the old one is missing, unparsable, not the private key's, or not signed by the current identity key; `State_initFromConfig` gives a config built in code one for that run. `Config_encryptionKey` returns the key pair (wipe it) and the signed bundle, checking all of that again. `saveConfig` writes through `writeFileAtomically` (`PATH.tmp`, mode 0600, rename). Never print the private key.
- Key store (`keystore.odin`, design 3.3): one `KeyStore` per server, `State.keyStoreDir/<pinned server fingerprint>.json`; `keyStorePath` accepts only a 64-hex fingerprint. `State.keyStoreDir` is empty in tests (memory only); `init` and the headless harness set it to `keyStoreDefaultDir()` (`keys/` next to `config.json`). A file that does not parse, has an invalid entry, another server key, or a newer `format` loads read-only (`writable` false, `loadError`) and is never written. `direct_conversations` (format 2, protocol 17) holds the no-downgrade flags (`KeyStore_conversationEncrypted`, `KeyStore_markConversationEncrypted`); `rooms` (format 3, protocol 18) holds each encrypted room's verified member log head (`KeyStore_roomHead`, `KeyStore_setRoomHead`, forward only, never removed). `room_chains` (format 4, protocol 19) holds the sender chains this profile opened (`KeyStore_roomChain`, `KeyStore_addRoomChain`, first one kept; chain keys wiped on deinit, the file bytes wiped after reading and writing): a cache that `ClientFetchRoomKeys` rebuilds. Bump `KEY_STORE_FORMAT` when adding data an older client would drop on rewrite.
- State (`e2ee_state.odin`, `State.e2ee`, one `ServerE2EEState` per server): `State_e2eeConnected` (from `State_connectionEstablished`) loads the store for the server's current pin (a trusted new server key gets a new store), publishes the bundle once per session (`e2eePublishBridge`), and refetches every pinned user. `State_e2eeRequestUserKeys(state, serverID, userIDs)` batches by `common.USER_KEYS_FETCH_MAX`, skips yourself, repeats and users already being fetched (`e2eeFetchBridge`; tests swap both bridges under `e2eeSendBridgeTestMutex`, and record only their own server ID because every test's Connected publishes). Opening a direct conversation fetches the peer when its state is Unknown, and so does the Verify dialog.
- Trust (`e2eeEvaluateBundle`, pure): a bundle that fails `verifyEncryptionKeyBundle` or has no identity key is `Invalid`; with a pin, another identity key is `IdentityChanged` (status `Changed`, the verified bundle kept as `offered`, the pin untouched), the pinned encryption key is `Same`, a different one with a `createdAt` not newer than the pin's is `Rollback` (refused), a newer one `NewEncryptionKey` (pin updated, `verified` cleared, notice `KeySetUpAgain`); without a pin, a bundle whose identity key differs from the directory's is `Inconsistent` (refused), else `FirstUse` (pinned unverified). A requested user in `missingUserIds` is `NoBundle`. The directory (`ServerUserList`, `ServerUserUpdated`; never presence, which carries no keys) also counts: a pinned user listed under another identity key is `Changed` and fetched, a pinned user without a bundle `NoBundle`, an unpinned one `NotSetUp`. A pushed `ServerUserKeyChanged` is applied only to pinned users. Only `State_e2eeTrustNewKey` and `State_e2eeMarkVerified` (which in KeyChanged trusts the offered key and marks it verified) change a pin to another identity key.
- Query API for E2/E4: `State_e2eePeerKeyInfo(state, serverID, userID) -> E2EEPeerKeyInfo{state, canEncrypt, blockReason, hasPin, identityPublicKey, encryptionPublicKey, createdAt, verified, notice, hasOfferedKey}`. `canEncrypt` is true only for Unverified and Verified; `blockReason` is `Pending` (Unknown: call `State_e2eeRequestUserKeys` and wait for `.UserKeysReceived`), `NotSetUp`, `KeyChanged`, `NotProvided` (the three cases of design 4.6) or `InvalidKey`. The keys are the pin's; encrypt to and verify against those only. `e2eeKeyStateText(info, name)` gives the sentence, `State_e2eeSafetyNumber` the formatted number, `Config_encryptionKey` this profile's own keys.
- UI (`e2ee_view_model.odin`, `view_e2ee.odin`): `buildVerifyDialogView` (`State.verifyDialog`, opened by the user menus' **Verify encryption…** through `State_openVerifyDialog`; drawn by `viewVerifyDialog`, deferred in `viewApp` under the context menu), `buildE2EEKeyBanner` above a direct conversation (KeyChanged with Verify and Trust the new key, NotProvided and InvalidKey warnings, the set-up-again notice with Dismiss), and `SidebarRow.keyState` with `e2eeKeyIndicator` on Conversation and Member rows. Widget IDs: `verify-dialog`, `verify-mark`, `verify-close`, `key-banner-verify`, `key-banner-trust`, `key-banner-dismiss` (server ID, user ID).
- Harness: `user-keys`, `verify`, `trust-key`, the `user_keys` event (printed after the key event was applied, from State) and `keyState` on `users`, `user_list` and `user_updated` (`docs/testing-harness.md`, "Encryption Keys"). Tests: `e2ee_test.odin` (key store, verdicts, publish once per session, first use, key change and trust, new key with notice, rollback and bad signatures, missing bundles, directory changes, the dialog and safety number, batches), `config_test.odin` (the encryption key's generation and replacement). Live: `dev/e2ee-proof.sh` (`./dev.sh live --e2ee`) and `dev/ui-smoke.sh` step 9.

## Encrypted Direct Messages

- Protocol 17, design 4.5, 4.6, 7.2-7.4; `direct_messages_e2ee.odin` (pipeline), `direct_messages_view_model.odin` (badges, composer), `view_direct.odin` (drawing). Only pinned keys are used: `State_directOpenKeys` (server pin, own identity, own key pair from `Config_encryptionKey`, wiped with `DirectOpenKeys_wipe`) and `State_directIdentityFor` (own key for self, else the pin, else nil).
- Every message must be signed by its sender (#82): a message whose sender's signature was not verified against the pin (or this profile's own key) is never shown. Receiving: every message is opened once by `openDirectMessageContent` (pure) into a `DirectMessageSecurity`: `Encrypted`, `Signed` (verified plaintext), `Pending` (no pin yet: a placeholder, never the text, which is kept only to check it later), `Failed` ("could not be decrypted": `failure` OwnKey, Envelope with an `envelopeError` after the signature (`directEnvelopeSecurity`: NoWrapForRecipient, BadEphemeralKey, BadWrap, BadCiphertext, BadPadding, BadPlaintext), Replayed), or `Hidden` (`failure` Unsigned, BadSignature, NoKey, or Envelope with an error at or before the signature check). Without an encryption key of its own the client still checks an envelope's signature (`verifyDirectMessageEnvelope`) before settling it OwnKey. `directMessageShown` is false for Hidden: the transcript, the conversation list (`ServerDirectCache_noteLatestMessage` is skipped) and the unread count leave it out, and the harness prints it as `hidden` without content. `State_directEntryOpened` marks the conversation encrypted (`KeyStore_markConversationEncrypted`, saved) or fetches the missing key; `State_directKeysChanged` (after `.UserKeysReceived`, `.UserKeyChanged`, `State_e2eeTrustNewKey`, and Connected via `State_directRequestQueuedKeys`) reopens only `Pending` entries and previews, settling them Hidden (`DIRECT_SETTLED_WITHOUT_KEY`) when no key can come (`State_directKeyMayArrive`). A failure is never reopened. `DirectConversationCache_checkReplay` marks the later of two opened messages with the same sender and `clientMessageId` Replayed.
- Sending (`State_sendDirectMessageTo`, `directSendMode`): Encrypt when `canEncrypt` (`State_directSend` seals into a stack buffer it wipes); Queue while Pending (`DirectConversationCache.queued`, sent by `State_directFlushQueued` once the key arrives, or put back into the draft, never as plaintext); Plaintext only with `fallbackOn`; otherwise Blocked with `e2eeKeyStateText`. Sends go through `directMessageSendBridge` with a `DirectMessageSend` (tests swap it under `directMessageSendBridgeTestMutex`).
- Fallback switch: `State_setDirectFallback` (`.NeedsConfirmation` the first time per conversation and run, `.Unavailable` unless `directFallbackAvailable`), `State_confirmDirectFallback`, `State_cancelDirectFallback`. It lives only in memory and turns off in `State_closeDirectConversation` (every place that changes `selected_dm_peer_id` away calls it) and in `State_directKeysChanged` once encryption works.
- View: `buildDirectComposerView` (modes Encrypted, SettingUp, Blocked, Confirm, Fallback), `directMessageBadge`/`directMessageText` (lock, "Unencrypted"; "This message could not be decrypted", "Opening encrypted message…", "Checking who sent this message…" for plaintext waiting for its sender's pin), `directPreviewUnencrypted` for `SidebarRow.previewUnencrypted`. Badges are drawn by `ui.TranscriptUnit.badge` (not part of the copied text). Widget IDs: `dm-fallback-switch`, `dm-fallback-confirm`, `dm-fallback-cancel`, `dm-send-unencrypted` (server ID, peer user ID).
- Harness: direct message events are printed after State applied them (`headlessWriteDirectMessageEvent`, `headlessWriteDirectHistoryEvent`, `headlessWriteConversationsEvent`); a live message waiting for a key is owed and printed when it opens; `State.directNotes` (recorded only with `recordDirectNotes`) become `direct_opened` and `direct_queue`. `dm` encrypts, `dm-plain` uses the switch actions.
- Tests: `direct_messages_e2ee_test.odin` (two States through the stubbed bridges: both ways, waiting for a key, failures and replays, which failures are hidden, the queue and no downgrade, the switch and badges, previews, the decisions). Other tests deliver signed messages through `testApplyDirectMessage` and `signed_messages_test.odin` (`testSignDirectMessage`, `testSignDirectPreview`, `testSignRoomMessage`: each test user's identity is derived from its ID and pinned in the receiving State by `testMessageSigner`).

## Encrypted Rooms

- Protocol 18, design 6.1-6.2; `room_log.odin` (state, verification, signing, rights, event lines), `room_log_test.odin`. `State.roomLogs` holds one `ServerRoomLogs` per server and one `RoomLogRoom` per encrypted room: `status` (Unknown, Loading, Verified, Failed), the verified `common.RoomLogState` (members, managers and their keys at epoch `state.version`), `events` (`RoomLogEventLine` per verified entry; `State_roomLogEventText` renders "alice added carol", "the server removed dave", "erin (manager) added themselves"), and the pages of a whole-log fetch.
- Verification: the first fetch is the whole log (`State_requestRoomLog`, page by page), replayed with `RoomLogState_apply` against the pins (`roomLogLookupPin`: this profile's own key for itself, else the key store pin) and the key store head (Fork if the entry at that version hashes differently, Rollback if the log ends before it). Later entries apply one by one (`State_roomLogApplyEntries`): older than the head skipped, the head's version must hash to it, a gap fetches after the head. A room list only triggers a fetch when its `logVersion` is above the verified one (a list can lag behind live entries, so a lower one proves nothing). Every failure is final for the run (`State_roomLogFail`: `ROOM_LOG_CHANGED_WARNING` as the chat status, the Members page and the composer note; nothing fetched or signed again). After a verified change: the head is saved, unpinned identities are fetched (E1 pins them on first use) and `State_roomLogsPinsChanged` (called from `State_directKeysChanged`) checks them against the new pins, pending actions run, `State.roomLogChanged` is called.
- API for sender chains: `State_roomLogVerified(state, serverID, roomID) -> ^common.RoomLogState` (nil unless Verified; members of the current epoch = its version), `State_roomLogEpoch`, `State_roomLogWasMember` (from `RoomLogRoom.memberships`, the stretches of epochs each user was a member, kept by replay and apply), and `State_roomChainsLogChanged`, called after every verified change or failure (`State.roomLogChanged` stays a hook for tests). Distribute keys only to the members that state names, with the keys it names (they equal the pins); never to `room_members`.
- Signing: `State_roomLogAppend(state, serverID, roomID, action, targetUserID, access, checkRights)` builds on the verified head, checks `RoomLogState_validate` locally unless `checkRights` is false (the harness), signs with the config's identity key over the pinned server key, and sends through `roomLogSendBridge` (tests swap it under `roomLogSendBridgeTestMutex`); a target without a pin is fetched first and the change waits in `State.roomLogPendingActions`. Nothing changes locally until the server's `ServerRoomLog` echo verifies. `State_addRoomMember`, `State_removeRoomMember` (a manager signs; an admin who is not one sends `ClientRemoveRoomMember`, which the server records unsigned) and `State_leaveRoom` route encrypted rooms here; `State_roomLogMemberChange` adds the Members page notice. Local refusals say who to ask ("Only this room's managers can add members; ask alice.").
- Creating: `State_sendCreateRoom(..., encrypted, managers)` validates, then `State_roomLogBeginCreate` keeps a `RoomLogPendingCreate` (this account first), fetches managers' keys first when needed, and sends `ClientCreateRoom{encrypted}`; `State_roomLogRoomCreated` (on `.RoomCreated` with `encrypted` and `logVersion` 0, matched by name) signs and appends the Create with the managers' pinned keys. The form (`RoomEditor.encrypted`, on by default for invite modes and never for Public, `uncheckedManagers`; `State_toggleRoomEditorEncrypted`, `State_toggleRoomEditorManager`, `State_roomEditorManagers`; `buildRoomEditorManagerRows`, widget IDs `room-editor-encrypt`, `room-editor-manager USER`) lists every admin the client sees (`State_roomLogAdminCandidates`), checked, the creator locked; admins without a usable pin cannot be checked. An Edit of an encrypted room keeps its access (`State_setRoomEditorAccess` ignores it) and repeats the flag.
- Rights and UI: `roomLogRights` (log membership and management plus the admin flag; an add needs both, a full room offers none) feeds `roomMemberRights` for encrypted rooms. `buildRoomMembersView` lists the log's members, its managers and the directory's admins apart with key states (`roomMemberKeyStateLabel`), `addNote`, Make/Remove manager and the access switch (widget IDs `room-members-make-manager`, `room-members-remove-manager`, `room-members-access`). `buildRoomView` places the event lines ("Member list", negative message IDs, no badge) among the messages by time (`parseServerTimestampUnix` on the message's timestamp) and replaces the composer with `State_roomChainsComposerNote` (the warning, `ROOM_LOG_NOT_SET_UP_NOTE`, `ROOM_NOT_A_LOG_MEMBER_NOTE`) when this account cannot send; the header reads "🔒 # name". `State_roomAllowsVoice` follows the room type only: voice in an encrypted room is end-to-end encrypted (protocol 21, Encrypted Voice below).
- Harness: `room-create` options `encrypted` and `managers=ID+ID|none`, `room-log`, `room-manager`, `room-access`, `room-log-entry` (an entry as hex, signed or unsigned, for proofs), the `room_log` event (printed from `State.roomLogNotes`, `recordRoomLogNotes`), `encrypted`/`logVersion` on room events. Live: `dev/e2ee-proof.sh` steps 8-10, `dev/ui-smoke.sh` step 11.

## Encrypted Room Messages

- Protocol 19, design 6.3-6.6, 7.2, 7.3; `room_chains.odin` (state, opening, distribution, requests), `room_chains_test.odin`, `headless_room_chains.odin`. `State.roomChains` holds one `ServerRoomChains` per server and one `RoomChainRoom` per room: the chain this session sends with (`sending`, `sendingEpoch`, `distribution` None/Sent/Stored), `queued` and `inFlight` messages (owned, wiped), this session's key fetch (`keysFetching`, `keysFetched`) and requests (`requested`), envelopes waiting for the log (`pendingEnvelopes`), and key requests waiting for a key or answered (`pendingAnswers`, `answered`).
- Cached room messages are `RoomMessageEntry` (`using message: common.StoredChatMessage` plus `security`: `protection` Plain/Pending/Encrypted/Failed/Hidden, `wait` Log/Key/Sender, `failure` Sealed (with `sealedError`), NotSealed, NotMember, BadIndex, LogFailed, Replayed, Unsigned, BadSignature, NoKey, and the decoded `header`). `RoomCache_mergeMessage` clones the sealed bytes and the signature and marks every message Pending; `State_receiveRoomChat` and `State_receiveRoomHistory` then open it (`State_roomChainsOpenMessage`, `State_roomChainsOpenNew`). `State_roomOpenEntry` is the one place that opens: plaintext goes to `State_roomCheckPlain` (below); a sealed message is decoded, then the verified log (Pending Log until it reaches the epoch; LogFailed when the log failed), the sender's membership of that epoch (`roomLogMembershipsInclude`), the sender's identity (own key, else the pin, else the verified log's), its signature (`verifyRoomMessageSignature`, before any key is waited for or asked for), the chain from the key store (Pending Key), `deriveSenderChainMessageKey`, `openRoomMessage`, the CBOR plaintext. Every room message must be signed by its sender (#90): a failure at or before the signature check (a decode error, no identity, a bad signature, plaintext in an encrypted room: NotSealed) is Hidden (`roomEntryHide` wipes the text), and LogFailed, NotMember and BadIndex are shown as Failed only when the signature verifies (`State_roomSettleSealed`). `RoomCache_checkReplay` marks the later of two opened (or two verified plaintext) messages with one sender and the same client message ID, or chain position, Replayed. Failures are never reopened; `State_roomChainsReopenPending` reopens only Pending ones, after keys or the log arrived.
- Plaintext room messages (protocol 22, `room_signatures.odin`, `room_signatures_test.odin`): `State_signRoomChat` signs every send (`signPlaintextRoomMessage` with a random `clientMessageID`, carried by `RoomChatSend` through `roomChatSendBridge`). `State_roomCheckPlain` checks every received one against the sender's pin (`State_directIdentityFor`, this profile's own key for itself): Plain when it verifies, Pending wait Sender while the sender's bundle may still be pinned (the follow-up fetches it, `State_roomMessagesKeysChanged` from `State_directKeysChanged` checks again), Hidden Unsigned, BadSignature or NoKey otherwise. `roomMessageShown`/`State_roomMessageShown` are false for Hidden: the transcript (`buildRoomView`) and the live unread count leave it out.
- Follow-up (`State_roomChainsFollowUp`): a message waiting for the log fetches it; waiting for a key fetches the room's envelopes once per session (`ClientFetchRoomKeys`, paged by envelope ID), then sends `ClientRequestRoomKey` once per chain. `State_receiveRoomKeys` (live `.RoomKeyEnvelopeReceived` or a `.RoomKeysReceived` page) opens each envelope only when the verified log shows its sender as a member of its epoch, with the sender's identity and this profile's key pair (`openSenderKeyDistribution`); NotForMe, Failed and NotMember are dropped, Pending ones wait in `pendingEnvelopes` for the log. The echo of this session's own distribution sets `distribution` Stored.
- Sending (`State_sendChannelChat` routes encrypted rooms to `State_roomChainsSend`): the message is queued and `State_roomChainsPump` starts a chain when there is none, its epoch is not the verified log's, or `SenderChain_needsReplacement`; distributes it (`State_roomChainsDistribute`: one SenderKey envelope, a wrap per verified member with a usable pin whose identity matches the log, the sender included; members whose key is Pending are fetched first, others get no wrap) and sends the queue only once the distribution is Stored ("Setting up encryption…" meanwhile). The sending side is never stored: every run starts new chains, so no index is ever used twice; the start key goes into the key store like a received chain. "Room key is out of date" puts the messages in flight back at the front of the queue, drops the chain and fetches the log; the other sealed refusals give the text back to the draft (`State_roomChainsRefuseQueue`). A connection reset drops messages in flight and a distribution never acknowledged (with its chain). Sends go through `roomChainSendBridge` with a `RoomChainRequest` (tests swap it under `roomChainSendBridgeTestMutex`).
- Key requests (`State_receiveRoomKeyRequest(…, epoch, senderUserID, requesterUserID, chainID)` → `State_roomChainsAnswer`): From join rooms re-seal (one wrap, the requester) only this account's own chain and only for a requester who was a member of that epoch in the verified log. Full history rooms (protocol 20, the verified log's `historyVisibility`) answer for any chain the key store holds whose sender was a member of its epoch, to a current member: the own chain as a SenderKey re-seal, another's as `sealRoomKeyForward` (`RoomChainRequest.senderUserID` set); a chain not held is `NotHeld`. Every answer goes to the requester's pinned key only when it is the identity the log names; a requester whose key is Pending waits in `pendingAnswers`; `answered` keeps one answer per (epoch, sender, chain, requester) and session.
- Full history (protocol 20, design 6.6): `State_roomLogApplyEntries` notes the Adds this account signed and, after the change verified, calls `State_roomChainsForwardHistory`, which answers the newcomer for every held chain of an earlier epoch (never on a whole-log replay, so a restart forwards nothing again). `State_roomChainsTakeEnvelope` opens an envelope with `forwarderId` only in a Full history room, from a forwarder who was a member at the same time as this account (`roomLogMembershipsOverlap`), for a sender who was a member of the epoch, with `openRoomKeyForward` against the forwarder's identity (pin, else the log's); otherwise `NotAllowed`. `State_roomChainsPeerOnline` (from `.UserPresenceChanged`) clears `requested` in Full history rooms the user is a member of, so waiting chains are asked for again. Notes carry `forwarderID`.
- View: `roomMessageDisplay` (the opened text with "🔒", "Waiting for this message's key from <name>", "Opening encrypted message…", "Checking who sent this message…", "This message could not be decrypted").
- Harness: room messages are printed after State applied them (`headlessWriteRoomChat`, `headlessWriteRoomHistory`) with `encrypted`, `decryptError`, `epoch`, `protection` (`hidden` messages and waiting ones without content, `headlessRoomContent`); a live one that waits is owed and printed when it opens; `State.roomChainNotes` (recorded only with `recordRoomChainNotes`) become `room_opened`, `room_key`, `room_key_request` (with `forwarderID`, outcomes `not_held` and `not_allowed` since protocol 20) and `room_queue`; `room-keys ROOM_ID [fetch]` lists held chains (never a key). Live: `dev/e2ee-proof.sh` steps 11-17 (17: Full history), `dev/ui-smoke.sh` step 11.

## Encrypted Voice

- Protocol 21, design `docs/plan/e2ee-voice-design.md`. `voice_e2ee.odin` (UI thread) owns the voice keys of the joined encrypted room in `ClientVoiceState.e2ee`; the engine (`voice_engine.odin`) seals and opens frames with `common/voice_e2ee.odin`. `ClientVoiceState.encrypted` comes from `RoomSummary.encrypted` at the join (it never changes, and a re-join keeps it), and an engine created for it gets `VoiceEngineConfig.encryption`: it never sends a frame without a send key, never sends an unsealed one, never plays a frame that did not open, and pads every Opus packet to one size per bitrate (`voiceE2EEPaddedOpusBytes`: capped at 1.6 times the nominal frame, then `opus.padPacket`) instead of constant bitrate, which dropped steady tones by 40 to 50 dB with in-band FEC at 24 kbit/s. Encryption is never decided per frame or from the server.
- Joining: `State_joinVoice` refuses with `State_voiceE2EEJoinBlocker` ("Setting up encryption…" while the verified log is missing, the profile's key, the log warning, not a log member). The engine starts on the acknowledgement as usual; `State_voiceE2EEEngineStarted` makes a new `voiceSessionID` on a join (not on `State_voiceRestartEngine`, which passes `restart` and keeps the session), pushes the held speaker keys into the new engine, and rotates.
- Speaking (`State_voiceE2EERotate`): a new random `common.VoiceKey` and generation, sealed with `sealVoiceKey` to every member of the verified log's current epoch whose **pin** (`State_e2eePeerKeyInfo`) matches the identity the log names, this account excluded; a member whose key is Pending holds the rotation back (`rotatePending`, retried from `State_voiceE2EEKeysChanged`). The engine gets the key (`VoiceEngine_setSendKey`) only after `ClientVoiceKey` went out. Triggers: the join, every engine (re)open (so no key ever meets two sequence counters), a new epoch in `State_voiceE2EELogChanged` (the old key is cleared from the engine first), `VOICE_KEY_ROTATE_SECONDS` in `State_voiceE2EETick`, a member's `ServerVoiceKeyRequest` (at most every `VOICE_KEY_REQUEST_INTERVAL_SECONDS`), and "Voice key is out of date" (`State_voiceE2EEProtocolError` fetches the log; the log change rotates).
- Listening (`State_voiceE2EEReceiveKey`, design 4.2-4.3): refused unless the sender was a member of the key's epoch in the verified log and is pinned with the identity the log names; a later epoch waits in `pending` (owned) for the log, a missing pin for the fetch; an earlier epoch only within `VOICE_EPOCH_GRACE_SECONDS` of the log moving on; `createdAt` within `VOICE_KEY_MAX_AGE_SECONDS` back and `VOICE_KEY_MAX_FUTURE_SECONDS` ahead (`State_voiceE2EENowMS`, overridable in tests); newer than the last accepted key of that sender (a higher generation of its session, or a session no older). `openVoiceKey` uses the **pin** and this profile's key; every failure is final and makes no request. Two keys per speaker (current, previous) go to the engine with `VoiceEngine_setSpeakerKeys`; old-epoch keys are wiped when the grace ends. A participant without a usable key for `VOICE_KEY_MISSING_REQUEST_MS` is asked once (`ClientRequestVoiceKey`), and the sidebar shows `State_voiceE2EEParticipantNote` ("Waiting for <name>'s voice key", "Clock out of sync").
- Keys live only in memory (`VoiceE2EEState`, the engine's key table): never in the key store or `config.json`, wiped when replaced, when voice ends (`State_voiceE2EEEnd` from `State_voiceStopEngine`) and when an engine closes or is destroyed. The engine's table is written under `keyMutex` and copied by the voice thread when `keyVersion` moved, like the speaker controls; seal and open allocate nothing.
- Harness: `voice_key` events from `VoiceE2EEState.notes` (`recordNotes`), printed by `headlessPollVoice`, which also runs `State_voiceE2EETick`; `voice_status` gains `encrypted` and `sendGeneration`; `voice-stats` an `e2ee` object; `voice-key-rotate SECONDS` sets `VoiceE2EEState.rotateSeconds`. The GUI loop runs `State_voiceE2EETick` after draining network events.

## Context Menus

- Toolkit (`client/ui`, no HayChat types). `overlay.odin`: `ui.beginOverlay(ctx, id, rect)` / `ui.endOverlay` draw on top with the clip stack reset. An overlay is modal from the frame after it is drawn: `overlayBeginFrame` (in `ui.beginFrame`) takes the previous frame's rect, and `mouseOver` returns false for every widget outside the overlay while the pointer is inside it (`ui.overlayBlocks`, pure), so clicks, hover, tooltips and the wheel (scroll areas and inputs go through `mouseOver`) never reach what is under it. A press outside it sets `ui.overlayPressedOutside(ctx, id)`; a left press there is also consumed (`pressConsumed`), a right press is not, so a menu can reopen on what was right-clicked. The frame's keyboard events move to `ctx.overlay.events` (`ui.overlayEvents`), so Enter in a menu never submits the focused composer under it. `ui.contextMenuRequested(ctx, id, rect)`: the right button went down over rect this frame (clip and overlay honoured); only the first caller gets a given press, and it records rect for automation under id.
- `menu.odin`: `ui.menuBegin(ctx, id, rect)`, `ui.menuItem(ctx, key, label, enabled, danger) -> bool`, `ui.menuSlider(ctx, key, label, value, low, high, step) -> SliderResult` (a labelled slider row, `MENU_SLIDER_HEIGHT` tall, widget ID `idOf("menu-slider", key)`; it takes no highlight, so Up and Down skip it, and moving it does not close the menu), `ui.menuSeparator`, `ui.menuEnd -> dismissed`, and `ui.menu(ctx, id, anchor, items) -> MenuResult{clicked, dismissed, sliderIndex, slider}` for a list known up front (a `MenuItem` with `slider` set is drawn with `menuSlider`). `ui.menuSize` measures (widest label, at least `MENU_MIN_WIDTH`), `ui.menuPlace(anchor, size, bounds)` (pure) puts the top-left at the anchor and flips left or up at the edges, then clamps. Up/Down move the highlight over enabled items (`ui.menuMoveHot`, pure, wraps), Enter activates; Esc, a press outside, and `input.focusLost` (`WINDOW_FOCUS_LOST`) dismiss. Item widget IDs are `idOf("menu-item", key)` and labels go through `ui.label`, so `click "LABEL"` works. The caller owns open and closed: an item click returns its index and does not close the menu by itself. The menu ID should change for every menu opened (the client uses `idOf("context-menu", serial)`): a menu not drawn last frame is never dismissed by the press that opened it, and its highlight starts fresh.
- Text inputs and transcripts report right-clicks themselves. `ui.textInput` takes focus on a right press (keeping its selection), and `ui.textInputContextMenuRequested(ctx)` returns that input's ID after drawing, so no screen wires its inputs; `ui.textInputFacts` (selection, text, drawn this frame) and `ui.clipboardHasText` decide the entries, and `ui.textInputCommand(ctx, id, .Cut|.Copy|.Paste|.SelectAll)` is applied by the input on its next frame (only it has the buffer). `ui.focusTextInput` focuses an input with the caret at the end. `ui.transcript` returns `TranscriptResult{contextMenu, unitKey, selectionText}`: the unit whose text line was right-clicked (not the gaps) and the transcript's selected text at that moment (temp).
- Client: `State.contextMenu` (`ContextMenuState`, `context_menu.odin`) holds the open menu's `ContextMenuTarget` (a union of `ChannelMenuTarget`, `ConversationMenuTarget`, `MemberMenuTarget`, `VoiceParticipantMenuTarget`, `MessageMenuTarget` and `SenderMenuTarget` (server, `common.ReadMarkerKind`, conversation and message ID), `ServerMenuTarget`, `TextFieldMenuTarget` (the input's `ui.ID`)), with IDs only, plus the click position, an owned copy of the transcript selection, and the Remove server confirmation. Widgets call `State_requestContextMenu` while drawing (`viewSidebarRowContextMenu`, `viewServerContextMenu`, `viewTranscriptContextMenu` in `view_context_menu.odin`, one call each in `view.odin` / `view_direct.odin`); `viewContextMenu`, deferred at the top of `viewApp` so it runs last on every screen, opens the pending request (replacing an open menu), builds the entries with the pure `buildContextMenu(state, facts)`, draws them with `ui.menu`, and runs `State_runContextMenuAction` after drawing. The action returns a `ContextMenuEffect` (text to copy, a text command, a composer to focus, keep open) that the view applies, so actions are tested without SDL.
- `buildContextMenu` returns `visible = false` when the target is gone (room not listed, account unknown, participant left voice, message not cached, server removed, text input not drawn this frame), which closes the menu. Entries: Channel (Mark as read, enabled with unread; Join/Leave voice from `roomVoiceHeaderAction`, none in a text-only room; Copy room name; admins on the selected server: Edit room…, Delete room…), Conversation / Member / Sender (Send message, not to yourself; Mark as read while a conversation exists, enabled with unread; Copy name; Verify encryption… for others, protocol 16), Voice participant (Send message, Copy name, and for others Mute for me / Unmute for me and a Volume slider, issue 47), Message (Copy message, Copy selected text with a selection, Copy name, Quote, and in rooms Send message to sender for others), Server (Server settings, Retry now while not connected, Copy address, Remove server… then "Click again to remove"), Text field (Cut, Copy, Paste, Select all). For admins, Conversation, Member, Voice participant and Sender menus end with the admin entries from `buildAdminUserControls` (Rename…, Make admin / Remove admin, Kick…, Ban… / Unban, disabled per D6; only for accounts the directory lists). Rename…, Kick… and Ban… open Server settings → Admin with that confirmation open (`State_openAdminConfirm`), since a menu cannot hold a text field; Make admin, Remove admin and Unban send at once.
- Actions use the existing paths: `State_markConversationReadAll` sends through `State_markConversationRead` (the read bridge) up to the newest known message, or `CONTEXT_MENU_MARK_ALL_READ_ID` (the server clamps a mark-read to the newest message) when the unread messages were never loaded, restoring `readSend.sentMessageID` so the automatic mark-read still compares loaded IDs; Delete room… is `State_openRoomEditor` plus `confirmDelete = true`; Mute for me / Unmute for me call `State_setUserVoiceMuted`; the Volume slider (`ContextMenuEntry.slider`, labelled "Volume: N %", 0–200 % in `SERVER_SETTINGS_VOLUME_STEP` steps) calls `State_setContextMenuVolume`, which applies it while it is dragged and saves the config when it is let go, keeping the menu open; Quote (`State_quoteIntoDraft`) appends `> ` lines on a line of their own to that conversation's draft, cut to `common.CHAT_MESSAGE_MAX_BYTES` at a character boundary, and focuses `composerInputID`. `ContextMenuAction` values name the entries' widget IDs: add new actions at the end.
- Tests: `client/ui/ui_test.odin` (placement, `overlayBlocks`, the frame start taking pointer, presses and keys from the widgets under an overlay, the highlight moves) and `context_menu_test.odin` (entries per target, admin gating, disabled states, gone targets, every action through the read bridge under `readMarkerSendBridgeTestMutex`). `dev/ui-smoke.sh` copies a message from its menu, pastes it with the composer's menu, and marks a channel read from its menu, checked by a second headless session of the same account.

## Dev Workflow

- Start the dev server with `./dev.sh up`; `./dev.sh seed` adds the fixture accounts admin and haypeer (the server creates `#general` itself).
- `./dev.sh client [PROFILE]` builds the client from the working tree and opens it on the host's Wayland or X11 display, inside the dev pod. Each profile keeps its config and identity key in its own volume, and a new profile starts with the profile name as display name and the dev server (`localhost:12345`) as its server, so profiles are distinct users. `./dev.sh key PROFILE` prints a profile's public key.
- A client on the host (`odin run client`) uses the host's real `~/.config/haychat`; with an empty config it opens the first-run screen, where `localhost` reaches the dev server. Point `XDG_CONFIG_HOME` at a scratch directory to try the first-run flow without touching your real identity.
- `headless.odin` is the headless harness (`client --headless`, see `docs/testing-harness.md`). It drives `State` and the actions with no SDL; `main` in `app.odin` only branches to it. Its connect step is one procedure (`headlessConnectAndWait`), so connection-flow changes adapt there. New runtime event kinds need a name and a case in `headlessRenderRuntimeEvent`; new user actions can get a row in `HEADLESS_COMMANDS`. Direct messages have `users`, `conversations`, `dm`, `dm-plain`, and `dm-history` commands and `direct_message`, `direct_history`, `user_list`, `conversations`, and `presence` events. Read state has the `read room|dm ID [MESSAGE_ID]` command and the `read_marker` event; the harness never sets `windowFocused`, so it never marks anything read by itself. Voice prints `voice_participants`, `voice_join_rejected`, and `voice_left` events, and `headless_voice.odin` adds the `voice-*` commands and the harness-derived `voice_status` and `voice_speaking` events: `headlessPollVoice` runs after every applied event and every loop pass, compares `State.voice.status` and the engine snapshot with `HeadlessHarness.voice`, and prints the edges (`headlessVoiceSpeakingUpdate` is pure, for tests). `voice-source`/`voice-sink`/`voice-gate` change the engine template (next join); `voice-volume USER_ID PERCENT` and `voice-mute-user USER_ID on|off` call the per-user voice actions (`user_voice.odin`) on the selected server; `voice-stats` reads the transport's `voiceStats` under the worker lock and lists the stored per-user settings with what the engine applies (`userVoice`); `voice-flush` waits on the engine's sink flush ticket. Room management has `room-create TYPE[,OPTION…] …` (options `public`, `member-invite`, `admin-invite`, `from-join`, `full`, `no-join`; `headlessParseRoomOptions`), `room-edit ROOM_ID TYPE[,ACCESS] …` (`text`, `voice`, or `both`), and `room-delete` (no admin check in the harness, so an agent can see the server refuse) and the `room_created` event, and room JSON carries `roomType`, `access` and `historyVisibility`; room access has `room-members`, `room-add`, `room-remove`, `room-leave` and `admin-rooms` and the `room_members`, `room_member_result` and `admin_rooms` events, and `room_membership` carries `userID`; `connected` and `status` carry `isAdmin` and `nicknameLocked`. Admin actions have `admin-role`, `admin-rename`, `admin-kick`, `admin-ban`, and `admin-unban` and the `user_updated`, `account_updated`, `admin_result`, and `session_ended` events; `users` carries `isAdmin` and `isBanned`. A command row's `text` is `.Required` or `.Optional` when the rest of the line is one more argument.
- `ui_script.odin` is GUI automation (`client --ui-script FILE`, see "GUI Automation" in `docs/testing-harness.md`). `runApp` takes an `AppOptions`; with a script it enables `ui.enableAutomation` and calls `UIScriptRunner_step` once per loop iteration, between frames, which pushes synthetic SDL events (so input takes the real path) and reads the frame's drawn strings and widget rects from `client/ui/automation.odin`. Without a script the only cost is nil checks. `right-click`, `right-click-id` and `right-click X Y` push the right button instead (context menus); `wait-gone "TEXT"` waits until TEXT is no longer drawn, and `scroll X Y N` turns the wheel over a point (scroll areas below the fold). Text drawn through `ui.label`, `ui.wrappedLabel`, `ui.button`, transcript units, menu items, and empty-input placeholders is findable by `click`/`wait-text`; text drawn another way (e.g. straight `ui.drawText`) is not, so new widgets that show user-facing text should call the automation hook. `click-id` relies on stable `ui.idOf` names, so keep widget names meaningful.
- Live client tests (`HAYCHAT_LIVE_STARTUP_AUTH=1`) run through `./dev.sh live`, which gives them a fresh server and database. They connect to `127.0.0.1:12345`.
