### Language Quirks

- Variable declarations follow the syntax `name: type = value`, where the type can be inferred from the value if it is not explicitly specified. For example, `x := 5` will infer that `x` is of type `int`, while `y: f32 = 3.14` explicitly declares that `y` is of type `f32`. If the type cannot be inferred from the value, it must be explicitly declared to avoid compilation errors.
- For getting the length of an array, use `len(array)`. This includes strings, slices, and other array-like structures.

## Project Structure

- `client/`: Contains the client-side code for the HayChat application, including the GUI and client logic.
- `server/`: Contains the server-side code for the HayChat application, including the ENet network thread, the router, database management and migrations, and client-server communication. It has no HTTP or admin port.
- `common/`: Contains shared code and definitions used by both the client and server.
- `docs/`: User, operator, and developer documentation; `docs/README.md` is the index. `docs/plan/` holds design documents and past round plans, which are historical records and not kept up to date. When behaviour changes, update the document that describes it (see the index).
- `deploy/`: Production server image (`deploy/Containerfile`), quadlet units, SQL helpers, and the release archive script used by `.forgejo/workflows/release.yml`. See `deploy/README.md`; `./dev.sh release-image --smoke` builds and smoke-tests the image.

## Code Style

- Tabs are used for indentation, with a standard indentation level of 4 spaces.
- One True Brace Style is used for braces, with the opening brace on the same line as the control statement and the closing brace on a new line.
- Lines should not exceed 100 characters in length, and should be broken up into multiple lines if necessary.
- Variable and function names should be descriptive and use camelCase.
- In camelCase names, use "URL" (not "Url"), "API" (not "Api"), "ID" (not "Id"), and "HTTP" (not "Http").
- Constants should be in all uppercase letters with underscores separating words.
- Comments should be used to explain the purpose of code blocks and any complex logic, and should be written in English.

## Chat Protocol And Ownership

- Shared encrypted application packets and database IPC types belong in `common/protocol.odin`. When changing a wire payload, update both client transport decoding and server routing, then validate `odin test common` before component tests.
- Room access is server-authoritative and membership-scoped (protocol 15, migration 4): every room has an access mode (`RoomAccess`: Public, Member invite, Admin invite) and a history setting fixed at creation (`RoomHistoryVisibility`: From join, Full; Public always reads Full). New accounts join only Public rooms and a new Public room includes every account; an invite room includes its creator only when `ClientCreateRoomPayload.creatorJoins` is set. `room_members` is the authoritative check for every send, history page, member list and voice join; a From join member reads history only after `room_members.joined_at`. Who may add (`ClientAddRoomMember`: holders of ManageRoomMembers in invite rooms, members in Member invite rooms, nobody in Public rooms), remove (`ClientRemoveRoomMember`: ManageRoomMembers only) and leave (`ClientLeaveRoom`: members of non-public rooms) is decided in one SQL statement with the change (`server/database_room_access.odin`). Clients may request room lists, history and members (`ClientFetchRoomMembers`, members and ManageRoomMembers), but must treat `ServerListRooms`, `ServerRoomMembershipChanged` (whose `userId` says whose membership changed), edit, and delete events as the source of truth for visible rooms; holders of ManageRooms or ManageRoomMembers see every room through `ClientAdminListRooms`. Encryption (E4) is not part of it.
- Room management (create, edit, delete) needs the ManageRooms server permission (protocol 23; admins hold every permission), checked in the create, edit and delete statements themselves. `ServerAuthSuccess.isAdmin` (protocol 8) and `permissions` (protocol 23) only tell the client which controls to show; a role changed by an admin from a client reaches the target's sessions at once as `ServerAccountUpdated` (protocol 14), one changed in the database on the next connection.
- Roles and server permissions (protocol 23, migration 11, #95): `common.ServerPermission` is a fixed enum carried as the `ServerPermissions` u64 `bit_set` (pinned bit values; only `SERVER_PERMISSIONS_ASSIGNABLE`, ManageRooms, ManageRoomMembers, CreateInvites and ApproveRegistrations, can go to a role other than admin) and stored as `server_roles.permissions`. An account's effective set is the union of its roles' bits; the built-in `admin` role (`server_roles.builtin`) holds every bit and cannot be renamed, deleted or reduced. Every permission check uses the shared subquery in `server/database_roles.odin` (`DATABASE_SERVER_PERMISSIONS_OPEN_SQL` + account expression + `DATABASE_SERVER_PERMISSIONS_CLOSE_SQL`, -1 for an admin) in the same statement as the change; kick, ban, rename and role management stay keyed to the admin role. `ClientAdminListRoles` (anyone) / `ServerRoleList`, and admins' `ClientAdminSaveRole`, `ClientAdminDeleteRole`, `ClientAdminSetUserRoles` (answered by `ServerAdminActionResult` with `roleId`), fan out `ServerRoleUpdated`/`ServerRoleDeleted`/`ServerUserUpdated` (`UserSummary.roleIds`) to every session and `ServerAccountUpdated{permissions}` to each account whose set changed. Clients gate controls on `State_hasPermission` (`client/connection_state.odin`) and keep roles in `client/roles.odin`. `ClientGetRoles` … `ServerRemovedRole` are retired placeholders pinned at 24..31. See `client/AGENTS.md` (Roles) and `server/AGENTS.md`.
- Room permissions and role rooms (protocol 24, migration 12, #96): `common.RoomPermission` (SendMessages 0, SpeakInVoice 1, ManageMembers 2, EditRoom 3, AttachFiles 4 since protocol 27) is an allow-only `RoomPermissions` u64 `bit_set`: `rooms.everyone_permissions` (default Send + Speak + AttachFiles) plus `room_role_permissions(room_id, role_id, permissions)` for members holding the role; ManageRoomMembers implies ManageMembers, ManageRooms implies EditRoom, admins hold every bit, and `room_members` still decides who sees a room. Every check uses the shared subquery in `server/database_room_permissions.odin` (`DATABASE_ROOM_PERMISSIONS_OPEN_SQL` + account + `DATABASE_ROOM_PERMISSIONS_ROOM_SQL` + room + `DATABASE_ROOM_PERMISSIONS_CLOSE_SQL`, -1 for an admin) in the statement that makes the change: posts (sealed too) need Send, member adds and removes ManageMembers (or, to add, membership of a Member invite room; the encrypted room log's Add too), edits ManageRooms or EditRoom with the room's own access and access roles, `ClientAdminSetRoomPermissions` ManageRooms or EditRoom and only bits the requester may grant. A voice join is never refused for Speak: the join check returns the joiner's set and the relay drops a session's frames while `NetworkVoiceRouteMember.speakDenied`, which every `ServerListRooms` the router sends updates (`MainRouterState_voiceUpdateSpeakPermissions`). `RoomSummary.myPermissions` is per recipient (`ServerListRooms`, `ServerAdminRooms`, the creator's `ServerCreateRoom`; other payloads carry none and clients keep theirs), and any change to grants, roles or the admin role resends `ServerListRooms` (`MainRouterState_resendRoomLists`). Grants travel in `ServerAdminRoomPermissions` (`ClientAdminFetchRoomPermissions`), not in `RoomSummary`. `RoomAccess.Role` (4) rooms take their members from `room_access_roles`: `DATABASE_SET_USER_ROLES_SQL`, `DATABASE_DELETE_ROLE_SQL`, `DATABASE_CREATE_ROOM_SQL` and `DATABASE_EDIT_ROOM_SQL` add and remove `room_members` (and removed members' read markers) in the same statement and the router sends `ServerRoomMembershipChanged`; manual add, remove and leave are refused, and encrypted rooms refuse Role (`rooms_encrypted_not_role`). Clients gate the composer, voice and controls on `State_roomPermissions` (`client/room_permissions.odin`). See `client/AGENTS.md` (Room Permissions) and `server/AGENTS.md`.
- Registration (protocol 25, migration 13, #43 G1, plan D7-D17): the mode (`common.RegistrationMode`, `server_settings`, migrated Open) is changed by admins (`ClientAdminSetRegistrationMode`, `ServerRegistrationMode` to everyone) or `deploy/sql/set-registration-mode.sql`. A key without an account that the identity statement will not create (not Open, `ClientAuthRequestPayload.registering`, no approved request, not `HAYCHAT_ADMIN_PUBLIC_KEY`) gets the **plaintext** `ServerRegistrationRequired{mode, status, message}`; both sides then activate the transport as on `ServerAuthSuccess`, and the session may send only sealed `ClientRegister{inviteCode, reason}` (14) and `Ping` (5 answers, 10 minutes). `ServerRegisterResponse{status, message, auth}` (15, sealed) is Created (authenticated now, `auth` the `ServerAuthSuccess` fields), Pending, Refused or Declined. Invite codes (`common/registration.odin`: 20 CSPRNG bytes, grouped Crockford base32, only `inviteCodeHash` sha256 stored and compared inside `DATABASE_REGISTER_SQL`) are created by CreateInvites holders (`ClientCreateInvite`/`ServerInviteCreated`, the only time a code is sent; non-admins plain codes expiring within 7 days), listed and revoked; in Invite + approval mode a code makes a request that ApproveRegistrations holders decide (`ClientListRegistrationRequests`/`ServerRegistrationRequests{pendingCount}`, `ClientDecideRegistration`, `ServerRegistrationRequestUpdated` to approvers), and approval completes a still-registering applicant live; an empty reason is left to the server, since a Skip approval code needs none. Clients send `registering` from `Server.use_invite_code` (**I have an invite code** on the first-run and add-server form, **Use an invite code** in Server settings) or an invite link (`haychat://HOST:PORT/invite/CODE?key=SERVER_KEY`, D19: the key is pinned, a link whose key differs from the pin is refused, and nothing signs up without the user). Restricted accounts (`users.restricted`, `UserSummary.isRestricted`, `ClientAdminSetRestricted`) come from room codes, never join Public rooms automatically, are added elsewhere only by ManageMembers holders, and see, are seen by and exchange direct messages with only accounts they share a room with and admins (approvers see everyone): the user list, presence, user updates and key changes are filtered per recipient. See `docs/protocol.md` (Registration), `docs/rooms-and-accounts.md` (Registration, Restricted Accounts), `client/AGENTS.md` (Registration) and `server/AGENTS.md`; `dev/registration-proof.sh` proves it end to end.
- Admin actions on accounts (protocol 14): `ClientAdminSetRole`, `ClientAdminRenameUser`, `ClientAdminKickUser`, and `ClientAdminBanUser` are answered with `ServerAdminActionResult` or a `ServerProtocolError`. The server checks the requester's role and the guards (no kick, ban, or role revoke of yourself; no kick or ban of another admin; never the last admin) in the same SQL statement as the change (`server/database_admin.odin`). It sends `ServerUserUpdated` (a full `UserSummary`, which now carries `isAdmin` and `isBanned`) to every session and `ServerAccountUpdated` to the target's sessions. An admin rename locks the name (`users.nickname_locked`): sign-in keeps it and reports it in `ServerAuthSuccess.nickname`/`nicknameLocked`. Kick and ban send `ServerSessionEnded{kind, reason}` before the disconnect, and a banned sign-in is refused with `ServerAuthFailure` "This account is banned from this server" (plus ": reason"); clients treat both as failures that are not retried until the user asks. Rooms have a type (`RoomSummary.roomType`, `common.RoomType`, only Chat, Voice and ChatAndVoice): a voice-only room refuses chat, a text-only room refuses voice joins, and editing a room to text-only removes its voice participants.
- Direct messages are server-authoritative too: a client must not append a sent direct message locally but wait for the `ServerDirectMessage` (or `ServerSealedDirectMessage`) echo, which carries the stored ID and timestamp and reaches every session of both users. Direct history pages exactly like room history. `ServerUserList` and `ServerUserPresence` are the source of truth for who exists and who is online.
- Encrypted direct messages (protocol 17, migration 6, design 4.5-4.6): a client encrypts whenever `State_e2eePeerKeyInfo.canEncrypt` (`ClientSealedDirectMessage`: a `sealDirectMessage` envelope bound to the server key, both user IDs, both **pinned** identity keys and a random 16-byte `clientMessageId`), queues a send while the peer's key is Pending, and otherwise sends only through the per-conversation **Send without encryption** switch (a signed `ClientDirectMessage`; unsigned ones are refused). The server checks the envelope's structure in the router and its signature in the database worker (`databaseCheckSealedDirectMessage`, with the recipient's identity key from `users.public_key`), stores it byte for byte with an empty `content` only while the recipient keeps that key, and refuses a reused `(sender, clientMessageId)`. Clients open envelopes only with the sender's pin and their own key, never retry a failure, mark replays, and flag encrypted conversations in the key store (no downgrade). Every direct message must be signed by its sender (#82): a client never shows one whose signature it did not verify against the sender's pin (no signature, a bad one, no pin to check with, or an envelope that fails at or before its signature check); an envelope whose signature verified but that does not open shows "This message could not be decrypted". See `client/AGENTS.md` and `server/AGENTS.md`.
- Attachment transfers (protocol 26, migration 14, attachments plan F1): a client uploads a file to a room or a direct conversation and gets a server-chosen random 16-byte blob ID (`ClientAttachmentUploadBegin` … `ServerAttachmentRefused`, CBOR on the control channel), and the chunks travel binary on ENet channel 5 (`common/attachment_wire.odin`, sealed with `sealFilePacket`/`openFilePacket` under the transport's file keys, key schedule `"haychat transport v3"`; both sides allocate six channels). The server's storage worker thread (`server/storage.odin`) does all file I/O; the router keeps the 8-chunk window, the per-session caps (2 uploads, 4 downloads) and the pace, and the begin statement every check. The client's transfer worker (`client/attachment_transfer.odin`) reads and writes files and seals chunks under the network worker lock. See `server/AGENTS.md` (Attachments) and `docs/protocol.md`.
- Attachments on messages (protocol 27, migration 15, attachments plan F2): `common.AttachmentRef{blobId, size, sha256, name, mediaType, removed}` lists 0..`ATTACHMENTS_PER_MESSAGE_MAX` (4) files on every room and direct message payload (`attachments`, `DirectConversationSummary.lastAttachments`); with files the content may be empty (`messageContentLengthIsValid`). Plaintext messages carry complete references signed under the v2 labels `"haychat-room-plain-v2"`/`"haychat-dm-plain-v2"` (only when there are files: v1 bytes stay unchanged); sealed messages carry only `blobId` and `size` outside, and the file key, hash, size, name and type inside the seal's `"attachments"` key (`common.SealedAttachment`, `encodeSealedMessagePlaintext`), and a client shows the files as unavailable when the two lists differ. Encrypted files use `common/attachment_e2ee.odin` (Padmé, 64 KiB XChaCha20-Poly1305 chunks, each sealed once; `AttachmentSealer`/`AttachmentOpener`). The four message inserts bind the listed blobs in the statement that stores the message (`DATABASE_ATTACHMENT_BIND_*`: the sender's, Ready, unbound, this conversation, matching encryption, size and hash), rooms need AttachFiles too, and `DATABASE_ATTACHMENT_DOWNLOAD_CHECK_SQL` is D10 (room history visibility through the shared `DATABASE_HISTORY_SINCE_*` cut, or a DM's two sides; the owner's unbound blob; never a Removed one). `ServerAuthSuccess.attachments` (`AttachmentLimits`) announces the limits. Client: `client/attachments.odin` (uploads, `MessageFile`s on entries, downloads by message); the GUI (F4: composer chips and the send gate, file cards with **Save…**, **Remove attachment…**, Admin → Storage, the native file dialogs) is `client/attachment_ui.odin`, `client/view_attachments.odin` and `client/file_dialog.odin`. See `client/AGENTS.md` (Attachments) and `server/AGENTS.md` (Attachments).
- Attachment moderation (protocol 28, no migration, attachments plan F3, D22): admins only, no assignable permission. `ClientAdminRemoveAttachment{blobId, reason}` (`DATABASE_ATTACHMENT_REMOVE_SQL`, `DATABASE_ACTOR_IS_ADMIN_SQL` in the statement) makes a Ready or Bound blob a Removed tombstone that keeps every signed field and its message link, answered by `ServerAdminActionResult{RemoveAttachment, userId = owner, blobId}`; the router ends the blob's downloads (`ServerAttachmentRefused` `common.ATTACHMENT_REMOVED_MESSAGE`), deletes the file (`StorageDeleteBlobs`) and sends `ServerAttachmentRemoved{blobId, roomId, senderId, recipientId}` to every session of the readers the statement names (room members past the From join cut, a DM's two sides, an unbound blob's owner). The reason (at most 500 bytes, `attachmentRemoveReasonIsValid`) is only logged. `ClientAdminAttachmentUsage` → `DATABASE_ATTACHMENT_USAGE_SQL` → `StorageFreeSpace` → `ServerAdminAttachmentUsage` (top 100 accounts, tombstones excluded). A reader's download check of a tombstone is `Removed`. `deploy/sql/remove-attachment.sql` cannot reach the server: the hourly tombstone pass (`DATABASE_ATTACHMENT_TOMBSTONE_FILES_SQL`) deletes such files and clients see it on their next history fetch (cached entries take the server's `removed` flag on re-merge). Client: `client/attachment_moderation.odin`. See `server/AGENTS.md` and `client/AGENTS.md` (Attachments).
- Voice frames (`ClientVoiceFrame`, `ServerVoiceFrame`) are binary, never CBOR: `common/voice_wire.odin` encodes them into caller buffers and decodes them without allocating, sealed in voice datagrams (`sealVoiceDatagram`/`openVoiceDatagram`) on ENet channel 2. A decoded `opus` slice borrows its input buffer and is valid only while that buffer is; copy it to keep it. The voice AAD (`makeVoiceAAD`) is the control AAD plus the datagram's kind byte and is never used for control packets. Voice control (`ClientJoinVoice` … `ServerVoiceLeft`, protocol 10) is ordinary CBOR on the control channel; `ServerVoiceParticipants.recipientJoined` (protocol 12) is set per recipient session and is the only join acknowledgement, because participants carry user IDs, not sessions, with `*_deinit` helpers in `common/protocol.odin` for its owned strings and arrays. `ClientVoiceData`/`ServerVoiceData` are retired placeholders that are never sent and stay only to keep later wire values.
- One voice session per user (protocol 13, Q2): the server keeps at most one voice session per account, so a participant list names each user once. A join the user asked for takes voice over from the account's other session, which gets `ServerVoiceLeft{"joined voice on another device"}`; the client's automatic re-join after a reconnect (`ClientJoinVoicePayload.rejoin`) replaces only a session with the same `deviceId` and is otherwise refused with "voice is active on another device". `deviceId` is the profile's `device_id` config key, 32 lowercase hex characters (`common/voice_device.odin`); the server refuses a join without a valid one but keeps the session. A decoded `ClientJoinVoicePayload` owns `deviceId` (`ClientJoinVoicePayload_deinit`).
- Read state is server-authoritative too (protocol 11): the server keeps a read marker per account and room and per account and direct conversation, and `ServerListRooms`, `ServerDirectConversations`, and `ServerReadMarker` carry the marker and unread count. A client counts live messages from others between those, never lowers a count itself, and marks a conversation read only while the user is viewing it (`client/read_state.odin`); the server fans `ServerReadMarker` out to every session of the account. The unread rules are in `server/AGENTS.md`.
- Account encryption keys (protocol 16, migration 5, design 2-3): each profile's X25519 key lives in `config.json` (`encryption_*`), signed by the identity key, and is published once per session (`ClientPublishEncryptionKey`); the server verifies it against the session's identity key before storing it in `user_encryption_keys`. `ClientFetchUserKeys` (1..`USER_KEYS_FETCH_MAX` distinct IDs) is answered by `ServerUserKeys` (bundles plus `missingUserIds`), and a stored change goes to every session as `ServerUserKeyChanged`. `UserSummary.identityPublicKey`/`hasEncryptionKey` are filled everywhere a `UserSummary` is built. Clients pin bundles per server in the key store (`client/keystore.odin`) and decide trust in `client/e2ee_state.odin`: callers that encrypt or verify use the pin (`State_e2eePeerKeyInfo`), never a key the server sent. See `client/AGENTS.md` and `server/AGENTS.md`.
- Encrypted rooms and their member log (protocol 18, migration 7, design 6.1-6.2): `RoomSummary.encrypted`/`logVersion`; an encrypted room is Member or Admin invite, its flag never changes, and the server creates it with **no members**: the creator's client signs the log's `Create` (the room ID is in every entry) after `ServerCreateRoom` and sends it with `ClientAppendRoomLog`. The server replays the stored log on every append (`server/database_room_log.odin`), validates the entry with `RoomLogState_validate` using accounts' `users.public_key` as its pins, applies its own 5.1 rules on top (an add needs an admin or a Member invite member **and** the log's signature), and stores and applies it to `room_members` in one transaction; `ServerRoomLog` fans it out to members, managers and the target. An admin's `ClientRemoveRoomMember` becomes a server-written unsigned Remove; `ClientAddRoomMember`/`ClientLeaveRoom` are refused for encrypted rooms. Voice in encrypted rooms is end-to-end encrypted since protocol 21 (below). Clients replay against their pins, keep the verified head per room in the key store, and treat every verification failure as final ("This room's member list was changed on the server"); never use `room_members` for key decisions. See `client/AGENTS.md` and `server/AGENTS.md`.
- Sender chains in encrypted rooms (protocol 19, migration 8, design 6.3-6.6): a room message is either plaintext (`content`, unencrypted rooms only) or a `SealedRoomMessage` in `ClientChatMessagePayload.sealed`/`ServerChatMessagePayload.sealed`/`StoredChatMessage.sealed` with an empty `content` and a random `clientMessageId` (encrypted rooms only). The router verifies a sealed message's and a `ClientRoomKeyEnvelope`'s signature against the **session's** identity key; the database stores a message only at the room's current `log_version` (else `ServerProtocolError "Room key is out of date"`) and an envelope only from a member to members (an older epoch only for a chain it already stores), and refuses a reused `(sender, clientMessageId)` or `(sender, chain, index)`. Envelopes go to the accounts their wraps name (`ServerRoomKeyEnvelope`), `ClientFetchRoomKeys` returns only envelopes with a wrap for the requester, and `ClientRequestRoomKey` is relayed to the chain's sender (`ServerRoomKeyRequest`). Clients distribute each chain to the verified log's members of its epoch with their **pinned** encryption keys, never resume a sending chain after a restart (no index is ever reused), keep received chains in the key store (format 4, a cache the server's envelopes rebuild), and answer a key request only for a requester who was a member of that epoch in the verified log. See `client/AGENTS.md` (Encrypted Room Messages) and `server/AGENTS.md`.
- Full history in encrypted rooms (protocol 20, migration 9, design 6.6): decided by the **verified** log's `historyVisibility`, never the server's flag. A `RoomKeyForward` envelope (`makeRoomKeyForwardAAD`, label `"haychat-room-key-forward-v1"`: server, room, epoch, the chain's original sender, chain, forwarder, recipient; exactly one wrap; signed by the forwarder) hands a chain someone else sent to one member; it travels as `ClientRoomKeyEnvelope` with `senderId` set and is stored with `room_key_envelopes.forwarder_user_id` (`RoomKeyEnvelope.forwarderId`). The server stores a forward only in a Full history encrypted room, from a member to a member, for a chain it already stores, and drops it silently when the recipient already has a wrap for the chain (first copy wins); it relays `ClientRequestRoomKey` in Full history rooms to every member's sessions (`ServerRoomKeyRequest.senderId` names the chain's sender). The client that signs an `Add` forwards every chain it holds from before it; any member answers a request for a chain it holds when the requester is a current member (its own chain as a SenderKey re-seal); a forward is accepted only from a forwarder who was a member at the same time, for a chain whose sender was a member of its epoch, verified against the forwarder's pin. Messages still verify against their real senders. From join rooms never forward, answer, or accept forwards of others' chains.
- Encrypted voice in encrypted rooms (protocol 21, no migration, design `docs/plan/e2ee-voice-design.md`): each participant makes a random voice key per voice session and generation and sends it as `ClientVoiceKey` (a `VoiceKey` envelope, kind 4, `makeVoiceKeyAAD`, label `"haychat-voice-key-v1"`: server, room, epoch, sender, `voiceSessionId`, generation, `createdAt`), wrapped for every other member of its **verified** log's current epoch with their **pinned** keys. The router checks the signature against the **session's** identity key, accepts it only from a session in that room's voice at the room's current log version ("Voice key is out of date" otherwise), keeps the latest per participant **in memory only** (never stored, never forwarded outside the room's voice), fans it out as `ServerVoiceKey` and hands joiners every current key right after their acknowledging `ServerVoiceParticipants`; `ClientRequestVoiceKey` is relayed as `ServerVoiceKeyRequest` (rate limited). Frames in an encrypted room carry a `SealedVoicePayload` (`common/voice_e2ee.odin`: `version ‖ keyId ‖ ciphertext ‖ tag`, XChaCha20-Poly1305, nonce = `frameSequence` LE ‖ 20 zero bytes, AAD `"haychat-voice-frame-v1"` binding server, room, sender, epoch, session, generation, sequence, flags, version and keyId), sealed and opened in caller buffers without allocating; the relay skips the Opus TOC check there, drops unsealed payloads (`NotSealed`) and forwards the rest unchanged (`NetworkVoiceRoute.encrypted`). A key is used by one engine only (a new generation on every engine (re)open), the engine refuses to reseal a sequence, and keys never reach disk. Listeners open keys only with the sender's pin, refuse keys older than an hour or more than 5 minutes ahead, never retry a failure, and an engine in an encrypted room never sends or plays plaintext; encrypted rooms keep constrained VBR but pad every Opus packet to one size per bitrate (`voiceE2EEPaddedOpusBytes`, `opus.padPacket`), never constant bitrate, which dropped steady tones with in-band FEC. See `client/AGENTS.md` (Encrypted Voice) and `server/AGENTS.md` (Voice Rooms).
- Signed room messages (protocol 22, migration 10, #90): every plaintext room message is signed by its sender (`signPlaintextRoomMessage`, label `"haychat-room-plain-v1"`: server key, room, sender, a random non-zero `clientMessageId` and the content), carried in `ClientChatMessagePayload`/`ServerChatMessagePayload`/`StoredChatMessage.signature`. The router verifies it against the **session's** identity key and refuses unsigned plaintext (`ROOM_MESSAGE_SIGNATURE_INVALID_MESSAGE`); the database stores the signature and refuses a reused `(sender, clientMessageId)`. Clients verify every room message against the sender's **pinned** identity key (fetching the bundle first, while the message shows no text) and never show one that fails, whether plaintext or sealed: a sealed message that fails at or before its signature check is not shown either. Migration 10 deleted every unsigned message, room and direct. See `client/AGENTS.md` (Encrypted Room Messages) and `server/AGENTS.md`.
- End-to-end encryption primitives (`common/e2ee.odin`, design `docs/plan/e2ee-design.md`) are pure procedures on caller buffers with fixed, versioned binary layouts documented at the top of the file; carry them as CBOR byte strings, never re-encode them. Open and verify only through its procedures (signature against the pinned identity key first, every failure fatal and never retried), and rerun `dev/tools/e2ee-vectors.py` after changing a layout or label.
- `MessageType` numbers its members automatically. `common/protocol_test.odin` pins the wire value of every member in use; never renumber, add new members at the end of the enum, pin each member you put on the wire, and bump `protocolVersion` for any payload or enum change.
- The database schema changes only through migrations: append the next version to `DATABASE_MIGRATIONS` in `server/database_migrations.odin` and never edit one that has merged. The server migrates at startup and never drops tables; it refuses a database it cannot migrate. See "Schema Migrations" in `server/AGENTS.md`.
- Chat history uses message IDs as stable pagination cursors. Fetch the newest page with cursor `0`, request older pages with the oldest loaded message ID, and merge duplicate page boundaries by message ID.
- CBOR-decoded strings and dynamic arrays are owned allocations. Transfer ownership explicitly between packet/event/message layers, clear the source after transfer, and free ignored payloads. Do not retain borrowed decoded data after its packet or event is deinitialized.

## Security

- Use appropriate data types that limit exposure of sensitive information
- Never commit secrets or API keys to repository
- Use environment variables for sensitive data
- Validate all user inputs on both client and server
- Follow principle of least privilege for database access and other resources

## Configuration

When adding new configuration options, update all relevant places:

- `config.odin` for the new configuration option
- `config_test.odin` for tests related to the new configuration option
- Documentation to include the new configuration option and its purpose
- Any relevant code that uses the new configuration option should be updated to handle it appropriately
- Ensure that the new configuration option is properly validated and has appropriate default values if necessary
- If the new configuration option is sensitive (e.g., API keys, secrets), ensure that it is not hardcoded in the codebase and is instead loaded from environment variables or secure vaults
- Documentation in `docs/client-configuration.md` (client `config.json` keys) or `docs/server-configuration.md` (`HAYCHAT_*` server variables, also listed in `.env.example`)

All configuration keys use consistent naming and MUST be documented.
