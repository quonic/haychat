## Project Status - Unreleased

Making breaking changes to the project is currently allowed, but it is recommended to avoid doing so unless necessary. If breaking changes are made, they should be clearly documented in the commit messages and in the documentation to ensure that users are aware of the changes and can update their code accordingly. ## Odin Programming Language

- Overview of the language: <https://odin-lang.org/docs/overview/>
- Base Library Collection: `$HOME/Odin/base`
- Core Library Collection: `$HOME/Odin/core`
- Vendor Library Collection: `$HOME/Odin/vendor`
- Shared Library Collection: `$HOME/Odin/shared`
- SDL3 bindings: `$HOME/Odin/vendor/sdl3` (SDL3_ttf bindings in `$HOME/Odin/vendor/sdl3/ttf`)
- GitHub Repository: <https://github.com/odin-lang/Odin>

### Language Quirks

- Variable declarations follow the syntax `name: type = value`, where the type can be inferred from the value if it is not explicitly specified. For example, `x := 5` will infer that `x` is of type `int`, while `y: f32 = 3.14` explicitly declares that `y` is of type `f32`. If the type cannot be inferred from the value, it must be explicitly declared to avoid compilation errors.
- For getting the length of an array, use `len(array)`. This includes strings, slices, and other array-like structures.

## Project Structure

- `client/`: Contains the client-side code for the HayChat application, including the GUI and client logic.
- `server/`: Contains the server-side code for the HayChat application, including the ENet network thread, the router, database management and migrations, and client-server communication. It has no HTTP or admin port.
- `common/`: Contains shared code and definitions used by both the client and server.
- `docs/`: User, operator, and developer documentation; `docs/README.md` is the index. `docs/plan/` holds design documents and past round plans, which are historical records and not kept up to date. When behaviour changes, update the document that describes it (see the index).
- `deploy/`: Production server image (`deploy/Containerfile`), quadlet units, SQL helpers, and the release archive script used by `.forgejo/workflows/release.yml`. See `deploy/README.md`; `./dev.sh release-image --smoke` builds and smoke-tests the image.

## Code Style

- Tabs are used for indentation, with a standard indentation level of 4 spaces.
- One True Brace Style is used for braces, with the opening brace on the same line as the control statement and the closing brace on a new line.
- Lines should not exceed 100 characters in length, and should be broken up into multiple lines if necessary.
- Variable and function names should be descriptive and use camelCase.
- In camelCase names, use "URL" (not "Url"), "API" (not "Api"), "ID" (not "Id"), and "HTTP" (not "Http").
- Constants should be in all uppercase letters with underscores separating words.
- Comments should be used to explain the purpose of code blocks and any complex logic, and should be written in English.

## Odin Checker

- Checking for compile errors for server component: `odin check server`
- Checking for compile errors for client component: `odin check client -target:windows_amd64` and `odin check client -target:linux_amd64` for Windows and Linux respectively.
- These need `odin` on `PATH`. Without a host toolchain, run them in the dev image: `./dev.sh check`, or `./dev.sh shell` for ad-hoc commands.

## Development Environment

- Development runs in podman containers through `./dev.sh` (`./dev.sh help` lists commands). The dev image (`dev/Containerfile`) holds Fedora 44, the system libraries, and the Odin toolchain pinned in `dev/bootstrap-odin.sh`; containers get a snapshot of the working tree, never the host's `logs/`, `storage/`, or `~/.config/haychat`.
- Package and pin changes go in `dev/install-packages.sh` and `dev/bootstrap-odin.sh`. Both the dev image and Forgejo CI (`.forgejo/workflows/ci.yml`) use them, and the image tag is a hash of those files.
- `./dev.sh up` / `restart` / `down` / `reset` manage the dev pod (PostgreSQL + server). `./dev.sh reset` deletes only the dev pod's volumes; no command touches the host's client config.
- The forge is Forgejo with a Linux-only runner. Windows is covered by `odin check client -target:windows_amd64` in `./check.sh`.

## Testing

- Test files: `*_test.odin` (e.g., `chat_test.odin`)
- Full gate (what CI runs): `./dev.sh ci`, which runs `./check.sh` and then `dev/live-proof.sh --all` (startup auth, two-client room chat, two-client direct message, in-process voice, headless harness, admin, two-process voice, GUI automation, and server SQL proofs, and the startup failure exit check) against a throwaway PostgreSQL. `./dev.sh check` runs only `./check.sh`. Tests run with `ODIN_TEST_FAIL_ON_BAD_MEMORY`, so any leak or bad free fails the suite.
- Prefer component-scoped checks while editing: `odin test common`, `odin test client`, or `odin test server -define:ODIN_TEST_THREADS=1`. The serial server suite is the reliable default for router/database tests.
- Acting as a user: `client --headless` runs the client without a window, reading commands on stdin and printing JSON lines on stdout, so an agent or script can connect, list rooms, send, and wait for events. See `docs/testing-harness.md`; `./dev.sh live --harness` runs its smoke test against a throwaway server, and `./dev.sh live --admin` runs `dev/admin-proof.sh` (two headless clients: a live role change, a locked rename, kick, ban and unban, and a room made text-only).
- Voice as a user: the harness's `voice-*` commands join voice, send a tone or file (`voice-source`), record into a raw F32LE mono 48 kHz file (`voice-sink`, `voice-flush`) and report counters (`voice-stats`), with `voice_status` and `voice_speaking` events; `dev/tools/voice-check` checks a recording for a tone with the client's Goertzel analysis (`client/toneanalysis`). `./dev.sh live --voice` runs `dev/voice-proof.sh`: two client processes, a 440 Hz tone through the server, checked by `voice-check` and the counters, then the same through SDL's disk audio driver, through injected loss, and one voice session per user (two profiles sharing one identity key with different `device_id` values: the second join takes voice over). See "Voice" in `docs/testing-harness.md`.
- Voice on real audio devices (manual, not in CI): `dev/voice-manual-test.sh [HOST:PORT]` on a host with PipeWire creates virtual devices only (`node.dont-fallback` on every stream, a routing check before any sound, module list and default devices restored on exit), runs two headless clients on SDL's PipeWire driver, and measures tone, speech through the voice activity gate, and mouth-to-ear delay. Measure a changed voice constant with it (`HAYCHAT_VOICE_MANUAL_CLIENT`) before changing a default. See `docs/voice-manual-test.md`.
- Driving the real window: `client --ui-script FILE` runs the GUI from a script (click by drawn text or widget ID, type, keys, wait for text, BMP screenshots) by pushing synthetic SDL events, with no OS input injection; `SDL_VIDEO_DRIVER=offscreen` needs no display. See "GUI Automation" in `docs/testing-harness.md`; `./dev.sh live --ui` runs `dev/ui-smoke.sh` (GUI alice and headless bob chat and exchange a DM, then admin alice creates a room, joins, mutes and leaves voice on SDL's dummy audio driver, uses context menus, and drives the admin UI).
- Use the built-in testing library from Odin. `import "core:testing"` and any procedures must have `t: ^testing.T,` as the first parameter.
- Use `assert(a == VALUE, "message that test failed")` for assertions in tests, and provide a clear message that indicates what the expected value was and what the actual value is if the assertion fails.

## Architecture

- Client GUI: a small immediate-mode UI toolkit in `client/ui`, drawn with `vendor:sdl3` (SDL_Renderer) and `vendor:sdl3/ttf` (text). Screens in `client/view.odin` call `State_*` action procedures directly.
- Global push-to-talk: `client/hotkey` (Windows `GetAsyncKeyState`, X11 `XQueryKeymap`, Wayland GlobalShortcuts portal over libdbus-1), every system library loaded at runtime; see "Voice UI and Settings" in `client/AGENTS.md`. Its tests need Xvfb, libXtst and dbus-daemon (in the dev image) and fail without them under `HAYCHAT_REQUIRE_HOTKEY_TESTS=1`, as in `check.sh`.
- Database: `shared:pg` bindings for libpq version 17, repository: <https://github.com/laytan/odin-postgresql>
- Client-Server Communication: `vendor:ENet` bindings for enet
- Client screens beyond chat: per-server settings (`client/server_settings.odin`) and per-user voice volume and mute (`client/user_voice.odin`) are client-local `config.json` fields, never synced (only a per-server display name reaches the server, as the sign-in name); context menus (`client/context_menu.odin`) and the admin UI (`client/admin_ui.odin`) send through the existing actions. See `client/AGENTS.md`.

## Chat Protocol And Ownership

- Shared encrypted application packets and database IPC types belong in `common/protocol.odin`. When changing a wire payload, update both client transport decoding and server routing, then validate `odin test common` before component tests.
- Room access is server-authoritative and membership-scoped (protocol 15, migration 4): every room has an access mode (`RoomAccess`: Public, Member invite, Admin invite) and a history setting fixed at creation (`RoomHistoryVisibility`: From join, Full; Public always reads Full). New accounts join only Public rooms and a new Public room includes every account; an invite room includes its creator only when `ClientCreateRoomPayload.creatorJoins` is set. `room_members` is the authoritative check for every send, history page, member list and voice join; a From join member reads history only after `room_members.joined_at`. Who may add (`ClientAddRoomMember`: admins in invite rooms, members in Member invite rooms, nobody in Public rooms), remove (`ClientRemoveRoomMember`: admins only) and leave (`ClientLeaveRoom`: members of non-public rooms) is decided in one SQL statement with the change (`server/database_room_access.odin`). Clients may request room lists, history and members (`ClientFetchRoomMembers`, members and admins), but must treat `ServerListRooms`, `ServerRoomMembershipChanged` (whose `userId` says whose membership changed), edit, and delete events as the source of truth for visible rooms; admins see every room through `ClientAdminListRooms`. Encryption (E4) is not part of it.
- Room management (create, edit, delete) is admin-only and checked by the server per request. `ServerAuthSuccess.isAdmin` (protocol 8) only tells the client which controls to show; a role changed by an admin from a client reaches the target's sessions at once as `ServerAccountUpdated` (protocol 14), one changed in the database on the next connection.
- Admin actions on accounts (protocol 14): `ClientAdminSetRole`, `ClientAdminRenameUser`, `ClientAdminKickUser`, and `ClientAdminBanUser` are answered with `ServerAdminActionResult` or a `ServerProtocolError`. The server checks the requester's role and the guards (no kick, ban, or role revoke of yourself; no kick or ban of another admin; never the last admin) in the same SQL statement as the change (`server/database_admin.odin`). It sends `ServerUserUpdated` (a full `UserSummary`, which now carries `isAdmin` and `isBanned`) to every session and `ServerAccountUpdated` to the target's sessions. An admin rename locks the name (`users.nickname_locked`): sign-in keeps it and reports it in `ServerAuthSuccess.nickname`/`nicknameLocked`. Kick and ban send `ServerSessionEnded{kind, reason}` before the disconnect, and a banned sign-in is refused with `ServerAuthFailure` "This account is banned from this server" (plus ": reason"); clients treat both as failures that are not retried until the user asks. Rooms have a type (`RoomSummary.roomType`, `common.RoomType`, only Chat, Voice and ChatAndVoice): a voice-only room refuses chat, a text-only room refuses voice joins, and editing a room to text-only removes its voice participants.
- Direct messages are server-authoritative too: a client must not append a sent direct message locally but wait for the `ServerDirectMessage` (or `ServerSealedDirectMessage`) echo, which carries the stored ID and timestamp and reaches every session of both users. Direct history pages exactly like room history. `ServerUserList` and `ServerUserPresence` are the source of truth for who exists and who is online.
- Encrypted direct messages (protocol 17, migration 6, design 4.5-4.6): a client encrypts whenever `State_e2eePeerKeyInfo.canEncrypt` (`ClientSealedDirectMessage`: a `sealDirectMessage` envelope bound to the server key, both user IDs, both **pinned** identity keys and a random 16-byte `clientMessageId`), queues a send while the peer's key is Pending, and otherwise sends only through the per-conversation **Send without encryption** switch (a signed `ClientDirectMessage`; unsigned ones are refused). The server checks the envelope's structure in the router and its signature in the database worker (`databaseCheckSealedDirectMessage`, with the recipient's identity key from `users.public_key`), stores it byte for byte with an empty `content` only while the recipient keeps that key, and refuses a reused `(sender, clientMessageId)`. Clients open envelopes only with the sender's pin and their own key, never retry a failure, mark replays, and flag encrypted conversations in the key store (no downgrade). See `client/AGENTS.md` and `server/AGENTS.md`.
- Voice frames (`ClientVoiceFrame`, `ServerVoiceFrame`) are binary, never CBOR: `common/voice_wire.odin` encodes them into caller buffers and decodes them without allocating, sealed in voice datagrams (`sealVoiceDatagram`/`openVoiceDatagram`) on ENet channel 2. A decoded `opus` slice borrows its input buffer and is valid only while that buffer is; copy it to keep it. The voice AAD (`makeVoiceAAD`) is the control AAD plus the datagram's kind byte and is never used for control packets. Voice control (`ClientJoinVoice` … `ServerVoiceLeft`, protocol 10) is ordinary CBOR on the control channel; `ServerVoiceParticipants.recipientJoined` (protocol 12) is set per recipient session and is the only join acknowledgement, because participants carry user IDs, not sessions, with `*_deinit` helpers in `common/protocol.odin` for its owned strings and arrays. `ClientVoiceData`/`ServerVoiceData` are retired placeholders that are never sent and stay only to keep later wire values.
- One voice session per user (protocol 13, Q2): the server keeps at most one voice session per account, so a participant list names each user once. A join the user asked for takes voice over from the account's other session, which gets `ServerVoiceLeft{"joined voice on another device"}`; the client's automatic re-join after a reconnect (`ClientJoinVoicePayload.rejoin`) replaces only a session with the same `deviceId` and is otherwise refused with "voice is active on another device". `deviceId` is the profile's `device_id` config key, 32 lowercase hex characters (`common/voice_device.odin`); the server refuses a join without a valid one but keeps the session. A decoded `ClientJoinVoicePayload` owns `deviceId` (`ClientJoinVoicePayload_deinit`).
- Read state is server-authoritative too (protocol 11): the server keeps a read marker per account and room and per account and direct conversation, and `ServerListRooms`, `ServerDirectConversations`, and `ServerReadMarker` carry the marker and unread count. A client counts live messages from others between those, never lowers a count itself, and marks a conversation read only while the user is viewing it (`client/read_state.odin`); the server fans `ServerReadMarker` out to every session of the account. The unread rules are in `server/AGENTS.md`.
- Account encryption keys (protocol 16, migration 5, design 2-3): each profile's X25519 key lives in `config.json` (`encryption_*`), signed by the identity key, and is published once per session (`ClientPublishEncryptionKey`); the server verifies it against the session's identity key before storing it in `user_encryption_keys`. `ClientFetchUserKeys` (1..`USER_KEYS_FETCH_MAX` distinct IDs) is answered by `ServerUserKeys` (bundles plus `missingUserIds`), and a stored change goes to every session as `ServerUserKeyChanged`. `UserSummary.identityPublicKey`/`hasEncryptionKey` are filled everywhere a `UserSummary` is built. Clients pin bundles per server in the key store (`client/keystore.odin`) and decide trust in `client/e2ee_state.odin`: callers that encrypt or verify use the pin (`State_e2eePeerKeyInfo`), never a key the server sent. See `client/AGENTS.md` and `server/AGENTS.md`.
- Encrypted rooms and their member log (protocol 18, migration 7, design 6.1-6.2): `RoomSummary.encrypted`/`logVersion`; an encrypted room is Member or Admin invite, its flag never changes, and the server creates it with **no members**: the creator's client signs the log's `Create` (the room ID is in every entry) after `ServerCreateRoom` and sends it with `ClientAppendRoomLog`. The server replays the stored log on every append (`server/database_room_log.odin`), validates the entry with `RoomLogState_validate` using accounts' `users.public_key` as its pins, applies its own 5.1 rules on top (an add needs an admin or a Member invite member **and** the log's signature), and stores and applies it to `room_members` in one transaction; `ServerRoomLog` fans it out to members, managers and the target. An admin's `ClientRemoveRoomMember` becomes a server-written unsigned Remove; `ClientAddRoomMember`/`ClientLeaveRoom` are refused for encrypted rooms. Voice in encrypted rooms is refused until E6. Clients replay against their pins, keep the verified head per room in the key store, and treat every verification failure as final ("This room's member list was changed on the server"); never use `room_members` for key decisions. See `client/AGENTS.md` and `server/AGENTS.md`.
- Sender chains in encrypted rooms (protocol 19, migration 8, design 6.3-6.6): a room message is either plaintext (`content`, unencrypted rooms only) or a `SealedRoomMessage` in `ClientChatMessagePayload.sealed`/`ServerChatMessagePayload.sealed`/`StoredChatMessage.sealed` with an empty `content` and a random `clientMessageId` (encrypted rooms only). The router verifies a sealed message's and a `ClientRoomKeyEnvelope`'s signature against the **session's** identity key; the database stores a message only at the room's current `log_version` (else `ServerProtocolError "Room key is out of date"`) and an envelope only from a member to members (an older epoch only for a chain it already stores), and refuses a reused `(sender, clientMessageId)` or `(sender, chain, index)`. Envelopes go to the accounts their wraps name (`ServerRoomKeyEnvelope`), `ClientFetchRoomKeys` returns only envelopes with a wrap for the requester, and `ClientRequestRoomKey` is relayed to the chain's sender (`ServerRoomKeyRequest`). Clients distribute each chain to the verified log's members of its epoch with their **pinned** encryption keys, never resume a sending chain after a restart (no index is ever reused), keep received chains in the key store (format 4, a cache the server's envelopes rebuild), and answer a key request only for a requester who was a member of that epoch in the verified log. See `client/AGENTS.md` (Encrypted Room Messages) and `server/AGENTS.md`.
- Full history in encrypted rooms (protocol 20, migration 9, design 6.6): decided by the **verified** log's `historyVisibility`, never the server's flag. A `RoomKeyForward` envelope (`makeRoomKeyForwardAAD`, label `"haychat-room-key-forward-v1"`: server, room, epoch, the chain's original sender, chain, forwarder, recipient; exactly one wrap; signed by the forwarder) hands a chain someone else sent to one member; it travels as `ClientRoomKeyEnvelope` with `senderId` set and is stored with `room_key_envelopes.forwarder_user_id` (`RoomKeyEnvelope.forwarderId`). The server stores a forward only in a Full history encrypted room, from a member to a member, for a chain it already stores, and drops it silently when the recipient already has a wrap for the chain (first copy wins); it relays `ClientRequestRoomKey` in Full history rooms to every member's sessions (`ServerRoomKeyRequest.senderId` names the chain's sender). The client that signs an `Add` forwards every chain it holds from before it; any member answers a request for a chain it holds when the requester is a current member (its own chain as a SenderKey re-seal); a forward is accepted only from a forwarder who was a member at the same time, for a chain whose sender was a member of its epoch, verified against the forwarder's pin. Messages still verify against their real senders. From join rooms never forward, answer, or accept forwards of others' chains.
- End-to-end encryption primitives (`common/e2ee.odin`, design `docs/plan/e2ee-design.md`) are pure procedures on caller buffers with fixed, versioned binary layouts documented at the top of the file; carry them as CBOR byte strings, never re-encode them. Open and verify only through its procedures (signature against the pinned identity key first, every failure fatal and never retried), and rerun `dev/tools/e2ee-vectors.py` after changing a layout or label.
- `MessageType` numbers its members automatically. `common/protocol_test.odin` pins the wire value of every member in use; never renumber, add new members at the end of the enum, pin each member you put on the wire, and bump `protocolVersion` for any payload or enum change.
- The database schema changes only through migrations: append the next version to `DATABASE_MIGRATIONS` in `server/database_migrations.odin` and never edit one that has merged. The server migrates at startup and never drops tables; it refuses a database it cannot migrate. See "Schema Migrations" in `server/AGENTS.md`.
- Chat history uses message IDs as stable pagination cursors. Fetch the newest page with cursor `0`, request older pages with the oldest loaded message ID, and merge duplicate page boundaries by message ID.
- CBOR-decoded strings and dynamic arrays are owned allocations. Transfer ownership explicitly between packet/event/message layers, clear the source after transfer, and free ignored payloads. Do not retain borrowed decoded data after its packet or event is deinitialized.

## Security

- Use appropriate data types that limit exposure of sensitive information
- Never commit secrets or API keys to repository
- Use environment variables for sensitive data
- Validate all user inputs on both client and server
- Follow principle of least privilege for database access and other resources

## Configuration

When adding new configuration options, update all relevant places:

- `config.odin` for the new configuration option
- `config_test.odin` for tests related to the new configuration option
- Documentation to include the new configuration option and its purpose
- Any relevant code that uses the new configuration option should be updated to handle it appropriately
- Ensure that the new configuration option is properly validated and has appropriate default values if necessary
- If the new configuration option is sensitive (e.g., API keys, secrets), ensure that it is not hardcoded in the codebase and is instead loaded from environment variables or secure vaults
- Documentation in `docs/client-configuration.md` (client `config.json` keys) or `docs/server-configuration.md` (`HAYCHAT_*` server variables, also listed in `.env.example`)

All configuration keys use consistent naming and MUST be documented.
